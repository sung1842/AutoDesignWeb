# R1 리뷰 — UI 디자인 / 디자인 시스템 관점

- 리뷰어 역할: 국내 대형 IT 기업 시니어 UI 디자이너(디자인 시스템 담당)
- 대상: `spec_v1.md` (v1)
- 기준: `rubric.md` (C1 완결성 / C2 AI 구현 가능성 / C3 대기업 통과)
- 관점 구분
  - **(A) 서비스 자체 UI**: 진단·결과·생성 대기·비교·편집·내보내기 화면. 서비스가 AI스럽게 보이면 "AI 티를 지워준다"는 약속을 스스로 깨게 된다.
  - **(B) 생성되는 시안의 UI 시스템**: token, 컴포넌트, 섹션 블록, 반응형, 폰트/이미지/아이콘 라이선스, 다크 모드, 내보내기 코드, 조화 규칙 수치.

## 총평

v1은 "왜 AI스러워지는가"와 "어떻게 피할 것인가"의 **원칙**은 좋지만, 디자인 시스템 관점의 **실체(목록·값·범위·스키마)가 거의 비어 있다.** 기획서는 "컴포넌트 라이브러리 하나 + CSS 변수 테마", "조화 규칙으로 스냅", "컴포넌트 부품만으로 레이아웃 트리 JSON"을 핵심 장치로 쓰는데, 정작 그 token 이름, 컴포넌트, 섹션 블록, 프리셋 값이 하나도 정의되어 있지 않다. 그래서 Claude Code가 구현하다 보면 결국 **shadcn/ui 기본값(zinc 팔레트, radius 0.5rem, Geist/Inter, Lucide)**으로 채우게 되고, 이것이 바로 기획서가 금지한 "AI 티" 그 자체다. 또 서비스 자체 UI(A)는 방향이 한 줄도 없다.

심각도 집계: **Blocker 6 / Major 13 / Minor 5**

# (A) 서비스 자체 UI

## UI-01 서비스 자체 UI의 디자인 방향과 token이 없다
- **심각도**: Blocker
- **관련 섹션**: 1장 기술 스택("shadcn/ui 베이스"), 3장(AI 느낌 지우기), 전체
- **허점**: 기획서의 디자인 논의가 모두 "생성되는 시안"에 대한 것이다. 사용자가 실제로 머무는 서비스 화면(진단, 결과, 편집)의 디자인 방향, 서체, 색, token은 한 줄도 없다. 기술 스택에 "shadcn/ui 베이스"만 있다.
- **왜 문제인가**:
  1. Claude Code는 정의가 없으면 shadcn 기본 테마(zinc/slate, `--radius: 0.5rem`, Geist/Inter, Lucide, 흐린 그림자 카드)를 쓴다. 3장 AI 티 목록 중 5~6개(전부 Inter, 균일한 rounded-xl+흐린 그림자, 기본 Lucide, 3열 아이콘 카드, 정중앙 히어로)가 서비스 자체에서 그대로 재현된다.
  2. "AI 티 없는 디자인을 만들어 준다"는 서비스가 AI스럽게 생겼다면 첫 화면에서 신뢰를 잃는다. 대기업 디자인 리뷰에서도 "자사 UI가 약속하는 가치를 증명하는가"는 기본 질문이다.
  3. 서비스 크롬(chrome)이 색과 개성이 강하면 사용자의 시안 판단을 오염시킨다. 시안과 서비스 UI의 위계를 분리하는 원칙이 필요하다.
- **보완안** (기획서에 붙여넣기용):

> ### 10. 서비스 자체 UI 디자인 원칙
> **콘셉트: "조용한 작업대(Quiet Workbench)"** — 서비스는 무채색에 가까운 작업대이고, 색과 개성은 사용자의 시안만 가진다.
> 1. **크롬과 콘텐츠의 분리**: 서비스 UI(크롬)는 무채색 + 강조색 1개만 쓴다. 시안 미리보기 영역에는 서비스 강조색, 그림자, 배경 패턴을 넣지 않는다. 시안 프레임은 1px 무채색 테두리만 쓴다.
> 2. **에디토리얼 톤**: 서비스는 "디자인 잡지/스튜디오 툴" 톤이다. 결과 유형 이름과 섹션 제목에는 세리프 디스플레이 서체, 본문과 UI에는 고딕을 쓴다.
> 3. **자기 린터 통과 의무**: 서비스 자체 화면도 11장 AI 티 린터를 통과해야 한다(보라~파랑 그라디언트, 그라디언트 텍스트, 이모지 아이콘, "✨ New" 배지, 3열 아이콘 기능 카드, 컬러 블롭 금지).
> 4. **shadcn/ui는 동작(접근성, Radix primitive)만 쓴다**: 기본 테마 변수는 모두 아래 서비스 token으로 덮어쓴다. shadcn 기본 `zinc`/`slate` 팔레트, 기본 `--radius`, 기본 폰트는 그대로 쓰지 않는다.
>
> **서비스 token (MVP 고정값)**
>
> | 그룹 | token | 값 |
> |---|---|---|
> | 색 | `--svc-bg` | `#F7F6F3` (따뜻한 오프화이트) |
> | | `--svc-surface` | `#FFFFFF` |
> | | `--svc-fg` | `#1A1A18` |
> | | `--svc-fg-muted` | `#5E5C57` (bg 대비 ≥ 4.5:1) |
> | | `--svc-border` | `#E3E1DC` |
> | | `--svc-accent` | `#D2461E` (버밀리언, 보라/파랑 계열 금지) |
> | | `--svc-on-accent` | `#FFFFFF` (대비 ≥ 4.5:1) |
> | | `--svc-focus` | `#1A1A18` 2px outline + 2px offset |
> | 서체 | 본문/UI | Pretendard Variable (OFL-1.1), dynamic subset |
> | | 디스플레이 | MaruBuri 또는 Hahmlet (OFL-1.1) 중 하나만, 결과 유형 이름과 H1에만 사용 |
> | | 숫자/코드 | JetBrains Mono (OFL-1.1) |
> | 타입 스케일 | 12 / 14 / 16 / 20 / 28 / 40 / 56 px | 본문 16px, 행간 1.6, 헤드라인 자간 -0.02em |

- **수용 기준**:
  - `globals.css`에 `--svc-*` token이 정의되어 있고, shadcn 기본 CSS 변수가 모두 이 token으로 매핑되어 있다(grep 했을 때 shadcn 기본 HSL 값이 남아 있지 않음).
  - 서비스 주요 6개 화면의 Playwright 스크린샷이 11장 AI 티 린터를 위반 0건으로 통과한다.
  - 서비스 화면에 쓰인 서체가 `Inter`, `Geist`, `system-ui` 단독이 아니다(computed style로 검사).

## UI-02 화면 목록과 화면별 상태가 정의되지 않았다
- **심각도**: Blocker
- **관련 섹션**: 1장(1~5단계), 6장(생성 파이프라인)
- **허점**: 단계는 있지만 화면(route) 목록, 각 화면의 구성 요소, 상태(로딩, 에러, 빈 상태, 진행 중 이탈, 재시도)가 없다. 특히 6장 파이프라인(후보 6개 생성 → 렌더 → 채점 → 수정 루프 → 상위 3~4개)은 수십 초에서 수 분이 걸릴 수 있는데, 대기 UX가 없다.
- **왜 문제인가**: Claude Code가 화면 구조를 임의로 정하게 되고(C2 FAIL), 긴 생성 대기 중에 이탈이 생기면 핵심 퍼널 지표가 무너진다. 대기업 리뷰에서는 화면 흐름도(IA)와 예외 상태 정의가 필수 산출물이다.
- **보완안**:

- **수용 기준**:
  - 위 10개 route가 모두 존재하고, 각 화면의 "필수 상태"를 Playwright 시나리오로 재현할 수 있다(Storybook 또는 `?state=` 디버그 파라미터).
  - 생성 대기 화면이 서버 단계 이벤트를 받아 갱신된다(타이머 기반 가짜 진행 금지).
  - 진단 도중 새로고침해도 진행 중이던 문항부터 이어진다.

## UI-09 설문 비교 카드 규격이 없다
- **심각도**: Major
- **관련 섹션**: 1장 1·2단계, 2장 "설문에는 같은 스타일 벡터로 재현한 오리지널 시안"
- **허점**:
  1. 4장 비교에서 무엇을 통제하고 무엇을 바꾸는지가 없다. 카피, 이미지, 레이아웃이 시안마다 다르면 사용자는 스타일이 아니라 "사진이 예뻐서"를 고른다.
  2. 오리지널 시안을 누가, 몇 장, 어떤 렌더러로 만드는지가 없다. 1단계 8~10문항 × 4장 = 문항 풀만 최소 40장이 필요하고, 문항 로테이션까지 고려하면 120장 이상이다.
  3. 모바일에서 4장을 2×2로 놓으면 한 장 폭이 약 170px라서 스타일을 판단할 수 없다.
  4. "둘 다 별로" 같은 탈출구가 없다.
- **왜 문제인가**: 입력 데이터(선택)의 품질이 취향 벡터 전체의 품질을 결정한다. 통제 변인이 없으면 벡터가 노이즈가 된다.
- **보완안**:

> ### 10.2 설문 비교 카드 규격
> - **생성 방식**: 설문 시안은 생성 시스템의 렌더러(같은 컴포넌트·섹션 라이브러리)로 프리셋 token을 적용해 만든다. 실제 사이트 스크린샷은 설문에 쓰지 않는다. 사람이 최종 검수한다.
> - **통제 변인**: 한 문항 안의 시안은 같은 가상 브랜드, 같은 카피(글자 수 ±10%), 같은 이미지 슬롯 구성을 쓴다. 이미지는 같은 사진을 각 시안의 톤 처리(그레이스케일/듀오톤/원본)로만 바꾼다. 바뀌는 것은 token(+ 1단계에 한해 섹션 variant)뿐이다.
> - **시안 풀(MVP)**: 프리셋 8종 × 가상 브랜드 3종 × 히어로 variant 2종 = 48장. 1단계 문항은 매번 서로 다른 프리셋 4개를 뽑고, 같은 세션에서 같은 시안이 다시 나오지 않게 한다.
> - **썸네일 렌더**: 뷰포트 1440×900, DPR 2, 첫 화면 기준 크롭, WebP q80, 장당 ≤ 250KB. 모바일 버전은 390×844로 따로 렌더한다.
> - **레이아웃**: 데스크톱(≥1024)은 2×2 그리드, 카드 최소 폭 480px. 모바일(<768)은 한 장씩 전체 폭으로 보여주고 좌우 스와이프로 4장을 넘긴 다음 하단 썸네일 바에서 선택한다. 길게 누르면 전체 화면 확대.
> - **위치 무작위화**: 카드 순서를 문항마다 섞고 선택 로그에 위치를 기록한다(위치 편향 보정용).
> - **탈출구**: "모두 별로" / "모르겠음" 버튼. 고르면 해당 문항은 벡터 이동 없이 불확실 축 문항을 하나 추가한다.
> - **2단계 A/B**: 바뀐 축 하나만 다른 두 시안을 나란히 보여주고, 바뀐 축 이름은 감춘다(편향 방지).
- **수용 기준**: 한 문항 4장의 카피 텍스트 diff가 0이다(자동 검사). 모바일 390px에서 카드 표시 폭이 ≥ 358px이다. 위치 로그가 저장된다. 시안 풀이 48장 이상 있어야 진단을 열 수 있다(seed 스크립트로 검증).

## UI-10 결과 화면 규격이 없다
- **심각도**: Major
- **관련 섹션**: 1장 4단계
- **허점**: 유형 이름 예시 하나뿐이다. 유형이 몇 개인지, 이름 짓는 규칙, 차트 형태, 공유 이미지 규격, "가장 닮은 실제 사이트 3곳"의 표시 방식(링크만? 썸네일?)이 없다. 2장은 실제 사이트를 결과 화면에서 링크로만 보여준다고 했는데, 링크만 있으면 화면이 텅 비고 썸네일을 쓰면 저작권 원칙과 충돌한다.
- **왜 문제인가**: MBTI식 결과는 공유(바이럴)가 핵심 성장 장치인데, 공유 카드 규격이 없으면 구현이 제각각이 된다. C2 기준 미달이다.
- **보완안**:

> ### 10.3 결과 화면
> - **유형 수**: 디자인 유형 = 프리셋(UI-08). MVP 8종. 유형 이름은 "형용사 + 양식 명사" 형식(예: 고요한 에디토리얼형)이고, 설명은 120~180자, 강점 3개, "이런 사이트에 잘 어울려요" 용도 2개로 구성한다.
> - **축 차트**: 6개 성향 축을 양극 막대(diverging bar)로 보여준다. 레이더 차트는 쓰지 않는다(읽기 어렵고 AI 대시보드 느낌이 남). 각 막대에 양 끝 라벨과 0~100 값을 표시하고, 같은 내용을 스크린리더용 표로도 제공한다.
> - **유형 미리보기**: 유형 프리셋으로 렌더한 자체 시안 2장(데스크톱 1, 모바일 1)을 보여준다.
> - **닮은 사이트 3곳**: 사이트명, 도메인, 닮은 축 2개 태그, 외부 링크(`rel="noopener nofollow"`)만 보여준다. 썸네일·스크린샷·로고는 표시하지 않는다.
> - **공유 이미지**: OG 1200×630, 스토리 1080×1920. 구성은 유형 이름, 축 막대 6개, 서비스 워드마크. 서버에서 `@vercel/og`로 생성한다.
> - **공유 URL**: `/result/[publicId]`, 비로그인으로 열람할 수 있고, 개인 입력(브랜드 정보)은 노출하지 않는다.
- **수용 기준**: OG 이미지가 1200×630 PNG로 2초 안에 생성된다. 결과 페이지에 외부 사이트 이미지 요청이 0건이다(network 검사). 축 차트에 대응하는 `<table>`이 DOM에 있다.

## UI-11 편집 화면: 슬라이더와 스냅 원칙 충돌, 편집 범위와 undo 부재
- **심각도**: Major
- **관련 섹션**: 1장 3단계("조금 더 둥글게" 슬라이더, 컬러 팔레트 직접 선택), 6장 피드백("요소 단위 수정은 token만 변경"), 8장 보정 3단계("원시값 직접 선택 없음")
- **허점**: 3단계는 "슬라이더"와 "팔레트 직접 선택"을 말하고, 8장은 "원시값 직접 선택 없음"을 말한다. 연속 슬라이더는 원시값 선택이다. 편집 화면에서 무엇을 바꿀 수 있는지(token? 섹션 순서? 카피?), undo, 미리보기 뷰포트, 조화 점수 표시 방식이 없다.
- **왜 문제인가**: 구현자가 연속 슬라이더를 만들면 조화 규칙이 무력화되고, 막으면 기획 의도(미세 조정)가 사라진다. 결정해야 할 제품 지점이다.
- **보완안**:

> ### 10.4 편집 화면 (MVP)
> **원칙: 모든 조정은 "검증된 단계 사이의 이동"이다.** 슬라이더 UI를 쓰더라도 값은 이산 단계(step index)에 스냅된다.
>
> | 조정 항목 | 컨트롤 | 단계 | 저장되는 값 |
> |---|---|---|---|
> | 모서리 | 단계 슬라이더 | radius 계열 4단계: sharp / soft / round / pill | `radius.family` |
> | 여백 밀도 | 3단 토글 | compact / regular / airy | `density` |
> | 크기 대비 | 3단 토글 | 1.2 / 1.25 / 1.333 (+디스플레이 배율) | `type.ratio` |
> | 색 | 팔레트 카드 | 현재 프리셋에서 조화 검증을 통과한 대안 팔레트 4개 | `palette.id` |
> | 서체 | 페어 카드 | 프리셋이 허용하는 페어 3~4개 | `fontPair.id` |
> | 깊이감 | 3단 토글 | 프리셋이 허용하는 depth 스타일 안에서 level 0~2 | `depth.level` |
> | 섹션 | 목록 | 순서 바꾸기(드래그 + 키보드), variant 바꾸기, 추가/삭제(용도별 필수 섹션은 삭제 불가) | layout tree |
> | 카피 | 인라인 편집 | 컴포넌트별 글자 수 제한(UI-24) | layout tree |
>
> - 미리보기: 데스크톱 1440 / 태블릿 768 / 모바일 390 토글. iframe 격리.
> - undo/redo: 최근 50단계(Cmd/Ctrl+Z, Shift+Cmd/Ctrl+Z).
> - 조화 점수: 화면 상단에 0~100 배지. 조정 결과가 점수 70 미만이면 적용은 하되 "조화 점수가 낮아졌어요 — 이유: (규칙명)"을 보여주고 "추천값으로 되돌리기" 버튼을 둔다. WCAG AA를 위반하는 조정은 적용하지 않는다(전문가 모드도 동일).

> - 이후 단계: 전문가 모드에서 hex/px 직접 입력(접근성 규칙은 유지).

> ### 10.5 서비스 접근성·반응형

# (B) 생성되는 시안의 UI 시스템

## UI-03 생성 시안의 token 스키마가 없다
- **심각도**: Blocker
- **관련 섹션**: 1장("CSS 변수 테마"), 3장 1번("token 값은 추출값/검증 프리셋에서만"), 6장, 8장
- **허점**: "token"이라는 단어가 10번 넘게 나오는데 token 이름, 단계 수, 값 범위가 하나도 없다. 2장의 추출기(getComputedStyle)가 추출한 값을 어떤 token으로 정규화하는지도 없다.
- **왜 문제인가**: token 스키마는 추출기, 프리셋, 조화 규칙, 린터, 편집기, 내보내기가 모두 공유하는 **계약(contract)**이다. 이것이 없으면 모듈마다 다른 이름과 단위를 쓰게 되고, "취향 일치도 = 같은 추출기로 벡터 거리"도 계산할 수 없다. 이 프로젝트에서 가장 먼저 확정해야 할 산출물이다.
- **보완안**:

> ### 11. 생성 시안 Design Token 스키마 (v1)
> 형식: JSON(W3C DTCG 호환 구조) → 빌드 시 CSS 변수(`--ds-*`)와 Tailwind v4 `@theme`으로 변환한다. 모든 색은 OKLCH로 저장하고 hex로도 출력한다.
>
> **11.1 색 역할 (semantic)**
>
> | token | 용도 | 규칙 |
> |---|---|---|
> | `color.bg` | 페이지 배경 | |
> | `color.surface` | 카드/섹션 대체 배경 | bg와 명도(L) 차이 0.02~0.06 |
> | `color.surface-inverse` | 반전 섹션(CTA, 푸터 등) | |
> | `color.fg` | 본문 텍스트 | bg 대비 ≥ 7:1 권장, ≥ 4.5:1 필수 |
> | `color.fg-muted` | 보조 텍스트 | bg·surface 둘 다 대비 ≥ 4.5:1 |
> | `color.fg-inverse` | 반전 섹션 텍스트 | surface-inverse 대비 ≥ 4.5:1 |
> | `color.border` | 구분선 | 장식용, 대비 요구 없음 |
> | `color.border-strong` | 입력 필드 테두리 | bg 대비 ≥ 3:1 |
> | `color.primary` | 주요 CTA 배경, 링크 | |
> | `color.on-primary` | primary 위 텍스트 | ≥ 4.5:1 |
> | `color.primary-hover` | hover | primary와 L 차이 ±0.06 |
> | `color.accent` | 강조(선택, 최대 1색) | 면적 ≤ 화면의 10% |
> | `color.on-accent` | | ≥ 4.5:1 |
> | `color.focus` | 포커스 링 | 인접 배경 대비 ≥ 3:1 |
> | `color.success/warning/danger` (+`on-`) | 폼 상태 | "2~3색" 집계에서 제외 |
> | `color.neutral.50~950` | 11단계 무채(또는 primary hue로 chroma ≤ 0.02 틴트) | 자동 생성 |
>
> **11.2 타이포그래피**
>
> | token | 값 범위 |
> |---|---|
> | `font.display` / `font.body` / `font.mono`(선택) | 폰트 화이트리스트 ID(UI-06) |
> | `type.base` | 16px 고정(한글 본문 가독성), 본문이 긴 에디토리얼 프리셋만 17~18px 허용 |

> | `type.display-boost` | {1.0, 1.25, 1.5, 2.0} — display/h1에만 곱하는 추가 배율("과감한 크기 대비"는 이 값으로 표현) |

> | `tracking` | 한글 헤드라인(≥ h3) -0.02em~-0.04em, 본문 0~-0.01em, 영문 대문자 라벨 +0.04~+0.08em |

> ```json
> {
>   "version": "1",
>   "tokens": { "presetId": "calm-editorial", "overrides": { "radius.family": "soft" } },
>   "page": {
>     "sections": [
>       { "block": "Hero", "variant": "H3", "bg": "bg",
>         "slots": { "eyebrow": "…", "title": "…", "body": "…",
>                    "primaryCta": { "label": "…", "href": "#contact" },
>                    "media": { "imageId": "img_123", "ratio": "4:5" } } }

>   }

## UI-07 조화 규칙 수치가 모호하거나 서로 충돌한다
- **심각도**: Major
- **관련 섹션**: 3장 3번, 8장 조화 규칙
- **허점과 충돌**:

| 기획서 문구 | 문제 |
|---|---|
| "모듈러 스케일 1.25" 고정 | 3장 "과감한 크기 대비", 에디토리얼/포스터형 프리셋과 충돌한다. 1.25로는 display가 body의 약 3.8배(6단계)에 그쳐서 모든 시안의 대비가 같아진다(= "같은 리듬" AI 티) |
| "2~3색" | neutral, 상태색, 이미지 색을 포함하는지 정의가 없다 |
| "색채 이론 팔레트" | 보색/유사색/삼각 등 어떤 관계를 몇 도 허용 오차로 판정할지, 어느 색 공간(HSL? OKLCH?)인지 없다. HSL hue는 지각적으로 균일하지 않다 |
| "WCAG AA" | 어떤 쌍을 검사하는지(텍스트/배경, 버튼, 이미지 위 텍스트, 포커스 링) 없다. 이미지 위 텍스트는 계산 방법이 필요하다 |
| "검증 페어링·최대 2종" | 검증 주체와 목록이 없다(UI-06) |
| "radius 한 계열" | "계열"의 정의가 없다(UI-03 11.4로 해결) |
| "장식 효과 최대 1~2" | 무엇이 장식 효과인지 목록이 없다 |
| "상충 조합 목록" | 목록 자체가 없다 |
| "한글 헤드라인 자간 -0.02em" | 크기별 차등이 없다(48px 이상은 -0.03~-0.04em이 자연스럽다). 영문 규칙도 없다 |
| "조화 점수 미달 시안 숨김" | 점수 공식과 임계값이 없다 |
| 미니멀 트렌드의 연회색 본문 | AA와 충돌하는데, 무엇을 우선하는지 명시가 없다 |

- **왜 문제인가**: 조화 규칙은 "감각 없는 사용자의 결과를 시스템이 책임진다"는 8장의 핵심 약속인데, 수치가 없으면 구현할 수 없고 검증할 수도 없다(C2 FAIL).
- **보완안**:

> ### 15. 조화 규칙 (수치 정의)
> **15.1 색**
> - 색 공간: OKLCH. "N색"은 chroma ≥ 0.04인 브랜드 색 수를 센다. neutral(chroma < 0.04), 상태색, 사진은 집계에서 제외한다. 허용: primary 1 + accent 0~1 (+ 선택적 2차 accent는 표현적 프리셋만, 면적 ≤ 5%).
> - 관계(primary↔accent hue 차): 유사 15~45°, 보색 160~200°, 분할보색 135~165°, 단색(accent 없음). 이 범위 밖이면 감점한다.
> - 채도 균형: accent chroma ≤ primary chroma × 1.3. 배경 chroma ≤ 0.03(컬러 배경 프리셋은 ≤ 0.08).
> - 대비(필수, 하드 게이트): fg/bg, fg/surface, fg-muted/bg, fg-muted/surface, on-primary/primary, fg-inverse/surface-inverse ≥ 4.5:1. 18.66px bold / 24px 이상 텍스트 ≥ 3:1. border-strong/bg, focus/인접 배경, 버튼 경계(배경과 구분이 필요할 때) ≥ 3:1.
> - 이미지 위 텍스트: 텍스트 영역 아래 이미지 픽셀을 렌더 후 샘플링해서 최악값(5퍼센타일 휘도) 기준 4.5:1을 만족해야 한다. 미달이면 오버레이(α 0.35~0.6)를 자동으로 추가한다.
> - AA와 미적 선택이 충돌하면 **AA가 이긴다**(연회색 본문, 저대비 neumorph 불가).
>
> **15.2 타이포**
> - ratio ∈ {1.2, 1.25, 1.333}, display-boost ∈ {1.0, 1.25, 1.5, 2.0}. 신뢰 강도 "강함" 용도(병원·금융·공공)는 boost ≤ 1.25.
> - display/body 크기 비: 최소 2.5배(밋밋함 방지), 최대 8배(데스크톱).
> - 자간: 32px 미만 0~-0.01em, 32~47px -0.02em, 48~71px -0.03em, 72px 이상 -0.04em(한글 기준). 영문 디스플레이 세리프는 -0.01~-0.02em.
> - 행간: 위 11.2와 같다.
> - 같은 화면에 font-weight 최대 3종.
>
> **15.3 형태·간격**
> - 모든 radius는 선택된 family 값에서만 나온다. 4/8pt spacing 스케일 밖 값은 0건이어야 한다.
>
> **15.4 장식 효과 목록 (페이지당 최대 2종, 신뢰 강도 "강함" 용도는 최대 1종)**
> grain 질감, glass, 그라디언트(2-stop, 같은 hue 계열만), 큰 장식 타이포/아웃라인 텍스트, 패턴 배경, hard shadow, 이미지 듀오톤, 마키(흐르는 텍스트), 커스텀 커서, 스크롤 패럴랙스.
>
> **15.5 상충 조합 (금지)**
>
> | 조합 | 이유 |
> |---|---|
> | glass + flat 단색 배경(뒤에 아무것도 없음) | 의미 없는 글래스 |
> | hard shadow + soft shadow 혼용 | 깊이 문법 충돌 |
> | sharp radius + pill 버튼 | 형태 계열 충돌(pill family 제외) |
> | 고대비 세리프 디스플레이(Cormorant 등) + 기하 고딕 본문 + round radius | 성격 3방향 충돌 |
> | grain + glass + 그라디언트 동시 | 장식 과잉 |
> | 다크 bg + 순수 #000 그림자 | 그림자가 보이지 않음 |
> | 보라(hue 270~310)→파랑(hue 220~260) 그라디언트 | AI 티(린터와 공유) |
> | 표현적 모션 + 신뢰 강도 "강함" 용도 | 용도 부적합 |
>
> **15.6 조화 점수 (0~100)**
> - 하드 게이트(하나라도 실패하면 0점, 노출 금지): 대비 위반, 화이트리스트 밖 폰트, 상충 조합, 용도 필수 섹션 누락.
> - 감점 항목: 색 관계 범위 이탈 −15, 장식 효과 초과 1개당 −10, weight 4종 이상 −5, 리듬 규칙 위반 1건당 −5, display/body 비 범위 이탈 −10, 섹션 수 범위 이탈 −5.
> - 노출 임계값: ≥ 70. 편집 중에는 70 미만이면 경고(UI-11).
- **수용 기준**: `harmony.ts`가 위 규칙을 순수 함수로 구현하고, 각 규칙에 통과/실패 단위 테스트(최소 규칙당 2케이스)가 있다. 골든 세트 30건의 조화 점수가 사람 라벨(좋음/나쁨)과 일치율 ≥ 80%다(초기 검증).

## UI-12 이미지 소스, 라이선스, 플레이스홀더 정책이 없다
- **심각도**: Major
- **관련 섹션**: 3장 6번("실사진"), 7번("진짜 같은 콘텐츠")
- **허점**: "실사진"을 쓰라고 하지만 어디서 가져오는지, 라이선스, 내보내기 시 처리(핫링크/동봉), 사용자 업로드, 생성 이미지 사용 여부가 없다.
- **왜 문제인가**: 이미지는 시안 인상의 50% 이상을 결정하고, 라이선스 위반은 법무 탈락 사유다. 스톡 API는 약관상 표시(attribution)·핫링크 의무가 있을 수 있어서 내보내기 설계에 영향을 준다.
- **보완안**:

> ### 17. 이미지 정책
> **MVP 소스 우선순위**
> 1. **사용자 업로드**(로고, 대표 사진): 업로드 시 "권리를 보유한 이미지만 업로드" 동의를 받는다. 최대 10장, 장당 10MB, jpg/png/webp. 서버에서 리사이즈한다.
> 2. **자체 큐레이션 이미지 팩**: Unsplash/Pexels 라이선스(상업 이용 가능) 이미지 중 **용도 6종 × 톤 4종 × 장면 10장 ≈ 240장**을 사람이 고르고 자체 스토리지에 저장한다. 메타데이터는 `{id, source, sourceUrl, author, license, licenseUrl, downloadedAt, tags[], dominantColorOKLCH, focalPoint, hasPeople, hasLogo}`. 인식 가능한 얼굴, 상표·로고, 실제 브랜드 매장이 보이는 사진은 제외한다(`hasPeople`이 true면 뒷모습/원경만). 각 소스의 API·라이선스 약관(표시 의무, 경쟁 서비스 금지 조항, 핫링크 요구)은 출시 전 원문으로 재확인한다.
> 3. **플레이스홀더**: 맞는 이미지가 없으면 프리셋 색으로 만든 단색/미세 패턴 면 + 비율 + 용도 라벨("매장 내부 사진 4:3")을 보여준다. 회색 X 박스, 무작위 추상 블롭, 그라디언트는 금지한다.
>
> - 이미지 매칭: 섹션 슬롯의 `{usage, tone, scene, ratio}` 태그로 검색하고 focalPoint로 크롭한다. LLM은 `imageId`만 고른다.
> - 톤 처리: 프리셋의 `image.treatment`(grayscale/duotone/warm-tint)를 CSS filter 또는 사전 처리로 적용해서 한 시안 안의 이미지 톤을 통일한다.
> - 생성 이미지(AI): MVP에서는 쓰지 않는다. "AI 티"의 주요 원인이고, 모델별 약관·권리 귀속 검토가 필요하다. 이후 단계에서 약관 검토 후 "추상 텍스처/배경" 용도에 한해 검토한다.

## UI-18 사용자 브랜드 자산(로고, 브랜드 컬러) 처리 규칙이 없다

- **관련 섹션**: 3장 7번(브랜드 정보 입력), 8장("원시값 직접 선택 없음")
- **허점**: 실사용자(소상공인, 스타트업)의 상당수는 이미 브랜드 컬러와 로고가 있다. 브랜드 컬러가 원시값 입력이라서 8장 원칙과 충돌하고, 처리 규칙이 없다.

> ### 23. 브랜드 자산 입력
> - 브랜드 컬러(선택, 최대 2개, hex)는 **"고정 hue 제약"**으로 취급한다. hue는 ±5° 안에서 유지하고, 명도·채도는 대비 게이트를 통과하도록 시스템이 조정한다. 조정 폭이 ΔE(OKLab) > 0.05면 "접근성을 위해 버튼 색을 조금 어둡게 조정했어요 (원본 #xxxxxx)"라고 알려준다.
> - 브랜드 컬러가 선택된 프리셋의 색 성격과 충돌하면(예: 네온 핑크 + lux-minimal) accent로 강등하고 면적을 ≤ 10%로 제한한다.
> - 로고: SVG/PNG 업로드. 로고에서 dominant color를 추출해 브랜드 컬러 후보로 제안한다. 로고가 없으면 브랜드명을 프리셋 display 서체로 쓴 워드마크로 대체한다(가짜 심볼 생성 금지).
- **수용 기준**: 임의 브랜드 hex 20개(채도·명도 극단값 포함) 입력 테스트에서 생성 결과가 100% 대비 게이트를 통과하고 hue 오차가 ≤ 5°다.

## UI-20 시그니처 디테일 후보 목록 (Minor)
- 3장 5번 "시그니처 디테일 하나(프리셋별 후보)"의 후보가 없다. UI-08 프리셋 표의 "시그니처 후보" 열을 정식 목록(`signatures.json`: `{id, name, appliesTo(blocks), tokensUsed, conflictsWith[]}`)으로 만들고, MVP는 12종(얇은 괘선, 섹션 넘버링, 거대 숫자, 그리드 라인 노출, hard shadow, 마키, grain, 모노 라벨, 와이드 자간 대문자 라벨, 사진 듀오톤, 아웃라인 디스플레이 텍스트, 비대칭 이미지 오프셋)으로 한다.
- 수용 기준: 시안마다 시그니처가 정확히 1개 적용되고(메타데이터에 기록), 장식 효과 한도(UI-07 15.4)에 포함해서 센다.

## UI-21 token 포맷과 Figma 내보내기 대비 (Minor, 이후)
- token JSON을 처음부터 W3C Design Tokens(DTCG) 형식(`$value`, `$type`)으로 저장해 두면, 2차 Figma Variables 내보내기를 Tokens Studio 등 표준 도구 경로로 할 수 있다. MVP 비용은 거의 없다.
- 수용 기준: `tokens.json`이 DTCG `$type`(color, dimension, fontFamily, shadow, duration, cubicBezier)을 사용한다.

## UI-22 질감 효과 성능 예산 (Minor)
- grain은 SVG `feTurbulence`를 전체 화면에 실시간 적용하면 모바일 스크롤 성능이 떨어지고, backdrop-filter도 저사양 기기에서 무겁다. grain은 256px 이하 정적 PNG/WebP 타일(≤ 20KB)로 만들고, glass는 화면당 최대 2개 요소로 제한한다.
- 수용 기준: 효과를 적용한 시안의 모바일 Lighthouse Performance 점수가 효과 없는 버전 대비 −5점 이내다.

## UI-24 카피 길이 제약 (Minor)
- 한글은 영문보다 짧지만 줄바꿈 단위가 달라서 넘침·고아 단어가 생긴다. 컴포넌트 슬롯마다 글자 수 제한(예: Hero title 한글 8~24자, 버튼 2~10자, 기능 설명 40~90자)과 `word-break: keep-all`, `text-wrap: balance`(헤드라인) / `pretty`(본문) 적용을 명세한다.
- 수용 기준: 슬롯 JSON Schema에 `minLength/maxLength`가 있고, 렌더 시 헤드라인 마지막 줄이 1~2글자만 남는 경우(고아)가 골든 세트에서 0건이다.

## 루브릭 판정

### C1 완결성 — **FAIL**
UI/디자인 시스템 영역에 Blocker 6건, Major 13건이 남아 있다. 서비스 자체 UI 방향(UI-01)과 화면·상태 정의(UI-02)가 전무하고, 시스템의 핵심 계약인 token 스키마(UI-03), 컴포넌트(UI-04), 섹션 블록(UI-05), 폰트·라이선스(UI-06)가 정의되지 않았다. 원칙은 있지만 원칙을 실행할 목록과 값이 없다.

### C2 AI 구현 가능성 — **FAIL**
Claude Code가 이 문서만으로 구현하면 다음을 스스로 결정해야 한다: token 이름과 단계, 컴포넌트·섹션 목록, 레이아웃 트리 스키마, 폰트 선택, 아이콘 세트, 브레이크포인트, 다크 모드 범위, 슬라이더 vs 스냅 충돌 해소, 조화 점수 공식과 임계값, 내보내기 구조. 결정 공백은 에이전트의 기본값(shadcn/Inter/Lucide)으로 채워지고, 이것이 기획서가 금지한 AI 티와 정확히 일치한다. 측정 가능한 품질 기준치(대비 쌍, 넘침 검사 뷰포트, Lighthouse/axe 기준, 린터 판정 조건)도 없다.

### C3 대기업 통과 — **FAIL**
대형 IT 기업 디자인 리뷰 기준으로 보면, 디자인 시스템 명세(token/컴포넌트/패턴), 화면 IA와 예외 상태, 접근성(KWCAG/WCAG AA) 준수 계획, 웹폰트·이미지·아이콘 라이선스 검토가 모두 빠져 있다. 특히 사용자가 상업 사이트에 그대로 쓰는 코드를 내보내는 서비스인데 폰트·이미지 라이선스 정책이 없다. 이것은 법무 게이트 단독 탈락 사유다.

**PASS로 가는 최소 조건**: UI-01~06(Blocker) 보완안을 기획서 10~14장으로 반영하고, UI-07·08·11·12·16·17(조화 수치, 프리셋 시드, 편집 스냅, 이미지 정책, 내보내기 기준, 린터 판정 조건)을 반영하면 UI 영역의 C1/C2는 PASS 가능한 수준이 된다.
