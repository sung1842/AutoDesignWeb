# R1 리뷰 — UX 디자인 / UX 리서치 관점

- 대상: `spec_v1.md` (디자인 취향 진단 기반 웹 시안 자동 생성 서비스, v1)
- 기준: `rubric.md` (C1 완결성 / C2 AI 구현 가능성 / C3 대기업 통과)
- 리뷰어 관점: 진단(설문) 플로우 UX, 비교 문항의 공정성, 정보 입력, 결과 화면, 생성 대기, 편집, 예외 상태, 접근성, 검증 계획, IA
- 맥락: 1인 개발 + Claude Code 자율 구현. 각 보완안에 **[MVP]** / **[이후]** 표시.

---

## 0. 총평

v1은 **"엔진(벡터·트렌드·생성 파이프라인)" 문서이고 "사용자가 겪는 제품" 문서가 아니다.** 사용자가 보는 화면이 몇 개인지, 각 화면에 무엇이 있는지, 몇 분 걸리는지, 막히면 어떻게 되는지가 하나도 정의돼 있지 않다. 그래서 Claude Code가 구현하면 화면 구성, 문항 수, 예외 처리, 편집 UI를 모두 스스로 정하게 되고(C2 위반), 대기업 디자인 리뷰에서는 "화면 목록과 플로우가 어디 있나요?"라는 첫 질문에서 막힌다(C3 위반).

특히 위험한 부분:
1. 진단 문항이 **최대 25문항 + 선택 단계 + 추가 양자택일 질문**인데 상한과 소요 시간 목표가 없다. 시각 비교 문항 25개면 6~10분이 걸리고 이탈이 크다.
2. 4장 비교 문항을 **모바일에서 어떻게 보여줄지** 정해지지 않았다. 웹 디자인 시안 4장을 390px 화면에서 비교하는 건 사실상 불가능하다.
3. **8절(원시값 직접 선택 없음, 스냅)과 1장 3단계(슬라이더, 직접 선택)가 서로 충돌한다.** 편집 UI의 기본 원칙이 정해지지 않았다.
4. 시안 생성(후보 6개 → 렌더 → 채점 → 수정 루프)은 **수 분이 걸릴 수 있는데** 대기 UX와 시간 목표가 없다.

## 1. 지적 사항

### UX-01 · Blocker · 화면 목록(IA)·플로우·와이어프레임 수준 명세 없음
- **관련 섹션**: 1장 전체, 6장, 8장 "보여주기"
- **허점**: 단계(1~5단계)만 있고 화면 단위 정의가 없다. 랜딩, 온보딩, 문항, 결과, 정보 입력, 생성 대기, 시안 선택, 편집, 내보내기, 오류 화면이 각각 존재하는지, 각 화면의 구성 요소·주요 행동·진입/이탈 경로가 없다.
- **왜 문제인가**: C2의 핵심 위반이다. 에이전트가 화면 구조를 마음대로 정하면 결과물이 "AI가 만든 흔한 SaaS 화면"이 되기 쉬워, 이 서비스가 가장 피하려는 'AI 느낌'이 서비스 UI 자체에서 나온다. C3에서도 IA와 와이어프레임이 없는 기획서는 디자인 리뷰 대상이 아니다.
- **보완안 [MVP]** — 기획서에 아래 표를 "화면 명세" 절로 추가:

| ID | 화면 | 경로 | 핵심 구성 요소 | 주요 행동(Primary CTA) | 진입 → 이탈 |
|---|---|---|---|---|---|
| S01 | 랜딩 | `/` | 가치 한 줄, 예시 결과 3개, "약 5분" 안내, 로그인 불필요 안내 | 진단 시작 | 외부 → S02 |
| S02 | 진단 문항(4지선다) | `/quiz/[sessionId]?q=n` | 진행률 바, 문항 제목, 시안 카드 4장, 보조 선택지(UX-04), 뒤로 | 카드 선택 → 자동 다음 | S01 → S02 반복 → S03 |
| S03 | 진단 문항(A/B) | 같은 경로 | 진행률, 시안 2장, "차이를 모르겠어요" | 하나 선택 | S02 → S03 반복 → S04 |
| S04 | 결과 | `/result/[resultId]` | 유형 이름·설명, 축 점수 차트, 신뢰도 표시, 닮은 사이트 3곳(링크), 결과 피드백(5점), 공유, 다시 하기 | 이 취향으로 시안 만들기 | S03 → S05 |
| S05 | 사이트 정보 입력 | `/brief/[resultId]` | 용도 선택, 브랜드명, 한 줄 소개, 선택 항목(UX-06) | 시안 생성 | S04 → S06 |
| S06 | 생성 대기 | `/generate/[jobId]` | 단계별 진행 상황, 예상 남은 시간, 완성된 시안부터 표시 | (대기) / 취소 | S05 → S07 |
| S07 | 시안 비교·선택 | `/drafts/[jobId]` | 시안 3장(취향 그대로/용도 최적/균형), 각 시안 라벨+보정 이유, 데스크톱/모바일 미리보기 토글 | 이 시안 다듬기 | S06 → S08 |
| S08 | 편집 | `/edit/[draftId]` | 실시간 미리보기, 편집 패널(UX-09), 되돌리기/다시하기, 변경 이력 | 완료·내보내기 | S07 → S09 |
| S09 | 내보내기 | 모달 | HTML 다운로드, React 코드 복사, 공유 링크 | 다운로드 | S08 → 종료 |
| S10 | 오류/빈 상태 | 공통 컴포넌트 | UX-10 표 참조 | 다시 시도 | 모든 화면 |

  - 각 화면에 대해 **텍스트 와이어프레임**(영역 배치 순서, 데스크톱 1440 / 모바일 390 각각)을 부록으로 첨부. MVP에서는 Figma 없이 마크다운 박스 다이어그램으로 충분.
  - 서비스 UI 자체의 디자인 원칙 1문단 추가: "서비스 UI는 중립 회색 계열(채도 ≤10%), 단일 서체, 장식 없음. 시안이 주인공이고 UI는 판단에 영향을 주지 않아야 한다."
- **수용 기준**: 기획서에 S01~S10 각각 경로·구성 요소·CTA·진입/이탈이 정의되어 있고, 에이전트가 화면을 추가·삭제할 필요가 없다. 모든 화면에 데스크톱/모바일 배치가 명시되어 있다.

### UX-02 · Blocker · 총 문항 수·소요 시간 상한 없음, 피로도·이탈 대책 없음
- **관련 섹션**: 1장 1~3단계, 8장 "보조 강도"(엇갈리면 추가 질문)
- **허점**: 1단계 8~10 + 2단계 10~15 + 3단계(선택) + 일관성 낮을 때 추가 질문 = **최대 25문항 이상**, 상한 없음. 소요 시간 목표, 진행률 표시 방식, 조기 종료 조건이 없다.
- **왜 문제인가**: 시각 비교 문항은 텍스트 문항보다 오래 걸린다(4장 비교 약 10~20초, A/B 약 6~10초). 25문항이면 중앙값 6~8분, 길게는 10분 이상이다. 진단형 콘텐츠는 3~5분을 넘기면 완료율이 크게 떨어진다. "가변 문항 수 + 진행률 바"는 진행률이 뒤로 가거나 멈춰 보이는 문제도 생긴다.
- **보완안 [MVP]**:
  - 문항 구성 확정: **1단계 8문항 고정 + 2단계 최대 8문항(적응형) = 최대 16문항.** 일관성 낮을 때의 추가 양자택일은 2단계 8문항 안에서 소화하고, 별도로 늘리지 않는다.
  - 2단계 조기 종료: 모든 성향 축의 불확실도가 기준치 아래로 내려가면 8문항 전이라도 종료(기준치는 알고리즘 절에서 정의, UX는 "최소 4문항"만 보장).
  - 3단계(요소 단위 선택)는 **진단에서 빼고 S08 편집 화면으로 옮긴다**(UX-09). 진단 길이를 줄이고, 결과 후 맥락에서 고르는 게 더 정확하다.
  - 소요 시간 목표: **중앙값 ≤ 4분, P90 ≤ 7분.** 랜딩과 첫 문항에 "약 4분 · 16문항 이내" 표시.
  - 진행률: 1단계는 "n / 8", 2단계 진입 시 "거의 다 왔어요 · 최대 8문항" 문구 + 바는 **절대 뒤로 가지 않게** (2단계는 남은 최대 문항 기준으로 계산, 조기 종료 시 100%로 점프).
  - 단계 전환 화면 1장(1단계 후): "큰 취향을 찾았어요. 이제 세부를 좁혀볼게요" + 잠정 성향 키워드 2개 미리보기 → 보상 제공으로 중간 이탈 감소.
- **수용 기준**: 진단 문항 수가 어떤 경우에도 16을 넘지 않는다. 진행률 값이 단조 증가한다. 내부 테스트(5명 이상)에서 진단 소요 시간 중앙값 ≤ 4분. 퍼널 지표(UX-12)로 "1단계 시작 → 결과 도달" ≥ 70%.

### UX-03 · Blocker · 4지선다 비교의 공정성과 모바일 비교 방식 미정
- **관련 섹션**: 1장 1단계, 2장 "주의: 저작권·약관"(재현한 오리지널 시안)
- **허점**: 4장 비교 시안의 콘텐츠(텍스트·이미지)가 같은지, 크기·잘림 범위·배치 위치가 같은지, 모바일에서 4장을 어떻게 보여주는지가 없다.
- **왜 문제인가**: 콘텐츠가 다르면 사용자는 **스타일이 아니라 사진·문구·주제를 고른다.** 노출 위치가 고정되면 왼쪽 위 선택이 많아지는 위치 편향이 생긴다. 데스크톱 캡처를 모바일에서 4분할로 축소하면 장당 약 170px 폭이라 서체·여백·radius 같은 핵심 축이 보이지 않는다. 즉 측정 자체가 틀어져 이후 파이프라인 전체가 잘못된 벡터를 받는다.
- **보완안 [MVP]**:
  - **콘텐츠 통제**: 설문용 시안은 모두 **동일한 더미 브리프 1종**("가상 브랜드 '온결' — 로컬 베이커리"처럼 중립적인 주제)으로 렌더. 헤드라인·본문·버튼 문구·이미지 슬롯이 같고, 이미지는 같은 사진 세트(무채색 보정 금지 — 원본 동일)를 쓴다. 바뀌는 건 token과 레이아웃 프리셋뿐.
  - **노출 범위 통제**: 각 카드는 같은 영역만 보여준다 — 내비 + 히어로 + 카드 1행(1440×900 기준 첫 화면). 캡처가 아니라 **실제 렌더(iframe 또는 컴포넌트 직접 렌더)를 축소**해 텍스트 선명도를 유지.
  - **위치 무작위화**: 카드 순서는 문항마다 무작위, 순서와 선택을 로그에 남긴다. 카드에 스타일 이름·라벨을 표시하지 않는다(A·B·C·D 또는 1·2·3·4만).
  - **기기별 표시 규칙**:

| 기기 | 1단계(4지선다) | 2단계(A/B) |
|---|---|---|
| 데스크톱(≥1024px) | 2×2 그리드, 카드당 최소 폭 560px, 호버 시 확대 없음(공정성) | 좌우 나란히, 같은 크기 |
| 태블릿(768~1023) | 2×2 그리드, 탭하면 전체화면 미리보기 | 좌우 나란히 |
| 모바일(<768) | 2×2 썸네일 개요 + **탭하면 전체화면 페이저**(좌우 스와이프로 4장 순회, 현재 위치 "2/4" 표시, 페이저 안에서 바로 선택). 시안은 **모바일 뷰포트(390px)로 렌더**한 버전을 보여준다 | 위아래 분할 대신 **토글 비교**(A/B 버튼으로 같은 위치에서 전환, 스크롤 위치 유지) |

  - 모든 시안은 같은 기기 안에서 같은 뷰포트로 렌더된다(데스크톱 사용자에게 모바일 렌더를 섞지 않음).
- **수용 기준**: 한 문항의 4장이 콘텐츠 diff 0(텍스트·이미지 동일), 차이는 token/레이아웃만. 카드 순서가 무작위이고 로그에 저장. 모바일 390px에서 본문 텍스트가 실제 크기로 읽힌다(전체화면 페이저). 위치별 선택 비율이 표본 200회 이상에서 20~30% 범위(편향 점검).

### UX-04 · Major · 건너뛰기 / 뒤로가기 / "모르겠음·둘 다 별로" 선택지 없음
- **관련 섹션**: 1장 1~2단계, 8장 "선택 일관성 측정"
- **허점**: 사용자가 4장이 다 싫거나, A/B 차이를 못 느끼거나, 실수로 눌렀을 때의 경로가 없다.
- **왜 문제인가**: 강제 선택만 있으면 잡음이 섞인 응답이 벡터에 그대로 들어간다. 특히 A/B에서 미세한 차이를 못 느낀 사용자가 아무거나 고르면 8장의 "일관성 낮음" 판정이 잘못 내려져 추가 질문과 프리셋 비중이 올라가는 악순환이 생긴다.
- **보완안 [MVP]**:

| 선택지 | 노출 위치 | 벡터 처리 | 비고 |
|---|---|---|---|
| 뒤로 | 모든 문항(첫 문항 제외) 좌상단 | 이전 응답 취소 후 재계산(응답은 덮어쓰기, 이력은 로그 보존) | 2단계 적응형 문항은 뒤로 가면 이후 문항을 다시 생성 |
| 다 별로예요 | 1단계 카드 아래 텍스트 버튼 | 4장 평균 방향에서 약하게 멀어짐(가중치는 일반 선택의 0.3배) | 같은 세션에서 3회 이상이면 "취향이 뚜렷하시네요. 다른 스타일을 더 보여드릴게요" 후 풀 다양성 확대 |
| 차이를 모르겠어요 | 2단계 카드 아래 텍스트 버튼 | 벡터 변화 없음, 해당 축 "민감도 낮음"으로 표시 → 이후 그 축 문항 건너뜀, 생성 시 용도 기본값 사용 | 일관성 계산에서 제외 |
| 건너뛰기 | 제공하지 않음 | — | "다 별로예요/모르겠어요"로 대체(무응답보다 정보가 많음) |

  - 선택 직후 자동으로 다음 문항으로 넘어가되 **300ms 선택 확인 애니메이션**을 두어 오탭 인지 가능, 뒤로 버튼으로 복구.
  - 응답 시간 로그: 1초 미만 선택이 연속 3회면 "천천히 보셔도 돼요" 토스트 1회(신뢰도 가중치 낮춤).
- **수용 기준**: 모든 문항에서 뒤로 가기가 동작하고 결과가 재계산된다. "모르겠어요" 응답은 벡터를 바꾸지 않는다. 문항 응답 레코드에 `answer_type ∈ {pick, none_liked, cannot_tell}`과 `response_ms`가 저장된다.

### UX-05 · Major · 중간 저장·세션 복구·계정 정책 없음
- **관련 섹션**: 1장, 6장(피드백 저장), 기술 스택(Supabase)
- **허점**: 진단 중 이탈 후 복귀, 결과·시안 재방문, 로그인 필요 시점이 정의되지 않았다.
- **왜 문제인가**: "로그인 언제 받나"는 퍼널 전체를 좌우하는 제품 결정이며 에이전트가 임의로 정하면 안 된다. 진단 전에 로그인을 요구하면 시작률이 크게 떨어지고, 아예 저장이 없으면 생성 대기(수십 초~수 분) 중 탭을 닫았을 때 결과가 날아간다.
- **보완안 [MVP]**:
  - 진단~결과~시안 생성까지 **로그인 없이 익명 세션**. 첫 문항 응답 시 서버에 `session` 생성, `sessionId`를 URL과 localStorage에 저장.
  - 응답마다 즉시 서버 저장(자동 저장). 재방문 시 "이어서 할까요? (n/16 완료)" 배너 → 이어하기 / 처음부터.
  - 익명 세션 보관 기간 **30일**. 결과(`/result/[id]`)와 시안(`/drafts/[id]`)은 추측 불가능한 ID의 공유 가능 URL.
  - 로그인(이메일 매직링크 또는 소셜 1종)은 **편집 결과 저장·내보내기 시점에만** 요구. 로그인하면 익명 세션을 계정에 귀속.
  - [이후] 마이페이지(진단 이력, 시안 목록).
- **수용 기준**: 진단 중 탭을 닫고 같은 브라우저로 돌아오면 마지막 응답 다음 문항부터 재개된다. 로그인 없이 결과·시안 3개를 볼 수 있다. 생성 중 탭을 닫아도 `/generate/[jobId]` 재접속 시 진행 상태가 이어진다.

### UX-06 · Blocker · 사이트 용도·브랜드 정보 입력 단계의 위치와 항목 미정
- **관련 섹션**: 1장 5단계, 3장 7번(진짜 같은 콘텐츠), 8장(용도별 허용 범위)
- **허점**: 3장·8장 모두 용도와 브랜드 정보를 핵심 입력으로 쓰는데, 언제·어떤 항목을·어떤 형식으로 받는지가 없다. 사용자가 입력한 브랜드 컬러가 취향 벡터와 충돌할 때의 처리도 없다.
- **왜 문제인가**: 생성 파이프라인의 입력 스키마가 비어 있는 것과 같다(C2 Blocker). 위치도 중요하다. 진단 전에 받으면 용도가 취향 응답을 오염시키고(병원을 생각하며 고르기), 진단 후 결과 전에 받으면 보상(결과)이 늦어져 이탈이 늘어난다.
- **보완안 [MVP]**:
  - **위치**: 결과 화면(S04) **다음**, "이 취향으로 시안 만들기"를 누른 뒤 S05에서 받는다. 진단은 용도와 무관한 "순수 취향"으로 측정한다(결과 화면 공유 가능성과도 맞음).
  - **항목**:

| 필드 | 필수 | 형식 | 제약 | 사용처 |
|---|---|---|---|---|
| `purpose` 용도 | 필수 | 단일 선택 칩 | 병원·클리닉 / 금융·공공 / 쇼핑몰 / 레스토랑·카페 / SaaS·IT 서비스 / 포트폴리오 / 기타(자유 입력 20자) | 8장 클리핑 강도, 섹션 템플릿 |
| `brandName` 브랜드명 | 필수 | 텍스트 | 1~30자 | 로고 자리, 카피 |
| `oneLiner` 한 줄 소개 | 필수 | 텍스트 | 10~80자, placeholder 예시는 용도별로 바뀜 | 히어로 카피 |
| `primaryAction` 방문자가 했으면 하는 행동 | 필수 | 단일 선택 | 예약 / 구매 / 문의 / 가입 / 작품 보기 / 위치 확인 | CTA 문구, 섹션 순서 |
| `audience` 주요 고객 | 선택 | 텍스트 | ≤40자 | 카피 톤 |
| `keyPoints` 강점 | 선택 | 텍스트 3개 | 각 ≤40자 | 기능/소개 섹션 카피(없으면 용도별 예시 카피 + "예시 문구" 표시) |
| `brandColor` 브랜드 컬러 | 선택 | 컬러 피커 + HEX | — | 아래 충돌 규칙 |
| `logo` / 사진 업로드 | [이후] | 이미지 | — | — |

  - 입력 시간 목표 **≤ 60초**(필수 4개만 채우면 진행 가능). "건너뛰고 예시 콘텐츠로 보기" 링크 제공(예시 브리프로 생성, 시안에 "예시 콘텐츠" 배지).
  - **브랜드 컬러 충돌 규칙**: 입력 컬러는 고정 포인트 컬러로 쓰고, 나머지 팔레트는 취향 벡터에서 조화 규칙(8장)으로 맞춘다. 입력 컬러가 취향 벡터의 따뜻함/채도 축과 크게 어긋나면(축 점수 차 ≥ 0.5) 시안 카드에 "브랜드 컬러를 우선 반영했어요" 안내 표시.
- **수용 기준**: 필수 4개 미입력 시 생성 버튼 비활성 + 필드별 오류 문구. 입력 데이터가 `brief` 테이블에 위 스키마로 저장된다. 생성된 시안의 히어로·CTA·내비·푸터에 `brandName`·`oneLiner`·`primaryAction`이 반영된다(로렘 입숨 0건).

### UX-07 · Major · 결과 화면의 이해도·신뢰 설계 부족
- **관련 섹션**: 1장 4단계, 8장 "보여주기"
- **허점**: 유형이 몇 개인지, 이름 체계, 차트에 표시할 축(성향 축 6개와 디자인 축 8개가 섞여 있음), 결과의 신뢰도 표시, 결과에 동의하지 않을 때의 경로가 없다.
- **왜 문제인가**: MBTI식 결과는 "맞다"는 느낌이 공유와 다음 단계(시안 생성) 전환을 결정한다. 축 정의가 모호하면 차트가 이해되지 않고, 유형 수가 정해지지 않으면 에이전트가 유형 이름·설명을 즉석에서 만들어 품질이 들쭉날쭉해진다. 또 사용자는 "이 결과로 만든 시안"을 신뢰해야 하는데, 결과가 틀렸다고 느낄 때 고칠 방법이 없으면 바로 이탈한다.
- **보완안 [MVP]**:
  - 유형 수: **MVP 8개 고정**(8장의 "검수된 프리셋"과 1:1 대응). 각 유형에 이름(형용사 + 명사, 예: "고요한 에디토리얼형"), 설명 2문장, 키워드 3개, 대표 시안 이미지 1장, 잘 어울리는 용도 2개를 **기획서 부록에 사람이 작성한 고정 텍스트**로 둔다(LLM 생성 금지).
  - 차트: **성향 축 6개만** 막대형 양극 차트로 표시(레이더 차트는 축 순서에 따라 모양이 바뀌어 오해 소지). 각 축 양 끝에 쉬운 말 라벨(예: "덜어냄 ↔ 표현함"). 디자인 축 8개는 "세부 보기" 접힘 영역.
  - 신뢰도 표시: 축별 불확실도가 높으면 해당 막대를 점선으로 표시 + "이 축은 아직 확실하지 않아요". 전체 일관성 낮음이면 상단에 "두 가지 취향이 섞여 있어요: A형 62% · B형 38%" 혼합 표시.
  - "가장 닮은 실제 사이트 3곳": 사이트명 + 외부 링크 + **자체 제작 설명 1줄**(스크린샷 미노출, 2장 저작권 원칙과 일치).
  - 결과 피드백: "이 결과가 내 취향과 얼마나 맞나요?" 5점 척도(지표 UX-12). 2점 이하이면 "다른 유형 보기"(인접 유형 2개 카드)로 사용자가 직접 닻 유형을 바꿀 수 있게 함.
  - 공유: 결과 OG 이미지(유형 이름 + 대표 시안) [MVP], 공유용 세로 카드 이미지 [이후].
- **수용 기준**: 결과 화면이 8개 유형 중 하나(또는 2개 혼합)를 표시하고 텍스트는 부록 고정값과 일치. 사용성 테스트에서 "차트가 무엇을 뜻하는지 설명해 주세요" 과제 정답률 ≥ 80%. 결과 공감 점수 평균 ≥ 3.8/5(MVP 목표).

### UX-08 · Major · 시안 생성 대기 시간 목표와 대기 UX 없음
- **관련 섹션**: 6장 파이프라인(후보 6개 → 렌더·채점 → 수정 루프 → 상위 3~4개)
- **허점**: 후보 6개 생성 + Playwright 렌더 + 비전 채점 + 수정 루프는 직렬로 돌면 수 분이 걸린다. 시간 목표, 진행 표시, 부분 결과 노출, 시간 초과 처리가 없다.
- **왜 문제인가**: 30초를 넘는 무응답 로딩은 이탈을 크게 늘린다. 시간 목표가 없으면 기술 설계(병렬화, 후보 수, 수정 루프 횟수)도 정할 수 없다 — UX 요구가 아키텍처 제약이 되어야 하는 지점.
- **보완안 [MVP]**:
  - 시간 목표: **첫 시안 표시 P50 ≤ 30초, 3개 모두 표시 P50 ≤ 60초 / P95 ≤ 120초.** 이를 맞추기 위해 MVP 수정 루프는 **최대 1회**, 후보 수는 6 → 4로 조정 가능(기술 리뷰와 합의).
  - 백그라운드 선행: S05에서 용도를 고르는 순간 프리셋·token 컴파일을 미리 시작.
  - 진행 표시(S06): 실제 파이프라인 단계와 1:1로 대응하는 단계형 표시 — ① 디자인 명세 만들기 ② 시안 그리기(n/4) ③ 품질 검사 ④ 다듬기. 거짓 진행률 바 금지. 단계별 실제 이벤트를 SSE로 전달.
  - 부분 결과: 검사를 통과한 시안부터 카드로 즉시 노출(나머지는 스켈레톤).
  - 대기 중 콘텐츠: 사용자 유형 설명, 이 시안에 적용 중인 규칙 2~3개("한글 헤드라인 자간 -0.02em 적용 중")를 표시해 "만들고 있다"는 신뢰 형성.
  - 시간 초과: 120초 시 "조금 더 걸리고 있어요" + 지금까지 완성된 시안 보기 / 계속 기다리기. 180초에 강제 종료하고 통과 시안이 1개 이상이면 그것만 노출, 0개면 UX-10 실패 상태.
  - 탭 이탈 후 복귀 시 진행 상태 유지(UX-05).
- **수용 기준**: 생성 로그에 단계별 소요 시간이 기록되고, 내부 테스트 20회에서 위 P50/P95 목표 충족. 진행 표시 단계가 실제 서버 이벤트와 일치. 180초 초과 작업이 0건(강제 종료 동작).

### UX-09 · Major · 수정·편집 인터랙션 미정 + 8장 원칙과 3단계 슬라이더 충돌
- **관련 섹션**: 1장 3·5단계("다듬어 완성"), 6장 "요소 단위 수정은 token만 변경", 8장 "원시값 직접 선택 없음 / 스냅 / 전문가 모드"
- **허점**: "하나 고르면 다듬어 완성"이 편집 기능의 전부다. 자연어 요청인지, 슬라이더인지, 프리셋 선택인지, 텍스트 직접 수정이 되는지, 되돌리기가 있는지가 없다. 1장 3단계의 "조금 더 둥글게" 연속 슬라이더와 8장 "원시값 직접 선택 없음, 검증 조합에 스냅"이 서로 충돌한다.
- **왜 문제인가**: 편집은 "AI 느낌 제거"를 사용자가 마무리하는 단계이고, 재방문·내보내기 전환을 좌우한다. 방식이 정해지지 않으면 에이전트는 가장 쉬운 "자연어 입력창 하나"를 만들 가능성이 높은데, 이는 감각이 부족한 사용자(8장 타깃)에게 가장 어렵고 결과 예측이 안 되는 방식이다.
- **보완안 [MVP]** — 원칙: **"사용자는 방향을 고르고, 값은 시스템이 스냅한다."**

| 편집 대상 | MVP 컨트롤 | 단계 | 동작 |
|---|---|---|---|
| 형태(radius) | 단계 슬라이더 | 5단계(각짐~둥긂), 각 단계 = 검증된 radius 계열 | 즉시 미리보기 |
| 밀도(여백) | 단계 슬라이더 | 3단계(촘촘·보통·여유) | 즉시 |
| 깊이감 | 단계 슬라이더 | 3단계(평면·약간·입체) | 즉시 |
| 컬러 팔레트 | 후보 카드 선택 | 현재 + 조화 후보 4개 | 즉시 |
| 폰트 페어링 | 후보 카드 선택 | 현재 + 검증 페어링 4개, 실제 헤드라인으로 미리보기 | 즉시 |
| 섹션 | 목록 | 순서 변경(드래그 + 위/아래 버튼), 숨기기, 용도별 섹션 추가 | 즉시 |
| 카피 | 미리보기 안 텍스트 직접 편집(contenteditable, 길이 제한) | — | 저장 시 반영 |
| 전체 분위기 | "더 과감하게 / 더 안정적으로" 버튼 | 한 번에 한 단계 | 재생성 없이 token만 이동 |

  - 조화 규칙을 깨는 조합을 고르면 막지 않되 미리보기 위에 "추천 보정: 대비가 부족해 글자색을 조정했어요" 안내 + "원래대로" 버튼(8장 "충돌 시 이유 안내"의 구체화). 접근성 규칙(WCAG AA)은 원래대로도 위반할 수 없음.
  - 되돌리기/다시하기(Ctrl/Cmd+Z, 최대 50단계), 변경 전/후 비교 토글.
  - 미리보기는 데스크톱/모바일 토글.
  - **[이후]** 자연어 요청("헤더를 좀 더 가볍게"): LLM이 위 컨트롤 조작(token 연산 JSON)으로만 번역하고, 적용 전 "이렇게 바꿀게요: 그림자 입체 → 약간" 확인을 받는다. 자유 CSS 생성 금지.
  - **[이후]** 전문가 모드: 원시값 입력(접근성 검사 유지).
  - 1장 3단계 "요소 단위 미세 조정"은 이 편집 화면으로 통합하고 진단 플로우에서 삭제(UX-02).
- **수용 기준**: 모든 편집 컨트롤이 token 변경만 일으키고 레이아웃 트리 재생성을 하지 않는다. 컨트롤 조작 후 미리보기 반영 ≤ 200ms. 어떤 조합에서도 내보낸 시안의 텍스트 대비가 WCAG AA를 만족한다. 되돌리기로 최초 상태까지 복구 가능.

### UX-10 · Major · 빈 상태·에러·실패 상태 정의 없음
- **관련 섹션**: 6장(린터 재생성, 조화 점수 미달 숨김), 8장 4단계(조화 점수 미달 시안 숨김)
- **허점**: "미달 시안은 숨긴다"는 있지만, 숨긴 결과 시안이 3개 미만이거나 0개일 때 사용자에게 무엇을 보여주는지 없다. 네트워크·모델 오류, 썸네일 렌더 실패 등도 없다.
- **왜 문제인가**: 생성형 서비스는 실패가 일상이다(모델 오류, 린터 반복 실패, 비용 한도). 실패 상태가 정의되지 않으면 에이전트는 빈 화면이나 기술 오류 메시지를 노출한다. 대기업 리뷰에서 예외 플로우는 필수 점검 항목이다.
- **보완안 [MVP]**:

| 상황 | 감지 조건 | 사용자에게 보이는 것 | 행동 | 로그 |
|---|---|---|---|---|
| 설문 시안 렌더 실패 | 카드 로드 5초 초과 또는 오류 | 해당 카드 회색 + "불러오지 못했어요" | 문항 자동 교체(같은 축 대체 문항) | `quiz_render_error` |
| 진단 결과 일관성 매우 낮음 | 일관성 점수 < 기준치 | 결과 화면 혼합 표시(UX-07) + "두 스타일로 각각 시안을 만들어 볼까요?" | 혼합 유형 2개로 시안 생성 | `low_consistency` |
| 통과 시안 1~2개 | 조화·린터 통과 < 3 | 통과한 시안만 노출 + "기준을 통과한 시안만 보여드려요" | "다른 방향으로 더 만들기"(1회) | `drafts_partial` |
| 통과 시안 0개 | 통과 = 0 | "이번엔 기준에 맞는 시안을 만들지 못했어요" + 유형 대표 시안(사람이 검수한 프리셋 시안) 제시 | 다시 시도 / 대표 시안으로 시작 | `drafts_none` |
| 모델·서버 오류 | API 오류, 폴백까지 실패 | "잠시 문제가 생겼어요. 입력하신 내용은 저장돼 있어요" | 다시 시도(입력 유지) | `gen_error` + 모델명 |
| 일일 생성 한도 초과 | 세션/IP당 한도(예: 하루 5회) | "오늘 생성 횟수를 모두 썼어요. 내일 다시 이용해 주세요" + 이미 만든 시안 링크 | — | `rate_limited` |
| 네트워크 끊김 | offline 이벤트 | 상단 배너 "연결이 끊겼어요. 응답은 연결되면 저장돼요" | 자동 재시도 | — |
| 내보내기 실패 | 다운로드 생성 오류 | 토스트 + 다시 시도 | — | `export_error` |
| 존재하지 않는/만료된 링크 | 404 / 30일 경과 | "링크가 만료됐어요" + 새로 진단하기 | — | — |

  - 모든 오류 문구는 "무슨 일이 / 내 데이터는 안전한지 / 다음 행동" 3요소 포함. 기술 오류 코드 노출 금지(개발자 콘솔 로그만).
- **수용 기준**: 위 9개 상태가 각각 구현되고 개발용 강제 트리거(쿼리 파라미터 또는 플래그)로 재현 가능. 어떤 실패에서도 빈 화면과 원문 오류 메시지가 노출되지 않는다.

### UX-11 · Major · 접근성 요구사항 없음(서비스 UI, 설문, 색 취향 문항)
- **관련 섹션**: 1장 1~3단계, 8장(시안의 WCAG AA만 언급)
- **허점**: 생성 시안의 대비 규칙만 있고 **서비스 자체**의 접근성 목표가 없다. 시각 비교가 본질인 설문을 키보드·스크린리더·색각 이상 사용자가 어떻게 할지 정의가 없다.
- **왜 문제인가**: 국내 대기업 리뷰는 KWCAG 2.2 / WCAG 2.1 AA 준수를 기본으로 본다. 또 색각 이상 사용자(남성 약 5~8%)가 색 취향 문항에서 고른 결과는 실제로 보는 색과 시스템이 기록하는 색이 달라, 생성 시안이 본인 눈에는 예상과 다르게 보일 수 있다.
- **보완안 [MVP]**:
  - 목표: 서비스 UI(S01~S10) **WCAG 2.1 AA**. 생성 시안은 8장 규칙 유지.
  - 키보드: 문항 카드는 `radiogroup`/`radio` 의미 구조. 방향키로 이동, Enter/Space로 선택, 숫자키 1~4 단축키, 뒤로 = Backspace 대신 명시적 버튼(Alt+←). 포커스 링 3px, 대비 3:1 이상. 모바일 페이저도 키보드로 순회 가능.
  - 스크린리더: 각 시안 카드에 **스타일 설명 대체 텍스트**를 프리셋 벡터에서 규칙 기반으로 생성(예: "명조 계열 큰 제목, 넓은 여백, 각진 모서리, 무채색에 주황 포인트"). 이 경우 진단은 '설명 기반 선택'이 되므로 결과 화면에 "설명으로 진단했어요" 표시. 진행률은 `aria-valuenow`로 노출, 문항 전환 시 제목으로 포커스 이동.
  - 색각 이상 대응: 컬러 관련 문항과 팔레트 선택 카드에 **색 이름 텍스트 라벨**(예: "짙은 남색 · 따뜻한 베이지 · 주황") 상시 표시. 진단 시작 화면에 선택 항목 "색 구분이 어려운 편이에요" 체크 → 체크 시 컬러 축은 문항 수를 줄이고 명도 대비 중심으로 묻고, 생성 시 색상 대비를 명도 기준으로 확보(색만으로 정보 전달 금지). 이 정보는 세션에만 저장(민감정보로 취급, 수집 동의 문구 표시).
  - 모션: 모션 축 문항은 `prefers-reduced-motion` 사용자에게 자동 재생하지 않고 "재생" 버튼으로 제공. 서비스 UI 전환 애니메이션도 비활성.
  - 시간 제한 없음(문항별 타이머 금지).
  - [이후] 외부 접근성 점검(국내 웹 접근성 인증 수준 진단).
- **수용 기준**: axe-core 자동 검사에서 S01~S10 critical/serious 위반 0건(CI에 Playwright + axe 포함). 키보드만으로 진단 시작 → 결과 → 시안 생성 → 내보내기 완료 가능. 모든 시안 카드에 비어 있지 않은 대체 텍스트 존재. 컬러 문항 카드에 색 이름 라벨 존재.

### UX-12 · Major · 사용성 테스트 계획·검증 지표 없음
- **관련 섹션**: 6장 골든 세트, 7장 "실제 선택률·수정 횟수", 8장
- **허점**: 모델 평가 지표는 있지만 **제품·UX 성공 지표와 진단의 타당성 검증**이 없다. "진단이 정말 취향을 맞히는가?"를 확인하는 방법이 없다.
- **왜 문제인가**: 이 서비스의 핵심 가설은 "16문항 진단 → 내 취향 시안"이다. 이 가설을 검증하지 않으면 정교한 벡터·트렌드 시스템이 사용자 눈에 랜덤 시안과 구분되지 않을 위험을 모른 채 지나간다. C3 기준에서 성공 지표 부재는 탈락 사유다.
- **보완안**:
  - **핵심 지표(North Star 후보)**: "생성 시안을 선택해 편집 후 내보낸 세션 비율".
  - **퍼널 지표 [MVP]** (이벤트 로깅으로 측정, 초기 목표치):

| 지표 | 정의 | MVP 목표 |
|---|---|---|
| 진단 시작률 | 랜딩 방문 → 첫 문항 응답 | ≥ 40% |
| 진단 완료율 | 첫 문항 → 결과 도달 | ≥ 70% |
| 진단 소요 시간 | 첫 응답 → 결과 | 중앙값 ≤ 4분 |
| 결과 공감 점수 | 5점 척도 평균 | ≥ 3.8 |
| 시안 생성 전환 | 결과 → 생성 완료 | ≥ 50% |
| 시안 선택률 | 생성 완료 → 시안 1개 선택 | ≥ 60% |
| 편집 횟수 | 선택 후 내보내기까지 컨트롤 조작 수 | 중앙값 ≤ 10 (적을수록 첫 시안 품질 높음) |
| 내보내기율 | 시안 선택 → 내보내기 | ≥ 30% |

  - **진단 타당성 검증 [MVP]**:
    - 블라인드 선호 테스트: 진단 결과 기반 시안 1개 vs 무작위 유형 시안 1개를 라벨 없이 보여주고 선택 → **결과 기반 선택 ≥ 70%**(n ≥ 30 세션).
    - 재검사 신뢰도: 같은 사용자가 1주 후 재진단 시 같은 유형(또는 혼합 1순위) 일치 ≥ 60%(n ≥ 15).
  - **사용성 테스트 계획 [MVP]**: 1인 개발 대체안 — 지인/커뮤니티 모집 **5명 × 2라운드**(구현 직후, 수정 후), 원격 화면공유 + 소리 내어 생각하기, 1인 30분. 참가자 구성: 비디자이너 3명(타깃 = 감각 부족 사용자), 디자이너/개발자 2명, 모바일 사용 2명 이상.
    - 과제: ① 안내 없이 진단 끝내기 ② 결과 차트 의미 설명하기 ③ 자기 가게(가상) 정보 넣고 시안 받기 ④ 시안의 모서리를 더 둥글게, 글꼴을 바꾸고 내보내기.
    - 측정: 과제 성공률(목표 ≥ 80%), 과제 시간, SEQ(과제 후 난이도 7점), 종료 후 SUS(목표 ≥ 70).
  - [이후] 실서비스 A/B(문항 수 12 vs 16, 4지선다 vs 3지선다), 코호트 리텐션.
- **수용 기준**: 위 퍼널 이벤트가 이벤트 스키마(이름·속성)로 기획서에 정의되고 구현된다. 사용성 테스트 2라운드 결과가 기록되고 과제 성공률 ≥ 80%, SUS ≥ 70 달성 전에는 공개 출시하지 않는다.

### UX-13 · Major · 2단계 A/B 문항의 인지 부하와 "차이 감지 가능성" 기준 없음
- **관련 섹션**: 1장 2단계("불확실한 축만 하나씩 바꾼 A/B 시안")
- **허점**: 한 축만 바꿨을 때 그 차이가 사용자 눈에 보이는 크기인지에 대한 기준이 없다. 자간 0.01em 차이나 그림자 미세 차이는 대부분의 사용자가 구분하지 못한다. 반대로 축 이름을 노출하면 "정답 고르기" 편향이 생긴다.
- **왜 문제인가**: 감지 불가능한 차이를 묻는 문항은 무작위 응답을 만들고(잡음), 사용자는 "같은 거 아니야?"라는 경험으로 서비스 신뢰를 잃는다.
- **보완안 [MVP]**:
  - 최소 변화량: A/B 간 해당 축 값 차이는 **축 범위의 30% 이상**(예: radius 0~24px 축이면 ≥ 8px 차이). 내부 검수로 "5명 중 4명이 차이를 말로 설명 가능"한 쌍만 문항 풀에 포함.
  - 노출 범위: 바뀐 축이 가장 잘 드러나는 영역을 기준으로 크롭(예: radius → 카드·버튼 영역, 타이포 → 히어로). 축별 크롭 영역을 문항 데이터에 `focusRegion`으로 저장.
  - 축 이름·차이 강조 표시(화살표, 하이라이트) 금지. 대신 문항 제목은 상황형 질문 사용: "어느 쪽이 더 마음에 드나요?" 통일(유도 문구 금지).
  - "차이를 모르겠어요" 선택지(UX-04)와 응답 시간으로 문항 품질을 측정 → "모르겠어요" 비율 30% 초과 문항은 풀에서 자동 제외 후보.
- **수용 기준**: 문항 데이터에 `axis`, `deltaRatio ≥ 0.3`, `focusRegion`이 존재. 문항별 "모르겠어요" 비율이 대시보드(또는 SQL 쿼리)로 확인 가능.

### UX-14 · Major · 진단 전후의 기대 관리·온보딩·출구(결과만 보고 떠나기) 미정
- **관련 섹션**: 1장 전체, 2장(설문에는 오리지널 시안)
- **허점**: 랜딩에서 "무엇을 얻는지", "누구를 위한 것인지"(타깃), 결과물이 실제 사이트 제작용인지 참고용인지가 없다. 결과에서 이탈하는 사용자(시안까지 안 가는 사용자)를 위한 가치도 정의되지 않았다.
- **왜 문제인가**: 타깃과 기대 수준이 화면 카피와 플로우에 반영되지 않으면, "MBTI 테스트"로 들어온 가벼운 사용자와 "실제 사이트 만들 사람"이 같은 플로우에서 모두 불만족한다. 문제 정의·타깃 부재는 C3 탈락 요인이기도 하다(기획 리뷰어 영역과 겹치나 UX 카피에 직접 영향).
- **보완안 [MVP]**:
  - 타깃 1순위 명시: "디자이너 없이 자기 사이트를 만들려는 소상공인·1인 창업자·개발자(감각에 자신 없음)". 2순위: 재미로 취향 테스트를 하는 사용자(공유 유입).
  - 랜딩 구성: 한 줄 가치("4분 취향 진단으로 내 취향에 맞는 사이트 시안 3개"), 예시 결과 3개(유형 + 시안), "로그인 없이 · 무료 · 약 4분".
  - 결과까지만 원하는 사용자를 위한 출구: 결과 공유, "내 유형 디자인 가이드"(폰트 페어링·팔레트·radius 값 요약 카드, 복사 가능)를 결과 화면 하단에 제공 → 시안 생성 없이도 가치.
  - 내보낸 코드의 사용 범위 안내 문구(상업적 사용 가능 여부, 폰트 라이선스) — 법무 리뷰와 연결.
- **수용 기준**: 기획서에 타깃 1·2순위와 각 타깃의 성공 경로가 정의됨. 랜딩·결과 화면 카피 초안이 기획서에 포함됨.

---

### UX-15 · Minor · 설문 화면 자체의 시각 환경이 판단에 영향
- **관련 섹션**: 1장 1~2단계, 디자인 축(다크)
- **허점/보완**: 서비스 UI가 다크 테마거나 강한 브랜드 컬러를 쓰면 카드 인식이 왜곡된다. 설문 영역 배경은 **중립 회색(#F4F4F5 계열) 고정**, OS 다크 모드여도 설문 카드 주변은 중립 유지. 다크 시안 문항은 카드 내부에서만 다크.
- **수용 기준**: 설문 화면 배경·카드 테두리 색이 고정 토큰으로 정의됨.

### UX-16 · Minor · 마이크로카피·톤 가이드 없음
- **허점/보완**: 서비스의 "일반론 카피 금지"(3장)가 서비스 UI 카피에도 적용되어야 한다. 해요체, 한 문장 ≤ 40자, 이모지 금지, "AI가" 대신 "시스템이/저희가" 표현 원칙 등 10줄 내외의 톤 가이드를 부록으로 추가 [MVP].

### UX-17 · Minor · 결과 공유 바이럴 장치
- **보완**: [이후] 공유용 세로 이미지(인스타 스토리 9:16), 친구와 취향 비교("우리 둘의 디자인 궁합"), 유형별 랜딩 URL(`/type/[slug]`)로 SEO 유입.

### UX-18 · Minor · 시안 비교 화면(S07)의 라벨 일관성
- **허점/보완**: 1장 5단계는 "취향 그대로 / 과감하게 / 안정적으로", 8장은 "취향 그대로 / 용도 최적 / 균형"으로 **라벨이 서로 다르다.** 하나로 통일(권장: 8장 안 — 보정 시스템과 논리가 맞음)하고, 각 카드에 "무엇을 보정했는지" 1줄 표시.

### UX-19 · Minor · 국제화·한글 렌더링
- **보완**: MVP는 한국어 전용 명시. 설문 시안의 한글 웹폰트 로딩(FOUT)으로 카드별 표시 시점이 달라지지 않도록 폰트 프리로드 후 4장을 **동시에** 노출(공정성, UX-03과 연결).
