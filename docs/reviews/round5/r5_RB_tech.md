## 2. 새 항목

### RB5-01 · Major · 실서비스(비스트리밍)에서 사건 t1이 3초 타이머보다 늦게 와 예열 추정이 깨짐 (테크 리드, AI/ML)
- 섹션: 06 6.9.4 ①③⑥, 6.2.3 시퀀스, 6.2.4 표, `callLlm`(`generateObject`만 사용), 6.12 기술 선택표
- 허점: U-01 ①은 비스트리밍의 사건 t1을 "응답 완료"로 정했다. 그런데 실서비스 호출은 전부 `generateObject`(비스트리밍)이고, 레이아웃 호출은 p50 25초 중 대부분을 쓴다. 그래서 실서비스에서는 항상 `t0 + 3s`가 먼저 온다. ③ 규칙("앞선 gen_layout이 t1에 도달했으면 cached")대로라면 후보 1~5는 모두 `cache_write`로 추정된다. 그러면 예약 누적이 0.05325 + 0.04481×6 = 0.32211 > 0.30이 되어, 실서비스 기본 경로에서 후보 5가 늘 `budget_skipped`가 된다. 실제 청구는 공급자 캐시가 처리 시작 시점부터 적중하므로 cached다. 결국 추정만 틀려서 후보를 버리는 셈이다. ⑥ `cost:model`의 "예약 합계 ≤ capEff" 검사가 어느 `cacheState`로 계산하는지도 정해지지 않아서, CI는 통과해도 실서비스는 다르게 동작할 수 있다. 6.2.4의 "예열 TTFT ≈ 1~2s"도 스트리밍을 전제로 한 문장이다.
- 보완안: 값은 바꾸지 않고 판정 규칙 한 줄만 고친다. `cacheState = cached` ⇔ 같은 잡의 앞선 `gen_layout`이 t1(= min(사건 t1, t0 + 3s)) 시점에 실패하지 않았다(진행 중이거나 완료). 후보 0이 t1 전에 실패한 경우에만 `cache_write`로 둔다. `cost:model`은 이 규칙(기본 경로 = 후보 0 cache_write + 5 cached)으로 계산한다고 적는다. 6.2.4 비고에는 "비스트리밍은 t0 + 3s 대기"를 적는다.
- 수용 기준: 사건 t1이 3초를 넘도록 지연을 준 Mock 변형(`MOCK_LLM_LATENCY_MS=4000`)으로 `ok`를 돌린다. 이때 후보 1~5의 est가 0.02774이고, `budget_skipped`가 0건이며, 후보 1~5의 `started_at`이 t0 + 3s ± 50ms다. 후보 0 실패 주입 시에는 다섯 모두 cache_write로 추정된다.

### RB5-02 · Major · `usage_overrun` 기대 상태가 U-01 계산 결과와 모순 (테크 리드, QA)
- 섹션: 06 6.9.4 ⑦ 표 `usage_overrun` 행, 6.2.3 `partial ⇔ 1 ≤ n_real ≤ 2`, 04 4.8 후보 인덱스(4·5 = `v_bal`), AC-06-61, AC-06-62 ③
- 허점: 새 거부 집합에 따르면 후보 0~4가 출발해 정산되고 `ok`다. 비전과 수정만 생략된다. 후보 인덱스로 보면 0·1 = `v_true`, 2·3 = `v_fit`, 4 = `v_bal`이므로 세 변형 모두 실물이 있어 n_real = 3이다. 비전을 생략해도 `succeeded`라는 점은 AC-06-62 ③이 이미 정해 두었다. 따라서 계산상 상태는 `succeeded`인데 표는 여전히 {partial, fallback}이다. U-01 ③은 "다르면 계산값을 쓰고 'U-01 계산' 주석"을 요구했지만 반영되지 않았다. 지금 상태로는 AC-06-61이 영구 fail이 되거나, 에이전트가 상태를 임의로 해석하게 된다.
- 보완안: `usage_overrun` 기대 상태를 `succeeded`(n_real 3, U-01 계산)로 고친다. 6.17·07 TC-R 중 이 시나리오를 참조하는 곳의 상태 문구도 같은 값으로 맞춘다.
- 수용 기준: `usage_overrun` 통합 테스트에서 잡 상태가 `succeeded`다. 노출 시안 3개가 모두 비폴백이고, `budget_skipped` 행은 후보 5, `judge_vision` 6건, 수정 호출뿐이다.

### RB5-03 · Major · tuning-log에 캐시 표시가 없고, AC-02-36 ③ gate 3회 도달 조건이 미정 (AI/ML, QA)
- 섹션: 02 2.16.2 시도 계수, AC-02-36 ③⑥, 07 7.12.1 tuning-log 스키마, 7.12.2 8c
- 허점:
  - AC-02-36 ⑥은 "2바퀴 시작점 항목은 캐시 표시로 세지 않는다"고 적었다. 그런데 tuning-log `trials` 스키마(`round, coordinate, value, devMetrics, objective, chosen, gateRun`)에는 캐시 필드가 없다. 그래서 8c가 dev 시도 수를 셀 때 캐시 항목을 넣는지 빼는지가 갈린다. 넣으면 16 > 15가 되어 guard FAIL이고, 아예 기록하지 않으면 ⑥의 "캐시 표시"를 확인할 수 없다.
  - U-08대로면 15회 안에서 gate는 보통 2회(1바퀴 뒤 1회 + 상한 도달 1회)까지만 돈다. AC-02-36 ③("가짜 실패 주입 시 gate 실행 수가 3에서 멈춘다")은 1바퀴에서 아무 좌표도 바뀌지 않아 2·3바퀴가 전부 캐시되는 픽스처에서만 성립한다. 그런데 그 픽스처 조건이 적혀 있지 않다. 같은 구성에 gate를 다시 돌릴 때 그것도 세는지도 정해지지 않았다. 그래서 ③과 ⑥이 서로 다른 gate 횟수를 기대한다.
- 보완안: ① trials 항목에 `cached: boolean`을 더한다. 8c는 `cached=false`인 dev 항목만 센다. ② AC-02-36 ③의 픽스처를 "dev 지표가 모든 좌표에서 동률(목적함수 ③으로 현재 값 유지), gate는 항상 FAIL"로 적는다. 같은 구성에 gate를 다시 돌려도 1회로 센다고 명시한다(결과: dev 11, gate 3, BLK `sim-limit`). 상한 값 15·3은 그대로 둔다.
- 수용 기준: ③과 ⑥ 픽스처 각각에서 guard 8c가 PASS다. ③은 gate 3·dev 11이고, ⑥은 gate 2·dev 15이며 `cached=true` 항목이 1개 이상이다.
