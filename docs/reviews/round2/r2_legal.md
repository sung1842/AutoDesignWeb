# R2 리뷰: 법무·개인정보·보안 관점

- 대상: `docs/spec/v2/08_legal.md`(전체 정독). 다른 장은 법무·개인정보·보안 관련 절만 grep으로 확인했다(06 6.3.3 DDL의 사용자 FK, 6.3.5 RLS, 6.4.2~6.4.5, 6.5, 6.6, 6.10.1, 6.11, 6.12 / 04 4.6.3~4.6.4, 4.15 / 01 1.2 S05, 1.5.5.3, 1.8.4, 1.12 / 05 5.3·5.4.1 / 09 9.2.2~9.2.5 / 00 §10).
- 기준: `rubric.md`, `decisions_v2.md`(R-01~R-38), 1라운드 `r1_legal.md`(LG-01~20)
- 규칙: 1라운드에서 해결된 항목은 다시 쓰지 않는다. 새로 찾은 허점과 덜 해결된 부분만 적는다. 다른 R2 리뷰가 이미 지적한 항목(미선택 후보 보관 규칙과 DDL 불일치 TL2-05, 08장의 옛 테이블명 `survey_sessions` 잔재, 폰트 서브셋 UI2-04, 판정 보류 상태 일반론 QA2-02)은 빼고 법무 영역에서 새로 생기는 결과만 다룬다. 이 리뷰는 법률 자문이 아니다. 법령 해석이 걸린 항목은 **사람 확인 필요**로 표시했고, 그동안 적용할 안전한 기본값을 함께 적었다.

## 총평

v2의 08장은 1라운드 지적 20건을 모두 받아들였다. 소스 매트릭스, ingest CLI 규칙, 스크린샷 90일, Originality Guard(G1~G6 + 보정 절차), 자산 레지스트리와 LICENSES.md 생성 규칙, 약관 조항 초안, AI 고지 위치표, 수집 항목표 P1~P13, 법적 근거, 동의 화면, 마스킹 정규식, `processors.yaml`, 보관 기간표, 권리 행사, 유출 대응, 승인 공급자 L1~L5, 고위험 브랜드 차단, 법무 문서 필수 헤딩, 전문가 질문 15개, 출시 게이트 체크리스트가 들어 있다. 거의 모든 규칙에 수용 기준이 붙어 있다. 1인 서비스 기준으로는 대기업 법무 리뷰에 올려도 뼈대가 부족하다는 말을 듣지 않을 수준이다.

남은 문제는 "정책은 맞게 썼는데, 다른 장의 구현 경로와 맞물리지 않는 곳"이다. 셋이 핵심이다.
1. **악용 방지 검사가 브리프 제출 한 지점에만 걸려 있다.** 편집 화면에서 텍스트 슬롯을 직접 고치면 고위험 브랜드·피싱 문구 검사 없이 공개 공유까지 갈 수 있다. 불법 업종(도박·성인·불법 대부 등) 입력은 아예 걸러지지 않는다.
2. **처리방침에 쓰려는 사실과 실제 동작이 다르다.** Google 프로필 미수집이라고 했지만 Supabase Auth가 이름·사진을 따로 저장한다. 국외 이전 표의 이전 항목도 실제 데이터 흐름보다 좁다. 탈퇴 후 1년 보관한다던 동의 기록은 DDL상 바로 cascade 삭제된다.
3. **사람 없이 구현할 때 컴플라이언스 데이터(고위험 브랜드 목록, 자산 라이선스 확인일, 법무 문서)를 어떻게 임시로 채울지 규칙이 없다.** 경로도 08장과 09장이 서로 다르다.

모두 문서 수정과 작은 구현 규칙 추가로 고칠 수 있다. 새 인프라는 필요 없다.

## 2. 새 항목

### LG2-01 · Major · 악용 방지 검사가 브리프 제출 한 지점에만 걸려 있음(편집 우회, 불법 업종 미필터)

- **관련 절**: 08 8.9.2(판정 위치: `POST /api/projects`·`POST /api/brief-drafts`), 8.9.6 / 06 6.4.3 버전 저장 처리, 6.4.5, 6.11.2, 6.11.3 / 04 4.15.1 "텍스트" 행, 4.15.2 재검사 표, 4.6.4 / 01 1.8.4 텍스트 행, 1.12
- **허점**:
  1. **편집 경로 우회.** 01 1.8.4와 04 4.15.1은 텍스트 슬롯을 사용자가 직접 입력하도록 허용한다. 그런데 버전 저장 시 서버 검사(06 6.4.3 "G-01, G-02·G-03, G-09 린터, G-10 브랜드명, G-12")와 04 4.15.2 재검사 표에는 8.9.2의 고위험 브랜드·피싱 문구 판정이 없다. 04 4.6.4의 "금지 사전"은 상투어 사전(`cliche_ko.json`)이라 이 역할을 못 한다. 6.11.3 `postCheck`(고위험 `domains`·별칭 검사)도 LLM 출력에만 걸린다. 결과적으로 "온결 베이커리"로 생성한 뒤 히어로 문구를 "KB국민은행 고객 본인인증 안내 — 보안카드 번호를 확인하세요"로 바꾸면 G-10(원래 브랜드명이 nav·hero·footer에 있음)도 통과하고, `pre_share` 저장 후 공개 공유(S13)까지 간다.
  2. **장 사이 모순.** 06 6.11.2는 "6.4.5 순서를 모든 사용자 텍스트 입력(브리프, 편집 텍스트 슬롯, **신고·문의 본문**)에 적용한다"고 적었다. 6.4.5에는 5단계(피싱 문구 판정 → 422 `BLOCKED_BRAND`)가 들어 있다. 이 문장을 그대로 구현하면 ① 편집 저장 실패를 `EDIT_GATE_FAILED`와 `BLOCKED_BRAND` 중 무엇으로 돌려줄지 정해져 있지 않다. ② 신고 본문에 "비밀번호 입력을 요구함"이라고 쓴 피싱 신고가 422로 막힌다.
  3. **불법·유해 업종 미필터.** 8.9.1 AUP ④는 불법 정보·청소년 유해 정보를 금지하지만, 입력 검사는 금융·공공 사칭(8.9.2)뿐이다. 01장 신고 사유에는 "불법·유해"가 있는데 이를 막는 사전 차단 규칙이 없다. 그래서 불법 도박·성인 서비스·불법 대부·마약류 판매 같은 브리프가 그대로 생성되고 공개 공유 링크로 배포된다. 8.1.5는 이 범주를 *레퍼런스*에서만 뺀다.
- **왜 문제인가**: 사칭·피싱 페이지 호스팅은 00장 리스크와 06 위협 모델 T-09가 이 서비스의 대표 평판·법적 위험으로 꼽은 것이다. 그런데 가장 쉬운 우회 경로가 열려 있다. 정보통신망법상 불법정보 유통 방지 관점에서도, 대기업 리뷰는 "제출 시점만 막는가, 게시 시점에도 막는가"를 반드시 묻는다(C3). 06 6.11.2를 따르면 에이전트는 오류 코드와 적용 범위를 스스로 정해야 한다(C2).
- **보완안 [MVP]**:
  1. 8.9.2에 "**입력별 적용 단계 표**"를 넣고 06 6.11.2를 이 표 참조로 바꾼다.

     | 입력 | 정규화(6.4.5 ②) | `maskPII` | 고위험·피싱·유해 업종 판정 | 실패 응답 |

     | 신고·문의·권리 요청 본문 | O | X(신고 증거 보존) | **X** | — |

  2. 새 하드 게이트 `G-13 abuse_terms`를 04 4.10.2에 추가한다. 브리프 단계 판정 함수를 그대로 재사용하고(`packages/compliance/abuse.ts` 하나), 렌더 게이트에서도 최종 트리 텍스트 전체에 다시 실행한다(LLM 출력 + 편집 결과 이중 확인).
  3. `config/high_risk_brands.json` 옆에 `config/prohibited_categories.json`을 둔다. 범주는 `gambling | adult | illegal_loan | drugs | weapons | counterfeit` 6개, 범주당 한국어 키워드 ≥ 10개, 정규화는 8.9.2와 같다. 판정되면 `BLOCKED_BRAND{reason:'prohibited_category'}`로 거부한다(R-13 `reason` enum 1개 추가, 01 1.12 문구 1행 추가: "이 서비스로 만들 수 없는 업종이에요. 오해라면 문의해 주세요."). 범주·키워드 목록의 적정성은 **사람 확인 필요**(8.14 Q13에 추가).
- **수용 기준**:
  - AC-08-41b: 정상 브리프로 생성한 시안에서 텍스트 슬롯 1개를 고위험 브랜드명 20종 / 피싱 문구 11종으로 바꿔 저장하면 100% 422 `EDIT_GATE_FAILED`이고 `failed`에 `GATE_FAILED:G-13`이 있다. 그 버전으로 공유 생성하면 409 `VERSION_GATE_NOT_PASSED`.

  - AC-08-41d: 본문에 "비밀번호", "OTP"가 들어간 신고·권리 요청이 202/201로 접수된다.

### LG2-02 · Major · Google 로그인 시 이름·사진이 Supabase Auth 메타데이터에 저장되어 "미수집" 고지와 어긋남

- **관련 절**: 08 8.7.1 ②, AC-08-29 / 06 6.5.2 "Google 범위 `openid email`만", 6.3.3 `users`(auth.users INSERT 트리거)
- **허점**: 08장은 "Google 프로필의 이름·사진은 가져오지 않는다"고 고지하고, AC-08-29는 `public.users.display_name IS NULL`만 확인한다. 하지만 Supabase Auth(GoTrue)는 OAuth 공급자 응답을 `auth.users.raw_user_meta_data`와 `auth.identities.identity_data`에 그대로 저장한다(보통 `full_name`, `name`, `avatar_url`, `picture`). Google 공급자는 앱이 `scopes`를 줄여 넘겨도 기본 범위(`email`, `profile`)를 붙이는 것으로 알려져 있다. 그래서 6.5.2의 "`openid email`만"은 설정만으로는 보장되지 않을 가능성이 높다. 이 데이터는 `auth` 스키마에 있어서 DDL 검사·RLS 테스트·내려받기(`GET /api/me/export`) 어디에도 걸리지 않는다.
- **왜 문제인가**: 처리방침의 "처리 항목"과 실제 보유 항목이 다르면 개인정보보호법상 처리방침 공개 의무(제30조)와 최소 수집 원칙(제16조) 문제가 된다. 열람 요청에 이 값이 빠지는 것도 문제다. 대기업 개인정보 심사는 "IdP에서 실제로 무엇이 들어오는가"를 토큰 덤프로 확인한다(C3). 구현 에이전트는 Supabase 기본 동작을 모른 채 설정만 하고 테스트를 통과시킨다(AC가 잘못된 곳을 본다).
- **보완안 [MVP]**:
  1. 06 6.3.3에 `auth.users` AFTER INSERT/UPDATE 트리거(security definer)를 추가한다. `raw_user_meta_data`에서 `email`, `email_verified`, `provider_id`, `sub`를 뺀 모든 키를 제거한다. `auth.identities.identity_data`도 같은 방식으로 정리한다. 로그인마다 공급자가 다시 덮어쓰므로 UPDATE에도 건다.
  2. 6.5.2 "Google 범위" 행을 "범위는 `openid email`을 요청하되, 공급자가 보낸 프로필 필드는 위 트리거가 저장 직후 지운다"로 고친다. 실제 저장 키 목록은 M2 구현 시 로컬 스택에서 덤프해 `docs/compliance/auth-metadata.md`에 기록한다(사람 확인 불필요, 테스트로 확인).
  3. 처리방침 2절(처리 항목)에 "Google 로그인 시 공급자가 전달하는 이름·프로필 사진은 저장하지 않고 즉시 삭제" 한 줄을 넣는다.
- **수용 기준**:
  - AC-08-29 개정: 로컬 Supabase에 Google 공급자 목(GoTrue 외부 공급자 테스트 픽스처 또는 `auth.users`에 직접 INSERT한 공급자 형태 행)으로 가입한 뒤 `auth.users.raw_user_meta_data`와 `auth.identities.identity_data`의 키 집합 ⊆ {`email`, `email_verified`, `provider_id`, `sub`, `iss`}이다. `full_name|name|avatar_url|picture` 키는 0건이다.
  - 같은 테스트를 "두 번째 로그인(UPDATE)" 후에도 통과한다.

### LG2-04 · Major · 탈퇴 처리: 동의 기록 보존·제재 기록·삭제 순서가 DDL과 충돌

- **관련 절**: 08 8.7.7("동의 기록 탈퇴 후 1년, `user_id`를 해시로 대체"), 8.7.9("남는 것: `consents`(해시)", P6 삭제), 8.9.5(`gen_suspended`·`suspended`) / 06 6.3.3 `consents.user_id … on delete cascade`, `users.id references auth.users on delete cascade`, `llm_calls.owner_id … on delete set null`, `admin_audit_logs`(append-only 트리거) / 06 6.2.5 `account-delete` 큐(절차 정의 없음)
- **허점**:
  1. `consents.user_id`가 `on delete cascade`라서 탈퇴하면 동의 기록이 **바로 삭제된다**. 해시로 바꿀 컬럼(`user_hash`)도 없다. 08장의 "탈퇴 후 1년 보관"이 구현될 수 없다.
  2. `account-delete` 잡의 단계가 정해져 있지 않다. 그래서 `llm-payloads` 객체(경로 `<yyyy-mm-dd>/<llm_call_id>`, 소유자 경로 아님)를 지우기 전에 `users`가 지워지면, `llm_calls.owner_id`가 `set null`로 바뀌어 **어느 객체가 그 사용자 것인지 더는 찾을 수 없다.** 30일 순환 삭제까지 남게 되어 8.7.9 "P6 삭제"가 깨진다.
  3. 제재(`users.status = 'suspended'`)는 `users` 행에만 있다. 정지된 사용자가 탈퇴하고 같은 이메일로 다시 가입하면 제재가 사라진다(8.9.5가 무력화된다).
  4. (부수) `admin_audit_logs.admin_id … on delete set null`은 참조 동작으로 UPDATE를 일으킨다. 그런데 이 테이블은 트리거로 UPDATE를 거부하므로, 관리자 계정을 탈퇴시키면 삭제 자체가 실패한다.
- **왜 문제인가**: 동의 증빙을 보존하지 못하면 분쟁 시 입증이 어렵다. 반대로 지운다고 써 놓고 남으면(P6) 처리방침 위반이다. 보관표와 DDL이 다르면 에이전트는 둘 중 하나를 골라야 한다(C2). 대기업 개인정보 심사는 "탈퇴 시 테이블별로 삭제·분리 보관·익명화 중 무엇을 하나"를 표로 요구한다(C3).
- **보완안 [MVP]**:
  1. 06장에 `account-delete` 절차를 순서대로 적는다. ① `users.status='deleting'` + 세션 폐기 + 공유 비공개 ② `llm_calls where owner_id=:uid`의 `llm-payloads` 객체 삭제 ③ `renders`·`exports` 객체 삭제 ④ `consents`를 `consents_archive(user_hash, doc_type, doc_version, agreed, agreed_at, archived_at)`로 옮긴다. `user_hash = HMAC-SHA256(user_id, CONSENT_HASH_KEY)`이고 키는 교체하지 않는다 ⑤ 제재 상태면 `sanctions(email_hash, level, until, reason_code)`에 기록 ⑥ `auth.admin.deleteUser`(cascade) ⑦ `admin_audit_logs(action='account_deleted', target_id=user_hash)`. 각 단계는 멱등이어야 한다(재시도 5회, 6.2.5).
  2. `consents_archive`·`sanctions`를 8.7.7 표에 넣는다(각각 1년, 제재는 `until`까지 + 최대 1년). 처리방침 4절(보유 기간)에 "부정 이용 재가입 방지를 위해 이용 정지 이력의 이메일 해시를 최대 1년 보관"을 적는다. 이 보관의 근거(정당한 이익)는 **사람 확인 필요**(8.14 Q6에 추가). 가입 콜백은 `sanctions`에 같은 `email_hash`가 있으면 `status`를 이어받는다.
  3. `admin_audit_logs.admin_id`는 FK를 없애고 `admin_hash text`로 바꾼다(append-only 유지).
- **수용 기준**:
  - 계정 삭제 E2E(AC-08-34 확장) 후: 해당 사용자의 `llm-payloads` 객체 0건, `consents` 0행이면서 `consents_archive`에 같은 수의 행, `auth.users` 0행.
  - 정지된 계정이 탈퇴 → 같은 이메일로 재가입하면 생성 API가 403 `ACCOUNT_SUSPENDED`다.
  - 관리자 계정 삭제가 성공하고 해당 감사 로그 행 수는 그대로다.
  - `RETENTION_NOW=+366d`에서 `consents_archive` 만료 행 0건.

### LG2-05 · Major · 익명 신고·문의·권리 요청 창구가 악용에 열려 있음(메일 폭탄·신고 남용·본인 확인 없음)

- **관련 절**: 08 8.1.6(접수 즉시 자동 확인 메일, `privacy_request`), 8.7.9(처리정지 요청 경로), 8.9.5(`impersonation`·`phishing` 신고 즉시 자동 비공개) / 06 6.4.3 `POST /api/rights-requests`·`/api/support`·`/api/share/:shareId/report`(인증 `anon`), 6.10.1 `rep:hour:a:<anon>` 5회/시간, 6.5.1(쿠키가 없으면 anon 경로에서 새로 발급)
- **허점**:
  1. 세 창구의 레이트리밋 키가 `anon_id` 쿠키 하나뿐이다. 쿠키는 지우면 새로 발급되므로 사실상 한도가 없다. IP 키도, Turnstile도 없다(R-29는 매직링크에만 적용).
  2. 권리 요청은 **사용자가 입력한 아무 이메일 주소로 자동 확인 메일을 보낸다.** 남의 주소로 대량 발송하는 데 쓰일 수 있고(Resend 발신 평판·계정 정지 위험), 스팸 신고로 매직링크 발송까지 막힐 수 있다.
  3. `privacy_request`(열람·삭제·처리정지)를 익명 양식으로 받지만 **요청자 본인 확인 절차가 없다.** 남의 이메일을 적어 "내 데이터 삭제·열람"을 요청하면 운영자가 응할지 정할 기준이 없다. 잘못 응하면 그 자체가 유출이다.
  4. 피싱 신고 1건이면 어떤 공개 공유 링크든 즉시 숨겨진다. 쿠키를 바꿔 가며 남의 공유 링크를 계속 내리는 괴롭힘을 막을 장치가 없다(소유자 통지도 없다).
- **왜 문제인가**: 1인 운영에서 외부 공격이 가장 먼저 노리는 곳은 인증 없는 양식이다. 메일 폭탄과 본인 확인 없는 개인정보 요청 처리는 대기업 보안 리뷰의 기본 점검 항목이다(C3). 본인 확인 방식은 운영자가 그때그때 정할 일이 아니라 규칙이어야 한다(C2).
- **보완안 [MVP]**:
  1. 세 창구 모두 Turnstile 토큰을 필수로 받는다(이미 쓰는 위젯 재사용, CSP는 이미 허용됨). 레이트리밋에 `rep:day:ip:<hmac>` 10회/일을 더한다.
  2. 자동 확인 메일은 "접수 번호·기한" 고정 템플릿으로만 보내고 사용자 입력 문자열(`details`)을 넣지 않는다. 같은 수신 주소에는 하루 1통만 보낸다(`mail:day:to:<sha256(email)>`).
  3. `privacy_request`는 처리하지 않고 "로그인한 상태에서 S12 셀프 서비스를 쓰거나, 계정 이메일에서 보낸 메일로 요청하세요"로 안내한다. 계정 이메일로 받은 요청만, **그 주소로 확인 링크(1회용, 24시간)를 보내 클릭된 뒤** 처리한다. 이 절차를 8.7.9에 1행으로 추가하고 처리방침 8절에 적는다.
  4. 자동 비공개된 공유 링크는 소유자에게 이메일로 통지하고(로그인 사용자만), S12에 "검토 중" 상태를 보여 준다. 같은 `ip_hmac`이 7일 안에 낸 신고가 3건 넘게 `dismissed` 처리되면 그 `ip_hmac`의 신고는 자동 비공개를 일으키지 않는다(검토 대기만).
- **수용 기준**:
  - Turnstile 토큰 없이 세 엔드포인트를 호출하면 400 `VALIDATION_FAILED`(또는 403)이고 DB 변경 0, 메일 발송 0.
  - 쿠키를 매번 바꿔 같은 IP로 권리 요청 11회 → 11번째 429. 같은 수신 주소로 3건 접수 → 메일 발송 1건(목 SMTP).
  - 확인 링크를 클릭하지 않은 `privacy_request`는 상태가 `received`에서 바뀌지 않는다. 처리 화면(ADM-11)의 "삭제 실행" 버튼이 비활성이다.
  - `dismissed` 3건 이력이 있는 `ip_hmac`의 `phishing` 신고 후에도 공유 링크가 200이다.

### LG2-06 · Major · 관리자(개인정보취급자) 접근 통제가 약함: 추가 인증·열람 기록·콘솔 계정

- **관련 절**: 08 8.13 S-10, 8.11.2 12절(안전성 확보 조치) / 06 6.5.4, 6.4.3 관리자 표("모든 **변경**은 `admin_audit_logs` 1행"), 6.11.5(`SUPABASE_SERVICE_ROLE_KEY`가 "관리자 로컬"에도 있음), 6.3.3 `admin_audit_logs.before/after jsonb` / 00 §10.1
- **허점**:
  1. 관리자 인증은 `ADMIN_EMAILS` + 일반 로그인(매직링크·Google)뿐이다. 관리자 경로는 모든 사용자의 이메일 검색(`/api/admin/users?q`), 문의·권리 요청 원문, 시안 스크린샷, LLM 원문(관리자 서명 URL)을 볼 수 있다. 그런데 추가 인증 요소가 없다. 6.5.4는 "목록에서 빠져도 자동 강등하지 않는다"고 적어서, 계정이 탈취됐을 때 대응이 수동이다.
  2. 감사 로그는 **변경만** 남긴다. 개인정보 **열람**(사용자 검색, 문의 조회, 원문 다운로드)은 기록되지 않는다.
  3. 실제로 전권을 가진 접근 경로인 Supabase·Vercel·Fly·LLM 공급자 콘솔 계정과, 관리자 노트북의 service role 키에 대한 요구(MFA, 키 보관)가 없다.
  4. `admin_audit_logs.before/after`에 사용자 이메일 같은 PII가 들어가면, 테이블이 append-only라서 탈퇴 후에도 지울 수 없다.
- **왜 문제인가**: 개인정보의 안전성 확보조치 기준(고시)은 개인정보취급자의 접근 권한 관리, 외부 접속 시 안전한 인증수단, 접속기록(열람 포함) 보관·점검을 요구한다. 1인·소규모 처리자에게 어디까지 적용되는지는 확인이 필요하지만, 처리방침 12절에 "접근 통제, 접근 기록"을 적겠다고 이미 약속했다. 대기업 보안 리뷰에서 "관리자 MFA 없음"은 즉시 지적 대상이다(C3).
- **보완안 [MVP]** (반나절 분량):
  1. 관리자 경로는 Supabase Auth MFA(TOTP)의 `aal2` 세션만 허용한다. `aal1`이면 `/admin/mfa`로 보낸다. 관리자 역할은 매 요청마다 `ADMIN_EMAILS`에 있는지 **다시 확인**하고, 목록에서 빠지면 즉시 404를 돌려준다(자동 강등).
  2. 개인정보를 돌려주는 관리자 GET(`users`, `support`, `reports`, `rights-requests`, `jobs/:id`, 서명 URL 발급)은 `admin_audit_logs(action='pii_view', target_type, target_id)`를 1행 남긴다. 운영 런북에 "월 1회 감사 로그 확인" 체크 항목을 추가한다(09장 운영 체크리스트).
