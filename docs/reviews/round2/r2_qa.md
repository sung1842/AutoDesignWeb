# R2 리뷰: QA 리드 관점

- 대상: `docs/spec/v2/07_quality.md`(전체 정독), `09_implementation.md` 9.2(데이터 묶음)·9.3~9.5(마일스톤·운영 규칙)·9.6·9.9·9.10. 다른 장은 grep으로 필요한 절만 확인했다(02 2.0·AC-02-30·D-0214, 04 4.4·4.10~4.12·AC-04-43, 06 오류 코드·6.11.4·6.15).
- 기준: `rubric.md`, `decisions_v2.md`(R-01~R-38), 1라운드 `r1_qa.md`(QA-01~27)
- 핵심 질문: AI 에이전트가 이 기획서대로 구현했을 때, 기준치만큼 결과가 나왔는지 **기계적으로** 판정할 수 있는가?
- 규칙: 1라운드에서 해결된 항목은 다시 쓰지 않는다. 다른 역할의 2라운드 리뷰(PM2·UX2)와 겹치는 항목(예: 07장이 00장의 G0~G4·P0-α/β를 참조하는 문제 → PM2)도 다시 쓰지 않는다.

## 총평

07장은 1라운드 QA 지적 27건을 거의 모두 반영했다. 테스트 3계층, 골든 세트 32케이스와 지표 M1~M15·합격선·회귀 허용폭, TC 카탈로그 9종, 성능·호환성·접근성 기준, 사람 블라인드 평가, 출시 게이트 G1~G7, 잠금·guard까지 있다. 지금 상태로도 **판정 장치의 설계**는 대기업 QA 게이트 수준이다.

남은 문제는 그 장치가 **실제로 한 가지 답을 내는가**다. 네 가지가 걸린다.

1. **임계값 파일의 키 구조가 장마다 다르다.** 같은 "조화 하한 80"이 09장 `harmonyMin`, 04장 `generation.harmony_floor`, 07장 `release.golden.harmonyFloor` 세 곳에 서로 다른 이름으로 있다. "코드는 `getThresholds()`로만 읽는다"는 원칙이 있어도, 어느 키를 읽는지가 정해지지 않았다.
2. **`temp`·`needs_live`·`needs_ci` 같은 "판정 보류" 상태를 어떤 단계가 언제 쓸 수 있는지 열려 있다.** 그래서 실패한 단계를 `temp`로 표시해 verify를 통과시킬 수 있다. 또 staging이 필요한 항목은 어느 보류 상태에도 속하지 않아, 에이전트 완료 조건(`release:check` 종료 코드 0 또는 2)에 영원히 도달하지 못한다.
3. **사람이 없을 때 기준 파일의 출처가 순환한다.** 이 저장소는 사람 없이 P3~P4를 진행한다(CLAUDE.md). 그러면 `thresholds.json`, 수용 테스트, verify 스크립트를 모두 에이전트가 쓰고, 에이전트가 스스로 잠근다. 스펙 문서와 기계적으로 대조하는 단계가 없다.
4. **07·09·04장 사이 수치와 수량이 어긋난다.** 추출기 왕복 0.10 vs 0.15, 폴백 조합 72 vs 24, 골든 32 vs 30, `low_score` 상태 `fallback` vs `partial` 등이다. 수용 테스트는 작성 직후 자체 잠금되므로, 잘못된 쪽으로 쓰인 테스트는 사람 없이 되돌릴 수 없다.

네 건 모두 문서와 스크립트 1~2개만 고치면 해결된다. 1인 개발 범위 안이다.

### QA2-01 · Major · `config/thresholds.json` 키 구조가 장마다 달라 "단일 원천"이 성립하지 않음

- **관련 절**: 07 P-1·7.12.1(`release.*`, camelCase), 09 9.5.6(평면 키 `harmonyMin`·`tasteMin`·`genP95Sec`…), 04 4.0 ④·4.10.3·4.12·AC-04-43(`generation.*`, snake_case, `golden.full_success_min`), 02 2.0·D-0214(평면 키 + `diagnosis` 객체), 09 M3 ②(`thresholds.harmonyMin`), 09 M4 ④(`diagnosis`·`release.surveySim`)
- **허점**: 같은 수치가 서로 다른 키로 여러 번 정의되어 있다.

  | 의미 | 09장 | 04장 | 07장 |
  |---|---|---|---|
  | 조화 하한 80 | `harmonyMin` | `generation.harmony_floor` | `release.golden.harmonyFloor` |
  | TM 하한 75 | `tasteMin` | `generation.taste_floor` | `release.golden.tasteFloor` |
  | p95 90초 | `genP95Sec` | `generation.job_p95_s` | `release.golden.latencyP95Sec` |
  | 편집 반영 p95 | — | `generation.edit_style_p95_ms` | `release.perf.editStyleP95Ms` |
  | 완전 성공률 | — | `golden.full_success_min` | `release.golden.fullSuccessMin` |

- **이유**: 판정 코드는 `getThresholds()`로만 읽어야 하고(07 P-1), guard는 "런타임 값 = 스펙 표 값"을 확인한다(7.12.2 ④). 그런데 키가 여러 개면 에이전트가 키 구조를 직접 정해야 한다(C2). 같은 값이 두 키에 있으면 한쪽만 바뀌는 드리프트도 생긴다. 즉 "단일 원천"이 이름뿐이다.
- **보완안**:
  1. 키 구조를 07 7.12.1 한 곳에서 **완전한 JSON**으로 정한다. 권장 구조는 다음과 같다. 최상위 객체는 `diagnosis`(02), `generation`(04), `perf`(06·07 런타임 SLO), `release`(07 출시 전용). 키는 camelCase로 통일한다. 평면 키는 폐지한다.
  2. 같은 의미의 값은 한 키에만 둔다. 출시 지표가 운영 하한과 같은 값이면 `release.golden.harmonyFloor` 대신 `generation.harmonyFloor`를 참조하고, 출시 전용 값(평균 ≥85 등)만 `release`에 둔다.
  3. 04 AC-04-43, 02 D-0214, 09 9.5.6, 09 M3·M4의 키 이름을 이 구조로 바꾸고, 각 장 본문은 "키 경로 → 07 7.12.1"로만 참조한다.
  4. `decisions_v3.md`에 R-39로 기록한다.
- **수용 기준**:
  - 07 7.12.1에 `config/thresholds.json`의 전체 JSON이 1개 블록으로 있다.
  - `rg -n 'thresholds\.json' docs/spec/v2`로 나오는 모든 키 경로가 그 블록에 존재한다(불일치 0).
  - 같은 숫자·같은 의미를 가진 키가 2개 이상 없다.
  - `scripts/guard/thresholds-schema.ts`가 zod 스키마로 파일을 검증한다. 알 수 없는 키나 빠진 키가 있으면 FAIL한다.

### QA2-02 · Major · 판정 보류 상태(`temp`·`needs_live`·`needs_ci`·staging)를 쓰는 규칙이 열려 있음

- **관련 절**: 09 9.4.1(`steps[].status: 'temp'`는 verify 통과로 간주), 09 9.9.1(종료 코드 2의 조건), 07 7.1.5·7.11.2·7.12.2 ②(`needs_ci`), 07 7.5.1 진단 API k6 "staging", 09 F17(원격 배포 금지), 09 9.9.2(완료 = 종료 코드 0 또는 2)
- **허점**:
  1. 어떤 verify 단계가 `temp`를 반환해도 되는지 목록이 없다. 명시된 예는 B6 폰트 용량 하나뿐이다. verify 스크립트는 에이전트가 M0에서 직접 쓰므로, 실패하는 단계를 `temp`로 표시하면 verify가 통과한다.
  2. `needs_ci`(07 7.12.2)는 `release-check.json`의 상태 enum(`pass|fail|temp|manual|needs_live`)에 없다.
  3. 7.5.1 진단 API k6는 staging에서 측정한다. 그런데 에이전트는 원격 배포를 하지 못한다(F17). 이 항목은 `temp`·`manual`·`needs_live` 어디에도 속하지 않는다. 그래서 G3가 `fail`이 되고, 종료 코드 1이 되어, 에이전트 완료 조건을 영원히 충족하지 못한다. 반대로 에이전트가 임의로 `manual`로 분류할 수도 있다.
- **이유**: "판정 불가"를 "판정 통과"로 바꾸는 경로가 열려 있으면 기계적 판정이 성립하지 않는다. 이것이 1라운드 QA-06이 막으려던 "스스로 통과시키기"의 남은 경로다.
- **보완안**:
  1. 07장에 "보류 상태 허용표"를 둔다(`config/test-policy.json`의 `deferrable` 객체, 사람 잠금). 열은 단계 ID, 허용 상태, 조건(예: 관련 묶음의 `provenance=temp`이거나 `LLM_MODE≠live`)이다. 예시는 아래와 같다.

     | 단계 | 허용 상태 | 조건 |
     |---|---|---|
     | `font-budget` | temp | B6 `provenance=temp` |
     | `extractor-human-label` | temp | B13 `provenance=temp` |
     | `golden-live` · `blind-*` | needs_live / manual | 평가 키 없음 / 사람 평가 |
     | `lock-digest` | needs_ci | `QA_LOCK_DIGEST` 미설정(로컬) |
     | `k6-diagnosis-api` | 로컬 스택에서 측정하면 pass/fail. staging 재측정은 manual | — |

  2. 이 표에 없는 단계가 보류 상태를 반환하면 `release:check`와 verify가 `fail`로 처리한다. 조건이 맞지 않는데 보류 상태를 반환해도 `fail`이다(예: B6가 human인데 `font-budget=temp`).
  3. 상태 enum에 `needs_ci`를 추가한다. 종료 코드 2의 조건에 `needs_ci`를 포함한다.
  4. 7.5.1 진단 API는 "MVP 자동 판정 = 로컬 docker 스택, k6 10 VU 5분. staging 재측정은 `release/manual-checklist.md`"로 고친다.
- **수용 기준**:
  - 보류 허용표가 07장과 `config/test-policy.json`에 있고 서로 같다.
  - 메타 테스트: 허용표에 없는 단계가 `temp`를 반환하면 `release:check` 종료 코드는 1이다. 조건이 맞지 않는 `temp`도 종료 코드 1이다.
  - `release-check.json`의 상태 enum이 07 7.1.5·7.11.2·09 9.9.1에서 같다.
  - 클린 클론과 키 없는 환경에서 `release:check`가 종료 코드 2를 낼 수 있다. 즉 남은 보류 사유가 전부 허용표 안에 있다(AC-09-01의 연장).

### QA2-03 · Major · 사람이 없을 때 기준 파일(임계값·수용 테스트·verify)의 출처가 순환함

- **관련 절**: 09 9.5.6(사람 잠금 = 사람이 구현 전에 커밋하고 `human-lock` 태그), 07 7.12.1~7.12.3, 09 9.5.1 ②(수용 테스트를 에이전트가 쓰고 자체 잠금), 저장소 CLAUDE.md(P3·P4는 사람 없이 진행)
- **허점**: 09·07장은 `config/thresholds.json`, `test-policy.json`, `human-lock` 태그, `QA_LOCK_DIGEST`를 사람이 만든다고 가정한다. 하지만 이 프로젝트의 실제 운영(CLAUDE.md)에는 사람이 없다. 그러면 다음 일이 생긴다.
  - 임계값 파일을 에이전트가 쓰고 에이전트가 잠근다.
  - "런타임 값 = 스펙 표 값" 확인(7.12.2 ④)도 에이전트가 쓴 수용 테스트가 한다.
  - `QA_LOCK_DIGEST`는 영원히 `needs_ci`다.

  결과적으로 기준을 만드는 쪽과 판정받는 쪽이 같다. 스펙 문서가 유일한 고정점인데, 스펙과 기계적으로 대조하는 단계가 없다.
- **이유**: 핵심 질문("기준치만큼 나왔는가")의 기준치가 구현자 손에서 만들어지면 판정이 순환한다. 7.12의 잠금은 "잠근 뒤의 변경"만 막고, "처음부터 틀리게 만든 것"은 막지 못한다.
- **보완안**(1인·무인 운영에 맞게, 사람 절차는 그대로 둔다):
  1. **스펙에서 추출하기**: `pnpm spec:extract`를 둔다. 이 스크립트는 07 7.12.1의 JSON 블록(QA2-01로 단일화)을 그대로 파싱해 `config/thresholds.json`을 만든다. guard는 이렇게 확인한다: 현재 `config/thresholds.json` 바이트 = `spec:extract` 출력. 스펙 문서(`docs/spec/**`)는 P3 확정 후 잠금 대상이므로, 고정점이 문서 하나로 모인다.
  2. **사람 없는 잠금 모드**: `human-lock` 태그가 없으면 P3 종료 커밋(`docs/spec/FINAL` 확정)에 `spec-lock` 태그를 만든다. guard:lock 규칙 ②의 기준 ref를 `human-lock ?? spec-lock`으로 정한다. `QA_LOCK_DIGEST`가 없으면 `needs_ci`가 되고(QA2-02), 이 상태는 출시(종료 코드 0)를 막는다.
  3. **수용 테스트 표본 감사**: 수용 테스트를 자체 잠그기 전에 `qa:trace --audit`를 실행한다. 이 명령은 테스트 본문이 스펙 AC 문장의 수치를 직접 쓰지 않고 `getThresholds()` 키를 쓰는지 정적 검사한다(QA2-07과 같은 규칙).

### QA2-05 · Minor · 골든 응답 로그 생성 시 기대값 자기 검증이 없음
