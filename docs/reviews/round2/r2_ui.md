# R2 리뷰: 시니어 UI 디자이너 관점

- 대상: `docs/spec/v2/03_design_system.md` 중심(3.1 토큰, 3.4 프리셋·타입 스케일, 3.5 컴포넌트, 3.6 블록, 3.7~3.8 서체·조판, 3.9 아이콘, 3.11 반응형, 3.12 다크, 3.13 브랜드 컬러, 3.14 조화 점수). 다른 장은 UI 관련 절만 grep으로 확인했다: 01 1.3.1·1.8.5·1.13·1.14, 04 §4.2.2·CM-06~11·§4.10.2(G-01~12)·§4.10.3(H7)·§4.16(E-01~13)·카피 덱 길이, 06 6.6.1, 07 7.1.2(시각 회귀)·7.x 브라우저/뷰포트 표, 09 D-0910·`registry` 타입.
- 기준: `rubric.md`, `decisions_v2.md`(R-01~R-38), 1라운드 `r1_ui.md`(UI-01~24)
- 규칙: 1라운드에서 해결된 항목은 다시 쓰지 않는다. 다른 2라운드 리뷰(PM·UX·QA·테크)에 이미 있는 항목(자극물 표시 크기 UX2-02, 확대 시 편집 상실 UX2-03, Docker 의존 시각 회귀·브라우저 매트릭스 TL2-01·02, 임계값 키 구조 QA2-01 등)은 다시 적지 않는다. 수치 주장은 직접 계산해 검증했다(대비는 WCAG 2.x 상대 휘도, 색 변환은 OKLab 표준 행렬). 1인 개발 맥락이므로 보완안은 문서 수정 또는 작은 구현 규칙으로 제한한다.

## 총평

v2의 03장은 1라운드 UI 지적 24건을 거의 모두 반영했다. DTCG 호환 TokenSet 스키마, 색 역할별 하드 대비 조건, 4pt 간격·radius family·depth 5종 수치, 프리셋 8종의 L2 기본값·허용 집합·타입 스케일 실측표, 컴포넌트 18종 variant×state 매트릭스, 블록 20종 50 variant와 모바일 변환, OFL 서체 26종·페어링 20쌍, 한글 조판(자간·행간·줄바꿈) 수치, 아이콘 3세트 40의미 매핑, 이미지 팩 사양, 조화 점수 H1~H12가 모두 수용 기준과 함께 있다. 서비스 UI도 01장 1.13에 `--svc-*` 토큰과 서비스 전용 린터(SVC-L)가 생겼다. 서비스 토큰 대비 표기값 15쌍을 다시 계산해 보니 모두 맞았다(예: `--svc-border-strong` 대 stage 3.09:1). 대기업 디자인 시스템 리뷰에 올릴 수 있는 밀도다.

남은 문제는 "규칙끼리는 각각 맞지만, 함께 돌리면 성립하지 않는" 지점 네 군데다.
1. **브랜드 컬러 보정 알고리즘이 밝은 색에서 해를 찾지 못한다.** 노랑 `#FFFF00`은 03장 AC-03-36 픽스처에 명시돼 있는데, L 이동 상한 ±0.25 안에서는 대비 조건을 만족하는 값이 없다. 실패했을 때 어떻게 할지도 정의되어 있지 않다.
2. **텍스트 역할 → 타입 단계 매핑이 없고, H7(display/body 비)의 정의가 03·04장에서 다르다.** 04장 정의를 따르면 T3 표준 트리가 H = 100을 낼 수 없어 AC-03-20이 성립하지 않는다.
3. **헤드라인 카피 길이 상한(8~24자)이 타입 스케일·컬럼 폭과 맞지 않는다.** T5·T8 split hero에서는 "1280에서 ≤ 2줄"을 지킬 수 있는 글자 수가 10자 안팎이다. 넘쳤을 때 결정론적으로 처리하는 규칙도 없다.
4. **편집 미리보기와 내보내기 코드의 폰트 서브셋 전략이 없다.** 페이지 서브셋을 글자 집합 해시로 만드는 구조라서, 편집기에서 텍스트를 바꿀 때마다 새 폰트 파일 요청과 FOUT가 생긴다. 서브셋 enum도 03장과 09장이 다르다.

### UI2-01 · Major · 브랜드 컬러 보정이 밝은 색에서 해를 찾지 못하고, 실패 경로가 없음

- **관련 절**: 03 3.13.2(의사코드), AC-03-36 / 04 §4.2.2 표("L을 0.01 단위로 이동(최대 ±0.25), 이후 C를 0.01 단위로 감소"), AC-04-03 / 01 1.5.5.3 `brand_color_notice`
- **허점**: 보정 루프는 `contrast(on, p) ≥ 4.5`와 `contrast(p, bg) ≥ 3.0`을 동시에 만족할 때까지 L을 최대 ±0.25 옮기고, 그다음 C를 낮춘다. 그런데 OKLCH에서 C를 낮춰도 상대 휘도는 거의 그대로이므로, 루프가 실제로 쓸 수 있는 것은 L 이동뿐이다. 라이트 bg(L ≈ 0.97, Y ≈ 0.91)에서 `p` 대 bg 3:1을 만족하려면 Y(p) ≤ 0.277, 대략 OKLCH L ≤ 0.65여야 한다. 따라서 시작 L이 약 0.90을 넘는 색은 ±0.25 안에서 해가 없다. 직접 계산한 결과는 다음과 같다(bg L 0.97, on = 흰색 또는 L 0.15 중 유리한 쪽, C를 0까지 낮추는 경우 포함).

| 입력 | OKLCH L·C·H | ±0.25 안에서 해 |
|---|---|---|
| `#FFFF00`(AC-03-36 픽스처에 명시) | 0.968 · 0.211 · 110 | **없음** |
| `#FDFD96`(파스텔 노랑) | 0.972 · 0.126 · 109 | **없음** |
| `#AAF0D1`(민트) | 0.900 · 0.082 · 165 | **없음** |
| `#FFD1DC`(파스텔 핑크) | 0.903 · 0.053 · 2 | 있음 |
| `#39FF14`(형광 연두) | 0.871 · 0.286 · 142 | 있음 |

  루프가 상한에 닿았을 때의 동작은 3.13.2와 04 §4.2.2 어디에도 없다. 무한 루프, 예외, 대비 미달 primary 채택 중 무엇이 될지 구현에 달렸다. 대비 미달 primary는 G-02·G-03에서 걸려 후보 전체가 폐기된다. `brand_color_notice` enum(`adjusted` / `demoted_to_accent`)에는 "적용하지 못함" 값도 없다. 강등 조건(hue 차 ≥ 60° ∧ VIVID_FORBIDDEN ∧ C > 0.15)은 보정 가능 여부와 관계가 없어서, 노랑은 T5·T6에서는 강등되지도 않는다.
- **왜 문제인가**: 국내 카페·베이커리·꽃집(local_business)의 브랜드 색은 파스텔·노랑이 흔하다. 이 입력은 "생성 실패" 또는 "3개 시안 모두 폐기 → 폴백"으로 이어질 수 있고, 사용자는 이유를 모른다. AC-03-36·AC-04-03은 `#FFFF00`을 포함해 100% 통과를 요구하므로 현재 규칙으로는 테스트를 통과할 수 없다. 에이전트는 실패 처리와 사용자 고지를 직접 정해야 한다(C2).
- **보완안 [MVP]**:
  1. 3.13.2에 **사전 가능성 판정**을 추가한다. 시작 L에서 ±0.25 안에 해가 있는지(단조 탐색이므로 L 경계 2점만 확인하면 된다) 먼저 본다. 해가 없으면 다음 순서로 처리한다. (a) accent 경로를 시도한다. accent는 텍스트 배경이 아니라 괘선·라벨·아이콘에만 쓰므로 `color.accent` 대 bg 비텍스트 3:1만 요구하고, `on-accent`가 필요한 쓰임(배지 채움)은 금지한다. (b) accent로도 안 되면 브랜드 색을 **장식 면 전용**으로 쓴다. `surface` 틴트(hue = h_b, C ≤ 0.035, 3.1.3 bg 조건 안) 또는 shape-graphic 색면 1개에만 적용한다.
  2. `brand_color_notice` enum에 `used_as_tint`("브랜드 컬러가 너무 밝아서 배경 색조로 반영했어요")와 `ignored`("이 색은 글자와 함께 쓰기 어려워 반영하지 못했어요")를 추가한다(01 1.5.5.3, 06 `MockupCard`, 04 DesignSpec `brand_color.notice`). 문구는 01장 카피 표에 넣는다.
  3. 루프 상한 도달은 예외가 아니라 위 분기로 끝나도록 의사코드를 바꾼다(반복 횟수 상한 25 + 10 + 색역 보정 ≤ 74를 주석으로 명시).
- **수용 기준**:
  - AC-03-36 픽스처에 `#FFFF00`, `#FDFD96`, `#AAF0D1`, `#FFF5CC`가 들어가고, 160건 이상 모두 (a) primary 적용 + 하드 대비 통과, (b) accent 강등, (c) `used_as_tint`, (d) `ignored` 중 하나로 **종료**한다. 예외·타임아웃 0건, 하드 대비 위반 0건.
  - 각 결과의 `brand_color_notice`가 위 4값(+null) 중 하나이고, S08 카드에 해당 카피 키 문구가 보인다(E2E 1케이스: `#FFFF00` + T3).
  - 1회 `applyBrandColor` 호출 ≤ 5ms(단위 테스트, 편집기 후보 카드 4장 동시 적용 대비).

### UI2-02 · Major · 텍스트 역할→타입 단계 매핑 부재와 H7 정의 충돌로 표준 트리 H = 100 불성립

- **관련 절**: 03 3.1.5("display/body 비 = display(1280)/base, 2.5~8.0(04장 H7)"), 3.4.6 D/B 열, 3.14.3 H7 "display/body 비(1280)", AC-03-04, AC-03-20 / 04 §4.10.3 H7 "1280에서 **h1** font-size / body font-size", CM-06("h1은 hero에 정확히 1개, 섹션 제목은 h2"), 3.6.1 cta.big-type "display 단계 제목", SIG-11 "hero(display 단계 1줄만)"
- **허점**:
  - **역할 → 단계 표가 없다.** 3.1.5는 단계 9개(caption~display)의 크기만 정한다. hero.headline이 h1 단계인지 display 단계인지, 섹션 제목·카드 제목·Stat 값·PriceTag·인용문·eyebrow·footer big-type이 각각 어느 단계인지는 어디에도 없다. 게다가 CM-06의 시맨틱 수준(`<h1>`·`<h2>`)과 타입 단계 이름(h1·h2)이 같은 이름을 쓰면서 서로 다르게 움직인다. cta.big-type은 `<h2>`이지만 display 단계이고, hero.type-only의 `<h1>`은 "거대 타이포"다. 그래서 에이전트는 블록 템플릿 50개마다 단계를 직접 고르게 되고, H6("모든 font-size ∈ 토큰 단계")은 통과해도 시안마다 위계가 들쭉날쭉해진다.
  - **H7 분자가 두 장에서 다르다.** 03장은 display, 04장은 h1이다. 04장 정의로 3.4.6 값을 계산하면 **T3 기본값이 h1 42px / body 17px = 2.47로 2.5 미만**이어서 H7 = 0이 된다. 그러면 표준 트리 최대 H = 92가 되고, "24개 트리 모두 H = 100"이라는 AC-03-20·AC-03-39와 AC-03-38(03·04 표 생성 비교 차이 0건)이 동시에 깨진다. 허용 집합 안의 다른 조합(T4 body 17 + ratio 1.2 + boost 1.0 → h1 42 / 17 = 2.47)도 04장 정의에서만 0점이다.
- **왜 문제인가**: 타입 위계는 시안 품질을 사람이 가장 먼저 판단하는 요소다. 단계 배정이 템플릿 작성자(에이전트) 재량이면 같은 프리셋 안에서도 블록마다 제목 크기가 달라진다. H7 충돌은 "표준 트리 = 100점 기준선"이라는 조화 점수의 영점 자체를 흔들고, 어느 장을 고쳐야 하는지도 분명하지 않다(C2).
- **보완안 [MVP]**:
  1. 03장에 **3.1.5a 텍스트 역할 표**(`data/taxonomy/text-roles.json`)를 추가한다. 키는 `role → {step_desktop, step_mobile, weight: heading|body|emphasis, leading, tracking_class, element}`이다. 최소 역할은 `hero.headline`(hero.type-only·full-bleed-image = display, 그 외 hero variant = h1), `section.title`(h2), `card.title`(h4), `item.title`(h4), `lead`, `body`, `caption`, `eyebrow`(small + 라벨 자간), `stat.value`(h2, tabular), `price`(h3), `quote`(h3), `cta.headline`(band = h2 단계, big-type = display), `footer.wordmark`(big-type = display), `nav.wordmark`(20~24px 고정)이다. 블록 템플릿은 font-size를 직접 쓰지 않고 `data-role`만 지정한다.
  2. 시맨틱 수준과 타입 단계의 이름을 분리한다. 단계 이름을 `t-display / t-1 / t-2 …`처럼 바꾸거나, 문서에 "단계 이름은 시맨틱 수준과 무관"이라는 문장을 넣는다.
  3. H7은 **03장 정의(display 단계 계산값 / base, 1280)**로 통일한다. 04 §4.10.3 H7 문장을 고치고, `harmony.json`이 원천이라는 D-0310에 따라 04장 표는 생성본으로 바꾼다. 렌더 측정에서 display 단계가 페이지에 없으면 토큰 계산값으로 판정한다(측정값이 아니라 토큰 기준이어서 결정론적이다).
- **수용 기준**:
  - `text-roles.json`의 zod 검증이 통과하고, 50 variant 템플릿의 모든 텍스트 노드에 `data-role`이 있다(렌더 DOM 검사, 누락 0).
  - 같은 프리셋에서 같은 role의 computed font-size 고유값이 뷰포트당 1종이다(골든 세트 렌더 검사).
  - 04장 H7 문구가 "display(1280) / base"이고 `harmony.json`과의 생성 비교 차이가 0건이다(AC-03-38).
  - AC-03-20 24개 표준 트리가 H = 100이다(T3 포함).

### UI2-03 · Major · 헤드라인 길이 상한이 타입 스케일·컬럼 폭과 맞지 않고, 넘칠 때의 결정론적 처리가 없음

- **관련 절**: 04 카피 덱 `hero.headline` 8–24자, §4.11.1 G-04/G-05 보정(짧은 덱 옵션 교체) / 03 3.4.6(타입 스케일), 3.8.1 "헤드라인 줄 수: 1280에서 ≤ 2줄, 375에서 ≤ 3줄(초과 시 덱 옵션 교체, 실패 시 warn)", AC-03-26(375px 4줄 이상 헤드라인 0건), 3.11.1(그리드), 3.6.1 hero variant
- **허점**: 한 줄에 들어가는 한글 글자 수 = 텍스트 영역 폭 ÷ (글자 크기 × 약 0.95em, 3.8.2 자간 반영)이다. 여기에 `keep-all` 줄바꿈 손실(줄당 평균 1~2자)을 고려해 계산하면 다음과 같다.

| 상황 | 글자 크기 | 텍스트 폭 | 줄당 글자 | 허용 줄 수 안의 최대 글자(공백 포함, 근사) | 덱 상한 |
|---|---|---|---|---|---|
| T5·T8 hero.split, 1280(6/12열) | display 128 / h1 96 | 약 624px | 5 / 7 | 약 10 / 14 (2줄) | 24 |
| T1·T4 hero.split, 1280 | h1 67 / 65 | 약 600px | 9 | 약 18 (2줄) | 24 |
| 모바일 375(T4~T8) | display 52 / h1 44 | 335px | 6 / 7~8 | 약 17 / 21 (3줄) | 24 |

  덱 옵션 3개가 모두 상한 근처면, "짧은 옵션으로 교체" 보정을 해도 줄 수 조건을 지킬 수 없다. 이때 3.8.1은 warn으로 끝나지만 AC-03-26은 0건을 요구해서 서로 어긋난다. 슬롯 `maxLength`(= 덱 상한)도 variant·프리셋과 관계없이 하나라서, 시각 조건에서 거꾸로 길이를 정하는 경로가 없다. 덱이 생성되는 시점(04 §4.6)에는 프리셋과 hero variant가 이미 정해져 있으므로 미리 계산할 수 있는데도 그렇게 하지 않는다.
- **왜 문제인가**: hero 헤드라인은 첫 화면의 인상을 결정한다. 거대 타이포가 개성인 T5·T8(포스터·럭셔리)에서 오히려 줄 수 위반, 단어 중간 줄바꿈(`overflow-wrap: anywhere` 발동), 고아 글자가 가장 자주 생긴다. 에이전트는 글자 크기를 줄일지, 카피를 자를지, 위반을 무시할지 직접 정해야 한다(C2). 대기업 디자인 QA에서 "헤드라인이 4~5줄로 깨진 시안"은 바로 반려 사유다(C3).
- **보완안 [MVP]**:
  1. **줄 예산 함수** `headlineBudget(presetTokens, variant, viewport) → maxChars`를 03장에 정의한다. 식은 `floor(textWidth / (size × 0.95)) × maxLines × 0.85`(0.85 = keep-all 손실 계수, 골든 세트로 보정)이고, 텍스트 폭은 variant 메타(`text_cols`: split 6/12, type-only 10/12, centered 8/12 등)를 `blocks.json`에 추가해 계산한다. 1280과 375 중 작은 값을 쓴다.
  2. 04 §4.6 카피 덱 생성 프롬프트에 `hero.headline` 3옵션 중 **최소 1개는 `maxChars` 이하**여야 한다는 제약을 넣고, 덱 zod 검증(G-01)에서 검사한다.
  3. 렌더 측정에서 줄 수를 넘으면 결정론적 순서로 처리한다. ① 짧은 덱 옵션으로 교체 → ② 해당 role의 단계를 한 단계 내린다(display → h1 → h2, 최대 1회, H6 위반 아님) → ③ 그래도 넘치면 warn. 이 순서를 3.8.1에 적고 AC-03-26을 "① 또는 ②로 해소율 100%, ③ 발생 0건(골든 세트)"으로 바꾼다.
- **수용 기준**:
  - 프리셋 8 × hero variant 6 × {1280, 375}의 `maxChars` 표가 `blocks.json` 빌드 산출물로 생성된다(스냅숏 테스트).
  - 골든 32케이스 렌더에서 hero 헤드라인 줄 수 1280 ≤ 2, 375 ≤ 3이 100%이고, 단어 중간 줄바꿈(한글 어절 내부 분리) 0건이다(Range API로 줄별 텍스트를 추출하고 공백 경계를 검사).
  - 단계 강등이 일어난 시안은 `spec.render_adjustments[]`에 기록되고, 그 비율이 골든 세트에서 ≤ 25%다(넘으면 덱 프롬프트 조정 신호).

### UI2-04 · Major · 편집 미리보기·내보내기 코드의 폰트 서브셋 전략이 없음(서브셋 enum도 03·09장 불일치)

- **관련 절**: 03 3.7.4("폼 입력… 서브셋 밖 글자는 `tf-fb-*`로 표시(허용)"), 3.7.5("페이지 서브셋… 미리보기·내보내기 동일", "편집 후: 다음 컴파일에서 서브셋을 다시 만든다"), AC-03-23(시스템 폴백 0건) / 01 1.8.5(편집 미리보기: 조작마다 브라우저에서 HTML 전체를 다시 컴파일해 `srcdoc` 교체, 반영 p95 ≤ 200/500ms, 측정용 iframe으로 `slotRects` 계산) / 06 6.6.1(URL에 `sha256(fontFileSha + cs)`와 `?cs=` 포함, Route Handler가 hb-subset으로 생성) / 09 `registry` 타입 `subset: 'full'|'ks-x-1001'|'latin'`(03장은 `'full'|'latin'|'page'`)
- **허점**:
  - 편집기에서 텍스트 슬롯을 한 글자 바꾸면 글자 집합 `cs`가 바뀌고, 그러면 폰트 URL이 바뀐다. 따라서 텍스트 편집 1회마다 heading·body 2~5개 폰트 파일을 새로 요청하게 되고, 서버는 hb-subset을 새로 실행한다(CDN 캐시 미스). 서체 조합 후보 카드(최대 4개)를 미리 보여 줄 때도 후보마다 같은 일이 생긴다. 그사이 `font-display: swap`으로 폴백이 보였다가 바뀌므로 매 조작마다 FOUT가 깜빡이고 줄바꿈이 다시 일어난다. 이는 01 1.8.5가 더블 버퍼로 막으려던 깜빡임을 폰트가 다시 만드는 셈이다. 측정용 iframe은 폰트가 로드되기 전에 `slotRects`를 잴 수 있어 오버레이 위치가 어긋난다. 반영 p95 ≤ 500ms에 폰트 요청이 포함되는지도 정의되어 있지 않다.
  - 내보내기 zip에는 그 시점 카피의 페이지 서브셋만 들어간다. 사용자가 받은 React/HTML 코드에서 문구를 바꾸면 새 글자는 모두 시스템 폴백으로 바뀌는데, README에도 경고가 없다(E-01~E-13에 해당 검사 없음).
  - 03장과 09장의 서브셋 enum이 달라서 `registry.json` zod 스키마를 어느 쪽으로 만들지 정해지지 않았다.
- **왜 문제인가**: 편집은 이 서비스의 두 번째 aha 지점이고, 텍스트를 고칠 때마다 서체가 깜빡이면 "편집기가 싸 보인다"는 인상이 즉시 생긴다. 내보낸 코드에서 폰트가 소리 없이 깨지는 것은 개발자 사용자에게 품질 결함으로 보인다. 에이전트는 편집기 폰트 공급 방식(전체 파일, KS X 1001 서브셋, 매번 페이지 서브셋)을 직접 정해야 한다(C2).
- **보완안 [MVP]**:
  1. **맥락별 서브셋 규칙**을 3.7.5에 표로 정한다.
     - 생성 렌더·공유·결과 미리보기: 지금처럼 `page` 서브셋을 쓴다.
     - **편집 미리보기(S09)와 후보 카드**: 패밀리·웨이트별 **`ks-x-1001` 정적 서브셋**(완성형 2,350자 + ASCII + 문장부호, 빌드 시 1회 생성, 해시 파일명 immutable)을 쓰고, 그 뒤에 `unicode-range`로 나눈 `page` 보충 파일 1개를 둔다. 서브셋 밖 글자(예: "똠", "햏")만 보충 파일로 처리하고, 보충 파일은 디바운스 1초 뒤 갱신한다.
     - **내보내기**: `page` 서브셋을 기본으로 하고 `fonts/extended/`에 `ks-x-1001` 파일을 함께 넣는다. 두 번째 `@font-face`를 `unicode-range: U+AC00-D7A3`로 선언해 카피를 바꿔도 2,350자 안에서는 같은 서체가 유지되게 한다. README "문구를 바꿀 때" 절에 안내를 넣는다. zip ≤ 15MB(E-13) 안에 들어간다(한글 OFL 서체 KS X 1001 woff2는 웨이트당 수백 KB).
  2. registry `subset` enum을 `'full'|'ks-x-1001'|'latin'|'page'`로 통일한다(03·09).
  3. 01 1.8.5에 "측정용 iframe은 `document.fonts.ready` 이후 `slotRects`를 계산한다"와 "반영 시간에서 폰트 첫 로드는 제외하고, 같은 서체 재사용 시에는 포함한다"를 명시한다.
- **수용 기준**:
  - S09에서 텍스트 슬롯을 10회 연속 편집할 때 새 폰트 네트워크 요청이 0건이다(서브셋 밖 글자를 넣지 않는 경우, Playwright 네트워크 로그).
  - 같은 시나리오에서 표시 iframe의 한글 텍스트 노드 사용 폰트가 매 프레임 지정 서체다(CDP `getPlatformFontsForNode`로 샘플 5회 측정해 폴백 0).
  - 내보낸 HTML의 hero 헤드라인을 KS X 1001 범위의 다른 문장으로 바꿔 렌더해도 폴백이 0건이다(E-14 신설, 야간 CI 골든 5케이스).
  - `registry.json` 스키마 enum이 03장과 09장에서 같다(정적 검사).

### UI2-05 · Minor · 렌더러 시각 회귀 범위가 03장과 07장에서 다르고 모바일이 빠짐

- **관련 절**: 03 3.5.2 "시각 회귀 대상은 이 케이스(18종 × variant × state) × 프리셋 8" / 07 7.1.2 "렌더러: 프리셋 8 × 대표 페이지 3 = 24장(1280×800)", AC-07-12 / 09 D-0910

- **수용 기준**: AC-07-12의 장 수와 03 3.5.2의 서술이 같다. 375 스냅숏에서 3.11.3 변환 규칙 위반(예: hero.offset 보조 이미지 노출)을 넣은 픽스처가 시각 회귀로 실패한다.

### UI2-06 · Minor · 브랜드 컬러 개수·워드마크 서체·파비콘 규칙이 장마다 다름

- **관련 절**: 03 3.13.1 "최대 2개", 3.13.3 "두 번째 색 → accent" / 01 1.5.5.2 `brandColor?: string // 선택, 1개(04장·R-21)` / 04 §4.2.2 "hex 1개"
  · 03 3.5.1 C18 Wordmark "`font.heading`으로 조판", 3.13.4 "가짜 심볼·이니셜 마크 생성 금지" / 04 §4.2.2 "브랜드명을 `font.display`로 조판한 워드마크"(TokenSet에 `font.display` 토큰 없음), E-10 "favicon(워드마크 이니셜 SVG)"
- **허점·보완**: R-21에 따라 03장의 2색 처리는 쓸 일이 없는 경로가 된다. 3.13.1을 "1개(R-21). 2색 입력은 [P2]"로 고치고, 3.13.3은 "강등된 색 → accent"만 남긴다. 워드마크 서체는 `font.heading`으로 통일한다(04장 문장 수정). 파비콘은 3.13.4의 "이니셜 마크 금지"와 충돌하므로, 파비콘 = "`color.primary` 정사각형 + 브랜드명 첫 글자 `font.heading` 텍스트 SVG"를 **허용 예외**로 3.13.4에 적거나, 파비콘을 빈 색면(primary 단색 정사각형)으로 바꾼다. 어느 쪽이든 서체 subset에 그 글자를 포함한다.
- **수용 기준**: 세 규칙이 03·04장에서 문자열로 일치한다(grep). E-10 검사가 3.13.4 규칙을 위반하지 않는다.

### UI2-07 · Minor · T7 glass를 쓸 수 없는 위치의 카드 스타일과 glass 위 대비 측정법이 미정

- **관련 절**: 03 3.1.8("glass는 아래에 이미지·색면이 있는 요소에만 적용", "한 시안의 depth.style은 1종"), 3.4.4(T7 기본 `depth.style = glass`), 3.12 / 04 CF-01, AIL-09(b), G-02("조상 배경 합성")
- **허점·보완**: T7 기본 시안은 대부분 단색 bg 섹션 위에 카드가 놓인다. 그런데 CF-01과 AIL-09(b) 때문에 그 위치에는 glass를 쓸 수 없고, 대신 무엇을 쓸지는 정해져 있지 않다. "depth.style 1종" 규칙 때문에 flat을 섞으면 CF-02 위반처럼 읽힌다. "glass 불가 위치는 flat 규칙(level 1 = `border.width.thin` + `color.border`, 다크는 surface +0.04)으로 렌더하며, 이는 CF-02·H9 집계에서 같은 depth로 본다"를 3.1.8에 추가한다. 또 `backdrop-filter` 요소 위 텍스트의 G-02는 알파 합성으로 계산할 수 없으므로 "이미지 위 텍스트와 같은 방식(텍스트를 숨긴 렌더의 bbox 픽셀 휘도 5퍼센타일)"으로 측정한다고 명시한다.
- **수용 기준**: T7 표준 트리 3개(용도별)에서 AIL-09 error 0, CF 위반 0, H = 100. glass 패널 위 텍스트의 G-02 측정 함수가 픽셀 방식임을 단위 테스트(이미지 위 glass 픽스처)로 확인한다.

### UI2-08 · Minor · 수치 표기 충돌(FP20 웨이트 대 AC-03-25, md 컬럼 수, grain α, S09 권장 폭)

- **허점·보완**(각각 한 줄 수정):
  - 03 3.4.4 "FP20 300은 ≥ 48px 단계에만, 48px 미만 제목은 400" ↔ AC-03-25 "heading 요소의 computed font-weight가 1종". T8 기본값(1280에서 h1 96·h2 51 = 300, h3 38 = 400)은 이 AC를 반드시 실패한다. AC-03-25에 "FP20은 2종(300/400) 허용, 페이지 고유 웨이트 ≤ 3 유지"라는 예외를 넣는다.
  - 03 3.11.1 md(768~1023) = **8컬럼** ↔ 3.11.3 "768~1023: **12열 기준** split은 6/6". "8열 기준 split 4/4"로 고친다.
  - grain 불투명도: 03 3.1.11 `0.04~0.06` ↔ 04 SIG-07 `α 0.03–0.06`. 03장 값으로 통일한다.
  - 07 브라우저/뷰포트 표 "S09 편집은 1024px 이상 권장", "S01~S08·S13 360px 완주" ↔ 01 1.3.1 "≥ 768px 전 기능", "S01~S08, S12, S13". 07장 문장을 01장(그리고 UX2-03 결과)에 맞춘다.

### UI2-09 · Minor · 서비스 UI: 토스트 위 포커스 링 1:1, 화면별 타입 역할·Hahmlet 서브셋 범위 미정

- **관련 절**: 01 1.13.2(`--svc-focus` = `2px solid #1A1A18`, "모든 배경에서 ≥ 3:1"), 1.13.3 Toast("fg 배경·surface 글자", 오류 토스트는 수동 닫기), 1.13.2 타입 스케일·`--svc-font-display`
- **허점·보완**:
  - 토스트 배경이 `--svc-fg`(#1A1A18)라서, 그 안 닫기 버튼에 같은 색 포커스 링을 그리면 대비가 **1.00:1**이다(계산값). 그래서 "모든 배경에서 ≥ 3:1"이 성립하지 않는다(WCAG 2.4.7·1.4.11). 반전 면 위에서는 `--svc-focus-inverse: 2px solid #FFFFFF`(대 #1A1A18 17.4:1)를 쓰도록 토큰을 추가한다.
  - 서비스 타입 스케일 8단계(12~56px)는 있지만 화면 요소별 배정 표가 없다. 지금은 S01 헤드라인(56/32), S03 유형 이름(40/56) 두 곳만 정해져 있다. 1.13.2 아래에 역할 표(H1 desktop/mobile, 섹션 제목, 카드 제목, 본문, UI 라벨, 캡션)를 6행으로 추가한다.
  - Hahmlet "weight 500·700 서브셋"의 글자 범위가 없다. H1에 사용자 입력(브랜드명 등)이 들어가지 않는다면 "고정 문구 집합 서브셋(빌드 시 `copy/ko.ts`의 H1·유형 이름 키에서 추출)"으로 정하고, 들어간다면 KS X 1001로 정한다.
- **수용 기준**: 토스트·반전 면 포커스 상태 스냅숏에서 링 대비 ≥ 3:1(AC-01-47 토큰 테스트에 쌍 추가). S01~S15의 `h1` computed font-size가 역할 표 값과 일치한다(렌더 검사).
