# R2 리뷰: 시니어 UX 디자이너 관점

- 대상: `docs/spec/v2/01_ux_screens.md`(전체 정독). 다른 장은 UX 관련 절만 grep으로 확인했다(00 §7.1·§5.3·§6.2·§8.3, 02 2.3·2.5·2.10·2.12·2.13, 03 3.13.5, 04 4.x `brand_color_notice`, 05 위치 편향, 06 6.2.4·6.4 `SurveyView`/`ResultView`·reconcile).
- 기준: `rubric.md`, `decisions_v2.md`(R-01~R-38), 1라운드 `r1_ux.md`(UX-01~19)
- 규칙: 1라운드에서 해결된 항목은 다시 쓰지 않는다. 새로 찾은 허점만 적는다. 1인 개발 맥락이므로 보완안은 문서 수정이나 작은 구현 변경 범위로 제한한다.

## 총평

v2의 01장은 1라운드 UX 지적 19건을 모두 반영했다. 화면 15개 IA, 화면×상태 매트릭스, 오류 코드→문구 표, 진단 표시 규칙(R1~R9), 편집 원칙, 접근성, 마이크로카피, 이벤트 발화 지점, 사용성 테스트 스크립트가 있고, 대부분에 수용 기준이 붙어 있다. 대기업 디자인 리뷰에 올릴 수 있는 수준의 뼈대다.

남은 문제는 세 가지다. 셋 다 문서 수정으로 고칠 수 있다.
1. **결과 화면(S03) ② 신뢰·경계 안내가 02장 2.13과 맞지 않는다.** 백분율 표기, 문구 우선순위, `open` 임계값, 문구 원문이 서로 다르고, 01장이 원천이라던 문구 일부는 01장에 없다. 그래서 에이전트가 직접 정해야 한다.
2. **자극물 표시 크기 규칙이 흔한 실기기 뷰포트에서 지켜지지 않는다.** mobile 1단계는 "세로 스크롤 없이"라는 자기 요구를 지킬 수 없다. desktop은 1366×768 노트북에서 축소율이 0.28까지 떨어져 모서리·그림자 축이 잘 보이지 않는다.
3. **200% 확대 시 편집 기능이 사라진다.** 편집 가능 여부를 CSS 뷰포트 폭(< 768)으로 판정하기 때문에 1.14.2의 확대·리플로 요구, 즉 WCAG 1.4.4·1.4.10과 정면으로 충돌한다.

## 2. 새 항목

### UX2-01 · Major · 결과 화면 신뢰·경계 안내가 01장과 02장에서 서로 다름

- **관련 절**: 01 1.5.2 ②, 1.5.2.1, 1.15.3 `result.lowSignal` / 02 2.12(판정 표), 2.13.1, 2.13.2 / 06 `ResultView`
- **허점**: S03 ② 영역과 축 막대 상태 표시의 규칙·문구가 두 장에서 아래처럼 어긋난다.

| 항목 | 01장 | 02장 |
|---|---|---|
| 경계 비율 | `{r1}% : {100−r1}%`(5% 단위)를 표시하고 근거로 "02장 2.13.2"를 듦 | "백분율 표기는 하지 않는다(01장)". 2.13.2에는 비율 규칙이 없음. `ResultView`에도 비율 필드가 없음 |
| 경계 문구 | "{1순위} · {2순위} 쪽에도 가까워요" | "{1순위}에 가깝고, {2순위} 성향도 있어요" |
| 문구 우선순위 | 신뢰도 문구 + 경계 + low_signal을 함께 표시하는 것처럼 읽힘 | `low_signal` → `conflict` → κ < 0.50 → `is_boundary` 순서로 **첫 번째 하나만** 표시 |
| `conflict`·κ < 0.50 문구 | 없음 | `conflict` 문구는 02장에 있음. κ < 0.50 문구는 "01장 원문"을 가리키는데 01장에 없음 |
| `open` 축 판정 | `state='open'` **이고 σ_display > 0.10** | `open` = σ > 0.08 |
| 축 문구 | "아직 확실하지 않아요" / "크게 신경 쓰지 않으시는 편이에요" | "이 축은 아직 확실하지 않아요" / "크게 가리지 않는 편이에요" |
| 신호 부족 문구 | ②는 "취향 신호가 부족해요", 1.15.3은 "고른 화면이 적어서 결과가 넓게 나왔어요" | "취향 신호가 부족해요" |

- **왜 문제인가**: S03은 이 서비스에서 처음으로 가치를 체감하는 화면(aha 1)이고, 결과를 얼마나 믿느냐가 생성 전환을 좌우한다. 에이전트는 백분율을 넣을지, 문구를 몇 개 겹쳐 보일지, 0.08과 0.10 중 어느 값을 쓸지 스스로 정해야 한다(C2 위반). 백분율을 넣으면 데이터 원천(`ResultView`)이 없어 즉석 계산을 하게 된다. 또 AC-01-16·AC-02-19 같은 문자열 일치 테스트가 어느 장 기준으로 깨질지 모른다.
- **보완안 [MVP]**:
  1. 문구 원문은 01장, 표시 조건과 우선순위는 02장이 소유한다고 정리하고 01 1.5.2 ②를 다시 쓴다. 02장 순서대로 첫 번째 하나만 표시하고, 그 아래에 신뢰도 한 줄(high/medium/low)을 덧붙인다.
  2. 백분율 표기는 뺀다. 02장 결정을 따르는 것이 데이터 원천도 없고 과잉 정밀이라는 문제도 피한다. 01 1.5.2 ② 규칙 칸의 "02장 2.13이 정한 수치 외 백분율 금지"를 "백분율 표기 0건"으로 바꾼다.
  3. 1.15.3 카피 표에 키 5개를 확정한다. `result.notice.lowSignal`, `result.notice.conflict`, `result.notice.lowConsistency`(κ < 0.50, 예: "고른 화면들의 방향이 조금씩 달라요 — 다시 해 보면 더 정확해져요"), `result.notice.boundary`, `result.notice.seasonAdjusted`. 축 상태 문구 2개(`result.axis.open`, `result.axis.insensitive`)도 넣는다. 02장은 키만 참조하고 문구를 지운다.
  4. `open` 판정은 서버 `axes[].state`만 쓴다. 01장의 "σ_display > 0.10" 조건은 삭제한다(임계값 단일 원천 = 02장, `config/thresholds.json`).
- **수용 기준**:
  - 01·02장 어디에도 S03 ② 문구 원문이 두 벌로 존재하지 않는다(02장은 키 참조만 한다).
  - 07장 골든 GS-25(low_signal), GS-28(conflict), κ < 0.50 픽스처, boundary 픽스처의 결과 화면 스냅샷에서 ② 안내가 정확히 1개 보이고 그 문구가 `copy/ko.ts` 해당 키와 일치한다.
  - S03 DOM에 `%` 문자 0건(축 값 제외).
  - 축 상태 표시는 `ResultView.axes[].state`만으로 결정된다(클라이언트 σ 비교 코드 0건, 단위 테스트).

### UX2-02 · Major · 자극물 표시 크기가 흔한 실기기 뷰포트에서 규칙을 못 지킴(측정 타당성)

- **관련 절**: 01 1.4.3(기기별 카드 비교 방식), 1.4.2 R5, 1.4.11 와이어프레임, AC-01-08 / 06 `SurveyItemView.assets.mobile?`
- **허점**:
  - **mobile 1단계 세로 예산이 정의되지 않았다.** 카드 폭이 `vw − 32`이고 자산 비율이 1:2라서 390px 폭에서 이미지 높이는 716px, 그 "상단 70%"는 약 500px이다. 여기에 헤더·진행률(약 80) + 제목 2줄(약 64) + "2 / 4"(24) + 썸네일 스트립(64) + "이걸로 할게요"(48) + "다 별로예요"(44) + 간격(약 40)을 더하면 약 865px이다. iOS Safari 390×844 기기의 실제 가시 높이(툴바 포함 약 660px)를 200px쯤 넘는다. 그러면 "세로 스크롤 없이"를 지킬 수 없고, 선택 버튼이 화면 밖으로 밀리며, 카드 안 세로 스크롤·페이지 스크롤·좌우 스와이프 세 제스처가 한 영역에서 겹친다.
  - **desktop 축소율 하한이 없다.** 카드 폭 공식은 높이 제약을 받는다. 1366×768 노트북(브라우저 가시 높이 약 657px)에서 `((657 − 208)/2) × 1.6 ≈ 359px`이므로 1280px 자산의 축소율은 0.28이다. 1280×720 가시 영역에서도 0.32다. 이 배율에서는 radius 8px가 약 2px, 그림자 단계 차이는 1px 안팎이 되어 A3 형태·A5 깊이 축의 차이가 사실상 보이지 않는다. 그러면 사용자는 색과 레이아웃만 보고 고르게 되고, 02장 시뮬레이션이 가정하는 "자극물 차이를 지각한다"는 전제가 깨진다.
  - `SurveyItemView.assets.mobile`이 optional인데, mobile 자산이 없는 문항을 mobile에서 어떻게 보여 줄지 규칙이 없다.
- **왜 문제인가**: 진단은 mobile 우선(00 §7.1)이고 국내 노트북 해상도 상위권이 1366·1280 폭이다. 실사용 환경에서 1단계 측정이 왜곡되면 이후 유형·생성 전체가 틀어진다. 그런데 AC-01-08은 폭만 검사해서 이 문제가 테스트에 걸리지 않는다. 또 에이전트가 레이아웃을 맞추려고 요소를 임의로 빼거나 줄이게 된다(C2).
- **보완안 [MVP]**:
  1. **mobile 1단계**: 카드를 고정 높이 창으로 만든다. `card_h = 100dvh − (헤더 56 + 진행률 8 + 제목 48 + 하단 고정 바 120)`이고, 하단 고정 바에는 "이걸로 할게요"와 [썸네일 4칸 + "2/4"]를 한 줄로 합친다. "다 별로예요"는 하단 바 위 텍스트 버튼(44px)으로 둔다. 이미지는 `object-fit: cover; object-position: top`으로 상단을 보여 주고 **카드 안 스크롤은 없앤다**. 전체를 보려면 "크게 보기"(세로 스크롤 라이트박스)를 쓴다. `card_h`가 300px 미만이 되는 극단적인 기기(가로 모드 등)에서는 "세로로 돌려 주세요" 안내를 표시한다.
  2. **desktop/tablet 1단계**: 카드 폭 하한 `w_min = 480px`(축소율 ≥ 0.375)을 둔다. 공식 결과가 `w_min`보다 작으면 높이 제약을 풀고 2×2 그리드를 세로 스크롤로 보여 준다. 위치는 이미 무작위(R2)라서 스크롤 때문에 생기는 편향은 위치 편향 점검(02 2.10)이 함께 잡는다. `ux.viewportClass` 옆에 `ux.cardScale`(소수 2자리)을 기록해서 축소율과 응답 품질의 관계를 사후에 볼 수 있게 한다.
  3. mobile 자산이 없는 문항은 mobile 세션의 문항 후보에서 제외한다(02장 문항 선택 필터에 한 줄 추가). 출시 데이터 묶음 검사에서 mobile 자산 누락 0건을 요구한다.
- **수용 기준**:
  - Playwright 뷰포트 360×640, 390×664, 412×780에서 S02 1단계의 "이걸로 할게요"와 "다 별로예요"가 페이지 스크롤 없이 보이고, 카드 요소의 `scrollHeight == clientHeight`이다(카드 안 스크롤 0).
  - 뷰포트 1280×720, 1366×657, 1440×900에서 1단계 카드 표시 폭이 ≥ 480px다.
  - 응답 `ux.cardScale`이 기록된다(계약 테스트).
  - 출시 데이터 묶음에서 `kind='pick4'|'ab'`이고 mobile 자산이 없는 활성 문항이 0건이다.

### UX2-03 · Major · 200% 확대 시 편집 기능이 사라짐(WCAG 1.4.4·1.4.10과 충돌)

- **관련 절**: 01 1.3.1("S09 편집은 ≥ 768px에서 전 기능, < 768px에서는 미리보기·공유만"), 1.8.7, 1.9 9번, 1.14.2 "확대·리플로" 행, D-0112
- **허점**: 편집·내보내기 가능 여부를 CSS 뷰포트 폭으로 판정한다. 1280px 데스크톱에서 200% 확대하면 CSS 뷰포트는 640px이 되어 S09가 mobile 읽기 전용 모드로 바뀌고 편집 패널과 내보내기 메뉴가 사라진다. 그런데 1.14.2는 "200% 확대·320 CSS px 폭에서 내용 손실 없음(S09 desktop 패널은 예외 없이 드로어 전환)"이라고 해서 정반대를 요구한다. 1024px 이하 노트북에서 150% 배율만 써도 같은 일이 생긴다.
- **왜 문제인가**: 확대 사용자(저시력)가 핵심 기능인 편집·내보내기를 잃는다. 이는 WCAG 1.4.4(텍스트 크기 조정 시 기능 손실 금지)와 1.4.10(리플로) 위반이고, 국내 대기업 접근성 심사(KWCAG)에서 바로 지적되는 유형이다(C3). 두 규칙이 서로 모순되므로 에이전트는 어느 쪽을 따를지 스스로 정해야 한다(C2).
- **보완안 [MVP]**: 판정 기준을 "기기"와 "레이아웃"으로 나눈다.
  1. **편집 허용 여부**는 기기 판정으로 한다: `matchMedia('(pointer: fine)').matches || screen.width >= 768`이면 편집을 허용한다. 터치 전용 소형 기기(휴대폰)만 1.8.7 읽기 전용 모드를 쓴다.
  2. **레이아웃**은 CSS 뷰포트로 정한다. 편집 허용 상태에서 뷰포트가 768px 미만이면 "1열 편집 레이아웃"을 쓴다. 상단 탭 [미리보기][편집]을 전환하고, 편집 탭은 패널 3탭을 전체 폭으로, 미리보기 탭은 375 뷰포트로 보여 준다. 컨트롤 컴포넌트는 desktop과 같다(새 컴포넌트 없음, 배치만 바뀜).
  3. 1.3.1, 1.8.7, 1.9 9번, D-0112 문장을 위 기준으로 고친다. 00 §7.1의 "모바일은 미리보기·공유만"은 "터치 전용 소형 기기는…"으로 바꾼다.
- **수용 기준**:
  - Playwright 1280×800 + `deviceScaleFactor` 유지 + CSS 확대 200%(뷰포트 640 에뮬레이션, `pointer: fine`)에서 S09의 스타일 탭 조작 1회, 저장, S10 다운로드까지 키보드로 완료할 수 있다.
  - 같은 상태에서 가로 스크롤이 0이다.
  - 모바일 에뮬레이션(390×844, `hasTouch`, `pointer: coarse`)에서는 1.8.7 읽기 전용 모드가 유지된다.

### UX2-04 · Minor · 1.15.3 핵심 문구 표가 본문과 다름

- **관련 절**: 01 1.15.3 `drafts.partial`, `result.lowSignal` / 1.7.2, 1.5.2 ②
- **허점·보완**: `drafts.partial` "기준을 통과한 시안만 보여드려요"는 1라운드 안 그대로다. 그런데 v2의 `partial`은 누락 변형을 "기본 구성"으로 채워 3칸을 모두 보여 준다(1.7.2 "일부 방향은 기본 구성으로 준비했어요"). 따라서 키 문구를 1.7.2 문구로 바꾸고 `drafts.fallback` 키를 추가한다. `result.lowSignal`은 UX2-01에서 함께 정리한다. MC-9에 따라 본문 문구와 카피 표가 다르면 카피 표가 이긴다는 규칙을 1.15.3 머리에 한 줄 넣는다.
- **수용 기준**: 1.15.3 표의 각 키 문구가 본문 같은 상태의 문구와 문자열이 일치한다(문서 검사 스크립트 또는 수동 대조 체크리스트).

### UX2-05 · Minor · 진행률 `aria-valuenow`와 단조 증가 수용 기준이 모순

- **관련 절**: 01 1.4.7, AC-01-06
- **허점·보완**: `aria-valuenow = 응답 수`인데 "이전 문항"을 누르면 응답 수가 1 줄어든다. 반면 AC-01-06은 `aria-valuenow`도 단조 비감소여야 한다고 기록한다. 시각 막대는 `p_shown`(단조)을 쓰고 `aria-valuenow`는 실제 위치(감소 가능)를 쓰도록 정리하고, AC-01-06의 측정 대상에서 `aria-valuenow`를 빼서 막대 폭만 본다. `aria-valuetext`는 텍스트 카운터와 같게 둔다.
- **수용 기준**: AC-01-06 문장이 "막대 표시 폭 단조 비감소, `aria-valuenow` = 현재 문항 위치"로 고쳐진다.

### UX2-06 · Minor · 생성 대기 화면의 경과 시간 기준이 두 가지

- **관련 절**: 01 1.6.2(경과 시간 = 현재 − `queuedAt`), 1.6.4(표 머리 "경과(`startedAt` 기준)") / 06 6.2.4
- **허점·보완**: 대기열을 거친 잡은 화면 시계가 "2:30"을 넘었는데도 90초 안내가 아직 안 나올 수 있다. 사용자가 보는 시계와 안내 문구가 어긋나는 것이다. 표시 시계는 SLO와 같은 `queuedAt` 기준으로 유지하고, 1.6.4의 90초 보조 문구도 `queuedAt` 기준으로 바꾼다. 120초·180초는 서버 사건이므로 `startedAt` 기준을 유지하되 표 안에 "(서버 기준, 대기 시간 제외)"를 명시한다. 대기가 길어 표시 시계가 3분을 넘으면 "사용자가 많아…" 문구를 유지한다.
- **수용 기준**: 목 서버로 대기 60초 + 실행 40초를 주입하면 표시 시계 1:40 시점에 90초 보조 문구가 보인다.

### UX2-07 · Minor · mobile S08의 주 행동이 정의되지 않음

- **관련 절**: 01 1.2(S11 진입에 "S08(mobile)"), 1.7, 1.8.7
- **허점·보완**: IA는 mobile S08에서 공유(S11)로 들어갈 수 있다고 하지만, 1.7에는 mobile 전용 규칙이 없다. 지금 상태에서는 [이 시안 다듬기]가 읽기 전용 S09로 이어져 막다른 길처럼 느껴진다. mobile(터치 전용 소형 기기, UX2-03 판정) S08 레일에서는 주 CTA를 "PC에서 다듬기"(링크 복사 + "로그인하면 내 기록에서 이어서 할 수 있어요")로 하고, 보조 CTA를 [공유 링크 만들기]로 정한다. 이메일 보내기 같은 새 기능은 넣지 않는다.
- **수용 기준**: 390×844 터치 에뮬레이션의 S08에서 주 CTA 문구가 카피 표 키와 일치하고, 공유 토글로 S11이 열린다.

### UX2-08 · Minor · 비공개 베타 초대 코드 입력 시점이 너무 늦음

- **관련 절**: 01 1.1.4, 1.12.2 `INVITE_REQUIRED` / 00 §7(비공개 베타)
- **허점·보완**: 베타 사용자(≤ 50명)는 진단·브리프·로그인·동의를 모두 마친 뒤에야 오류 박스로 초대 코드를 입력하게 된다. 베타 지표의 분모가 바로 이 사용자들이라 첫인상이 중요하다. 초대 링크 `/?invite=<code>`의 값을 localStorage에 보관했다가 로그인 직후 자동으로 `redeem`하는 규칙 한 줄을 추가하고, `BETA_INVITE_ONLY=true`일 때 S01 정보 줄에 "시안 생성은 초대받은 분부터 열려 있어요"를 표시한다.
- **수용 기준**: 초대 링크로 들어온 E2E 사용자가 `INVITE_REQUIRED` 박스를 0회 보고 S07에 도달한다.

### UX2-09 · Minor · 1.18 추가 결정 표의 반영 상태가 낡음

- **관련 절**: 01 1.18 D-0111
- **허점·보완**: D-0111은 "02장 미반영 / 03장 미반영"으로 적혀 있지만, 실제로는 02 2.3(`dominant_colors`)과 03 3.13.5(`colorName`)에 반영돼 있다. 상태를 "반영 완료"로 고친다.
- **수용 기준**: 1.18의 각 상태가 대상 장 grep 결과와 일치한다.
