## 총평

2라운드 Blocker 1건과 Major 4건은 본문에 실제로 반영됐다. 정규화기 temp(B18 `2026-S0`, 홀드아웃, 재적합 금지 F19), few-shot 0개 처리, 시뮬레이션 판정 설계(gate/dev 시드 분리, 풀링 점추정, 공통 난수 쌍체, 닫힌 조정 공간, 시도 상한 15·gate 3, BLK 종료), 골든 M1a/M1b 분리와 `muRef`·seed 고정, `gen_copy` 실패 4단계, Mock 역할 4개 재작성과 `mixed` 시나리오가 모두 들어 있다. 덕분에 통계 설계의 뼈대는 대기업 ML 리뷰에 올릴 수준이 됐다. 조정 공간의 시도 수(4+3+3+2+2+1 = 15)가 `maxTuningTrials` 15와 정확히 맞고, M1b의 근거(RMSE 0.12에서 ±0.12 포함 약 68%)도 맞다.

남은 문제는 "반영은 됐는데 새 규칙끼리, 또는 새 규칙과 기존 hard 조건이 맞물리지 않는" 지점이다. 다섯 가지다.
1. **temp 분기의 "막지 않는다"가 verify hard 조건과 충돌한다.** 05 5.9 temp 분기는 실패 축을 `reliable=false`로 두고 진행하라고 한다. 그런데 같은 표는 "CI 실패"라고 적고 있고, M3 ③(모든 프리셋·축 ≤ 0.10)과 M4 ①(활성 카드 48, 축별 ≥ 19쌍)도 hard 조건이다(AI3-01).
2. **`reliable[k]=false`가 TM 식에 들어가 있지 않다.** 05장은 "TM 가중 0"이라고 말하지만, 04 4.10.4 식에는 마스크가 없다. A1·A4가 unreliable이면 S_free는 정의조차 되지 않는다(AI3-02).
3. **유일한 정확도 게이트인 시뮬레이션이 temp에서 배포 자극물과 다른 x를 쓴다**(target_l1 + 잡음, AI3-03).
4. **Mock의 재호출·수리 응답 규칙이 없다.** 공통 시드에 호출 종류와 시도 번호가 없어서 repair와 다양성 재호출이 같은 출력을 돌려준다. 그래서 TC-R-15의 "재호출 후 다양성 100%"를 만족할 수 없다(AI3-04).
5. **조정 탐색의 목적함수와 gate 실행 시점이 정해지지 않았다.** 지표가 13개인데 "dev 지표가 가장 좋은 값"이 무엇인지 문서에 없다(AI3-05).

### AI3-01 · Major · temp 분기의 "막지 않는다"가 hard 조건과 충돌함

- **관련 절**: 05 5.9 표(앵커 행 실패 처리 "CI 실패. 아래 실패 절차", 카드 행 "기준 밖 카드는 draft", A/B 행 "축별 활성 쌍 ≥ 19/24가 빌드 통과 조건")와 temp 분기("이때는 막지 않고 … 실패한 축은 `reliable[k]=false`"), 5.7 D-056("5축 중 3축 이상이 false면 출시를 차단") / 09 M3 ③(모든 프리셋·축 ≤ `roundtripAbsMax`), M4 ①(활성 카드 ≥ 48 중 approved 전부, 축별 ≥ 19쌍) / 02 2.6.1(제약 (a)(b)(f)는 해제하지 않음) / 07 deferrable `temp` 목록(`extractor-roundtrip` 같은 단계가 없음)
- **허점**:
  - 사람 라벨이 없는 temp 상태에서 앵커 왕복이 한 축이라도 0.10을 넘었다고 하자. 그러면 5.9 temp 분기는 `reliable=false`로 두고 계속하라고 한다. 반면 같은 표의 앵커 행과 M3 ③은 CI 실패다. 이 단계는 S-03 보류 허용표에도 없으므로, 보류 상태를 반환하면 fail이 된다. 결국 verify:m3가 실패할지 통과할지가 문서에 정해져 있지 않다.
  - 카드·쌍도 마찬가지다. temp 분기는 실패한 카드·쌍을 draft로 두라고 한다. 그런데 M4 ①은 "활성 카드 ≥ 48"이고 카드 계획은 48장이므로, 한 장만 draft가 되어도 M4 ①이 실패한다. 축별 활성 쌍이 19 미만이 되는 경우도 같다. 또 활성 카드가 줄어 2.6.1에서 해제하지 않는 제약 (a)(b)를 만족하는 4장 조합이 0개가 되면, 엔진 동작이 정의되지 않는다.
  - "3축 이상 false면 출시 차단"이 verify에도 적용되는지(M3 fail인지), release:check에만 적용되는지도 적혀 있지 않다.
  - temp 정규화기는 b0·b1을 축별 최소제곱으로 맞춘다. 최소제곱 적합은 회귀 희석 때문에 축 끝 값(3.4.7의 0.00·1.00)을 중앙 쪽으로 당긴다. 그래서 앵커 왕복 실패는 드문 예외가 아니라 실제로 일어날 수 있는 경로다. 예를 들어 상관이 r일 때, 끝 값 앵커의 예측은 대략 0.5 − r·0.5가 된다. r = 0.8이면 오차가 0.10에 이른다.
- **왜 문제인가**: 에이전트는 verify를 통과시키려고 셋 중 하나를 고르게 된다. ① M3 ③을 temp에서 건너뛴다(기준 완화). ② 실패를 BLK로 넘긴다. ③ 카드 계획 수를 바꾼다. 어느 쪽이든 문서에 없는 결정이다(C2). ①은 프로젝트 금지 사항인 기준 완화에 해당한다.
- **보완안 [MVP]** (decisions_v4 1행 + 05·07·09 문장 수정):
  1. 단계 상태를 하나로 정한다. 새 단계 ID `extractor-roundtrip`를 둔다. B18이 `provenance:"temp"`일 때만 실패 축이 `temp`를 반환한다. 이 경우에도 reliable 축 수가 `release.extractor.reliableAxesMin`(3) 미만이면 fail이다. human 정규화기에서는 기존대로 fail이다. 이 단계를 07 deferrable `temp` 목록에 추가한다. 기준값 0.10은 바꾸지 않는다. 판정은 그대로 하고 결과의 상태 분류만 정하는 것이다.
  2. M3 ③ 문장에 "B18 temp이면 위 1의 상태 규칙"을 덧붙인다. 05 5.9 앵커 행의 "CI 실패"에는 "(human 정규화기)"를 붙인다.
  3. M4 ①은 완화하지 않는다. temp에서 카드·쌍 미달이 생기면 M4 ①은 fail이고, S-08과 같은 방식으로 처리한다. 즉 BLK를 등록하고 G2-진단은 fail로 둔 채 M5 이후를 계속한다. 이 문장을 09 M4에 넣는다.
  4. 02 2.6.1에 "해제 후에도 후보 0개이면 `SURVEY_ITEMS_INSUFFICIENT`로 세션 시작을 거부한다(빌드 단계에서 미리 검출)"를 넣는다.
- **수용 기준**:
  - 픽스처: temp 정규화기에서 앵커 1개 축의 오차를 0.12로 주입하면 `extractor-roundtrip=temp`이고 `reliable` 해당 축이 false다. verify:m3 종료 코드는 0이 아니며 허용표 안이다. 3축을 주입하면 fail이다.
  - 픽스처: 활성 카드 47장이면 verify:m4 ①이 fail이고 BLOCKED.md에 BLK가 생기며, M5 작업은 계속 진행된다.
  - 2.6.1 후보 0개 픽스처에서 세션 생성 API가 정해진 오류 코드를 반환한다(06 오류 표에 존재).

### AI3-02 · Major · TM·S_free 식에 `reliable`·`subjective` 반영이 없음

- **관련 절**: 04 4.10.4(`w_k = λ_k/(σ_k² + τ²)`, `S_free = … mean_{k∈{A1,A4}}`, 노출 조건 TM ≥ 75 ∧ S_free ≥ 65) / 05 5.7 D-056("ρ < 0.70인 축은 `reliable[k]=false` … 04장 취향 일치도에서 해당 축 가중치를 0"), ICC 행("`subjective=true` … λ를 0.5배"), 5.9 temp 분기("해당 축의 TM 가중은 0") / 07 7.3.2 G2 행, 7.2.5 M8 / 04 4.11.2(`axis_gaps` 상위 3축)
- **허점**:
  - 04 본문에는 `reliable`라는 단어가 0건이다(grep). 05장의 "TM 가중 0"과 "λ 0.5배"를 어떤 식으로 적용하는지, 즉 정규화 전에 곱하는지 후에 곱하는지가 정의되지 않았다. 04 4.10.4가 TM 식의 원천이므로, 05장 문장만으로 구현하면 원천과 다른 식이 생긴다.
  - S_free는 A1·A4 두 축만 쓴다. reliable 축이 3개(`reliableAxesMin`)라는 조건을 만족해도, unreliable 2축이 A1·A4이면 S_free는 빈 평균이 된다. 노출 조건 `S_free ≥ 65`와 골든 M8 "S_free 최솟값 ≥ 65"를 계산할 수 없다. 1축만 unreliable인 경우에도 S_free를 1축으로 줄이는지 정해져 있지 않다.
  - 수정 루프 `axis_gaps`가 unreliable 축을 피드백에 넣는지도 정해져 있지 않다. 넣으면 측정을 믿을 수 없는 축으로 LLM을 수정시키게 된다.
  - temp에서는 AI3-01 경로로 `reliable=false`가 실제로 생긴다. 그래서 이 공백은 mock 전 구간에서 실행되는 코드 경로다.
- **왜 문제인가**: 노출 판정(TM·S_free)은 제품의 핵심 품질 게이트다. 이 판정이 구현자의 선택에 따라 달라진다(C2). ML 리뷰에서는 "신뢰할 수 없는 측정 축을 점수에서 어떻게 빼는가"를 반드시 묻는다(C3).
- **보완안 [MVP]** (04 4.10.4 식 2줄 + 표 1행):
  ```
  m_k  = reliable_k · (subjective_k ? 0.5 : 1)
  w_k  = m_k·λ_k / (σ_k² + τ²),  Σ w_k = 1 로 정규화(m_k = 0 축 제외)
  F    = {A1, A4} ∩ {k : reliable_k}
  S_free = F = ∅ ? null : 100·clip(1 − sqrt(mean_{k∈F}(v_k − t_k)²)/0.30, 0, 1)
  노출 조건: TM ≥ 75 ∧ (S_free = null ∨ S_free ≥ 65)
  ```
  S_free = null이면 `QualityReport.sFree = null`과 경고 `SFREE_NA`를 기록한다. 골든 M8 S_free 최솟값은 null이 아닌 값만으로 계산하고 null 개수를 리포트에 적는다. 이것은 합격선 완화가 아니다. 측정할 수 없는 경우를 명시하는 것이다. 사람 라벨 G2가 이 상태를 확인한다. `axis_gaps`는 `reliable_k = true` 축만 넣는다. 원천은 04로 두고, 05 D-056은 "04 4.10.4 m_k"를 참조하도록 고친다.
- **수용 기준**:
  - 단위 테스트: reliable = [T, F, T, T, T]이면 A2 가중이 0이고 Σw = 1이다. reliable = [F, T, T, F, T]이면 `sFree = null`이고 노출 판정은 TM만으로 한다.
  - `rg -n "reliable" docs/spec/v2/04_generation.md`가 4.10.4에서 1건 이상 나온다.
  - mock 골든 리포트 스키마에 `sFree: number | null`과 null 개수 필드가 있다.

- **수용 기준**:

### AI3-05 · Major · 조정 탐색의 목적함수·좌표별 대상 지표·gate 실행 시점이 없음

- **관련 절**: 02 2.16.2 조정 절차("좌표 순차 탐색(① → ⑥ 순서, **각 좌표에서 dev 지표가 가장 좋은 값 채택**) … dev 시도 ≤ 15회, gate 실행 ≤ 3회"), 표 13행 / 09 M4 ④ / S-08 ④ / QA3-02(튜닝 상수 잠금, 여기서는 다루지 않음)
- **허점**:
  - 합격 지표는 13개이고 방향이 서로 다르다. RMSE는 낮을수록, top-1은 높을수록 좋다. 포함률은 구간 [0.85, 0.95] 안에 들어야 한다. κ는 β=16에서는 높게, β=2에서는 낮게 나와야 한다. 그런데 "dev 지표가 가장 좋은 값"이 무엇인지, 즉 스칼라화나 사전식 순서가 정의되지 않았다. 좌표마다 영향을 받는 지표도 다르다. calibKappa는 포함률만 바꾸고, (llChance, llRef)는 κ만 바꾼다. 그런데 목적함수가 하나로 고정되어 있지 않으니, 같은 dev 결과에서도 구현에 따라 다른 값이 채택된다.
  - gate를 언제 돌리는지 정해져 있지 않다. 좌표마다 돌리면 3회 상한을 바로 쓴다. 또 gate 결과를 보고 다음 좌표를 고르면, S-08이 막으려던 판정 표본 누출(선택 편향)이 다시 생긴다. "최대 3회"는 gate를 사실상 튜닝 표본으로 쓰는 것을 허용하는 셈이다.

- **왜 문제인가**: 튜닝 규칙이 결정론이 아니면 같은 저장소에서도 세션마다 다른 상수와 다른 G2 판정이 나온다. 이렇게 되면 AI2-02에서 만든 통계 설계의 이점이 사라진다(C3). 목적함수도 에이전트가 정하게 된다(C2).
- **보완안 [MVP]** (02 2.16.2 문단 1개):
  1. **목적함수(사전식)**: ① dev 풀링 결과에서 합격선을 못 넘은 지표 수가 적을수록 좋다. ② 동률이면 정규화 부족분의 합 Σ max(0, (합격선 − 값)/합격선)이 작을수록 좋다. 포함률은 구간까지의 거리로 계산한다. ③ 그래도 동률이면 현재 값을 유지하고, 다음으로 값 집합의 사전순으로 정한다.
  2. **좌표별 평가 지표**: ①④⑥은 전 지표로 평가한다. ②는 κ 2행만, ③은 포함률만, ⑤는 사전 영향 행과 전 지표의 미달 수로 평가한다. 다른 지표가 새로 미달하게 되는 값은 채택하지 않는다.
  3. **시도 계수**: 현재 값의 dev 실행을 시도 1회로 센다(시작점 1회 + 좌표별 비현재 값 = 1 + 3 + 2 + 2 + 1 + 1 + 1 = 11 ≤ 15).
  4. **gate 시점**: gate는 ①~⑥을 한 바퀴 다 돈 뒤에만 실행한다. gate 결과는 PASS/FAIL만 쓰고 다음 탐색에 지표값을 넘기지 않는다. 두 번째 바퀴는 dev만으로 다시 돈다. gate 3회는 "바퀴 3회"를 뜻한다.
  5. `sim/reports/tuning-log.json` 스키마에 `round`, `coordinate`, `value`, `devMetrics`, `objective`, `chosen`, `gateRun`을 둔다.
- **수용 기준**:
  - 같은 커밋에서 튜닝을 2회 실행하면 `tuning-log.json`의 바이트가 같다(결정론).
  - 메타 테스트: gate 결과 지표값이 다음 dev 선택 함수의 입력에 없다(정적 검사: 선택 함수 시그니처가 dev 리포트만 받는다).
  - 가짜 실패 주입 시 gate 실행 수가 3에서 멈추고 BLK가 1건 생긴다.

### AI3-08 · Minor · 골든 `persona.simulator` 필드 의미가 모호함

- **관련 절**: 07 7.2.2(`"simulator": {"beta": 16, "policy": "argmax", "seed": 1}`), 7.2.3
- **허점·보완**: argmax 정책에서는 β가 응답에 영향을 주지 않는다. 동점 처리와 `seed`가 무엇을 정하는지(1단계 ε-explore와 셔플은 세션 seed에서 나온다, 02 2.6)도 적혀 있지 않다. 둘 중 하나로 정한다. (a) `policy:"argmax"`이면 `beta` 필드를 금지하고, seed는 세션 seed로 쓴다고 명시한다. (b) `policy:"sample"`(β=16, seed = 응답 난수)로 바꾼다. 회귀 검출 목적에는 (a)가 단순하다.
- **수용 기준**: 골든 zod 스키마가 `policy`에 따라 `beta`를 금지하거나 필수로 요구한다(판별 유니온).

### AI3-09 · Minor · Mock `judge_vision` 위치 교환 의미가 미정

- **관련 절**: 09 9.6.2(`hash(candidateIds)`로 정한 JudgeResult), 04 4.10.5((A,B)·(B,A) 2회, 다르면 무승부, 편입 조건 "위치 교환 불일치율 ≤ 15%")

- **수용 기준**: mock 골든에서 위치 교환 불일치율이 0이고, `judge_position_bias`에서는 1.0이다.
