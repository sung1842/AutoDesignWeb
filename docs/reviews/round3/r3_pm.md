- 대상: `docs/spec/v2/00_overview.md`(§1·§5~§10·§14·§15 정독). 01~09장은 PM 관련 절만 grep으로 확인(01 1.6.5·1.11·1.12·1.17, 04 4.12, 06 6.2.3·6.4·6.11.2·6.13·6.16, 07 7.3.1·7.8·7.9·7.11·7.12.1, 08 BLOCKED_BRAND 표, 09 9.4 M0~M8·AC-09-12)

## 총평

2라운드 Major 5건 중 4건은 본문에서 해결을 확인했습니다. 목표-예산 검산(§9.4), 취소 한도 규칙(00·06·04·01 같은 문장), KPI 쿼리 분모(§8.5), 출시 단계 명칭·값(06~09장 `P0-α` 등 0건, 07 7.3.1 ≥65%, 09 M7 404)이 모두 고쳐졌습니다. 숫자와 규칙의 정합성은 2라운드보다 확실히 좋아졌습니다.

남은 문제는 **"00장에서 정한 것이 구현 장으로 내려가지 않은 것"**과 **"2라운드 수정이 만든 새 빈틈"**입니다.
1. S-18(검증 표본 운영)은 00장에만 반영됐습니다. 01장에는 재검사 안내·배너·A5 후속 시트 화면이 없고, 06장에는 응답 API가 없습니다. 그래서 AC-00-04는 여전히 충족할 수 없습니다.
2. S-16(취소 시 노출 0이면 환불)은 공정성 문제를 해결했지만, "요청 → 노출 전 취소"를 반복하면 한 계정이 하루 전체 예산(US$10)을 30분 안에 태울 수 있습니다. 대응은 경보(A4)뿐입니다.
3. 예산 검산은 사용자 생성만 셉니다. 골든 live 실행(약 US$24/회), 블라인드 평가 시안, staging 비용이 예산 모델에 없습니다. staging 일 예산 US$2로는 G2 게이트(골든 32×3)를 돌릴 수 없습니다.
4. 09장 마일스톤 M0~M8 어디에도 이벤트 수집·KPI 쿼리·어드민 KPI 화면·초대 코드·생성 한도·페이크 도어·문의가 배정되어 있지 않습니다. 00장의 AC-00-04·06·09·13·15·21이 구현 순서상 갈 곳이 없습니다.

모두 문서 수정으로 고칠 수 있는 범위입니다(반나절~하루).

### PM3-01. 검증 운영 장치(S-18)가 00장에만 있음
- **심각도**: Major
- **관련 절**: 00 §5.1 A1 ②·A5·A7, §5.2 AC-00-04, §5.4, §8.3 `adoption_followup_answer`, §8.5. 01 1.5.2(S03 소유자 뷰), 1.11(S12), 1.12. 06 6.4 API 표. decisions_v3 S-18(대상 장: 00, 01, 07)
- **허점**:
  1. **01장에 화면 명세가 없습니다**. grep 결과 01장에 "1주 뒤 다시", "다시 진단해 보기" 배너, "실제로 사용했나요" 시트가 0건입니다. S12(1.11)에는 [새로 진단하기] 버튼만 있고, "6일 이후 첫 방문 시 배너"라는 조건·문구·닫기 동작이 없습니다. 카피 키(`copy/ko.ts`)도 없습니다.
  2. **06장에 응답 경로가 없습니다**. `adoption_followup_answer`는 `source: server`입니다. 그런데 이를 받는 API(예: `POST /api/mockups/:id/followup`)가 06 API 표에 없습니다. "1회만 표시"를 보장할 저장 위치(예: `mockups.followup_answered_at`)도 없습니다. `verify:api-parity`가 06장 엔드포인트 목록을 기준으로 하므로, 에이전트는 엔드포인트를 만들면 parity를 깨고, 만들지 않으면 이벤트를 기록할 수 없습니다.
  3. **트리거 조건이 모호합니다**. "채택 7일 이후 첫 로그인 방문"에서 시안이 여러 개일 때 어떤 시안을 묻는지, 하루에 몇 개까지 묻는지, 닫으면 다시 묻는지가 없습니다.
  4. **A5·A7 계산식이 없습니다**. AC-00-04는 "§8.5 쿼리 존재"를 요구하지만 §8.5에는 A5("배포 또는 외주 전달" ≥30%)와 A7(클릭률 ≥5%) 쿼리가 없습니다. 특히 A5의 분모가 "응답한 시안"인지 "채택한 시안 전체"인지 정해지지 않았습니다. 무응답률이 높으면 두 정의의 결과가 크게 다릅니다.
- **왜 문제인가**: A5는 Phase 2 진입 조건 ③이고, A1 ②(재검사)는 공개 출시 조건입니다. 데이터가 들어올 화면과 API가 없으면 2라운드와 같은 상태(측정 장치는 있지만 데이터 경로가 없음)가 계속됩니다. 화면 문구, 트리거, 분모를 에이전트가 스스로 정해야 합니다(C2).
- **보완안**:
  > - 01 1.5.2 S03 소유자 뷰에 재검사 안내 1줄을, 1.11 S12에 배너 행을 추가한다. 배너 조건은 "로그인 사용자, 마지막 `survey_complete` 후 6~14일, 이 기간에 아직 닫지 않음"이다. 닫기는 `localStorage`가 아니라 서버 플래그(`users.retest_prompt_dismissed_at`)에 저장한다. 카피 키는 `retest.notice`, `retest.banner`.
  > - 01장에 후속 시트를 추가한다. 대상은 `adopted_at ≤ now() − 7d`이고 `followup_answered_at is null`이며 `followup_dismissed_at is null`인 시안 중 가장 오래된 1개다. 표시는 방문 1회당 1개, 닫으면 그 시안은 다시 묻지 않는다. 카피 키는 `followup.*`.
  > - 06장: `POST /api/mockups/:id/followup {answer} → 204`(소유자만, 중복 409)와 `POST /api/mockups/:id/followup/dismiss → 204`를 API 표에 추가한다. `mockups.followup_answered_at`·`followup_dismissed_at` 컬럼도 추가한다. 이벤트는 서버가 기록한다.
  > - 00 §8.5에 두 쿼리를 추가한다. A5 = `answer ∈ {deployed, handed_off}` 응답 시안 / **응답 시안**(판정 최소 응답 n ≥ 15). 응답률(응답 / 채택 7일 경과 시안)도 함께 보고한다. A7 = `paywall_interest` 주체 / `paywall_view` 주체.
- **수용 기준**: 01·06장 grep으로 위 카피 키·엔드포인트·컬럼이 각각 1건 이상 나옵니다. AC-00-04 픽스처 테스트가 A1 ②·A5·A7을 §8.5 쿼리로 계산합니다. 같은 시안에 시트가 두 번 표시되지 않습니다(통합 테스트).

### PM3-02. "노출 전 취소 = 환불"로 단일 계정이 전체 일 예산을 소진할 수 있음
- **심각도**: Major
- **관련 절**: 00 §9.3 한도 표 `canceled` 행("원가 남용은 레이트리밋과 A4 경보로 감시"), §9.4 KS-1·경보 A4, RK-02. 06 206행, 6.12.4 A4("경고"), 6.10.1 레이트리밋(계정 2회/분)
- **허점**: S-16으로 "비폴백 노출 0인 상태의 취소"는 환불됩니다. 그런데 이 시점에는 이미 후보 생성(잡당 LLM 예산 ≤ US$0.18, §9.1)의 원가가 대부분 발생해 있습니다(첫 노출 p50 ≤ 45초 이전). 산술은 다음과 같습니다.
  - 레이트리밋 계정 2회/분 × 잡당 약 US$0.18 ≈ 분당 US$0.36. `GEN_DAILY_BUDGET_USD=10`은 **약 28분**이면 소진됩니다.
  - 한도(3회/일)는 환불되므로 막지 못합니다. 사용자당 진행 잡 1개 규칙도 "요청 → 취소 → 요청" 순서에서는 막지 못합니다.
  - A4(단일 계정 ≥ 일 예산 20%)는 **경고만** 보냅니다(06 6.12.4). 1인 운영의 수동 대응 기준은 24시간이므로, 그 전에 KS-1이 발동해 **모든 사용자의 생성이 그날 막힙니다**.
  - 취소했을 때 진행 중인 LLM 호출을 바로 끊는지(abort)도 06 cancel API(1273행)에 정해져 있지 않아, 취소 후 원가가 얼마나 더 발생하는지 알 수 없습니다.
- **왜 문제인가**: 일부러 악용하지 않아도 같은 일이 생깁니다. 대기 중 반복 취소처럼 흔한 사용 패턴으로도 하루 예산을 다 쓸 수 있습니다. 대기업 리뷰에서 "무료 한도의 환불 경로가 비용 공격 경로가 되는가"는 BM·보안 공통 체크 항목입니다(C3). 에이전트는 남용을 막을지, 막는다면 어떤 수치로 막을지 스스로 정해야 합니다(C2).
- **보완안**: MVP에서는 경보를 자동 차단으로 바꾸는 최소 규칙 2개로 충분합니다.
  > - **환불 취소 횟수 상한**: 노출 0 취소 환불은 계정당 하루 **2회**까지만 한다. 3번째부터는 노출 0이어도 차감하고, 01 1.6.5 확인 시트 문구에 이 분기를 추가한다("오늘은 취소해도 횟수가 차감돼요").
  > - **계정 일 원가 상한**: `USER_DAILY_COST_CAP_USD`(기본 1.5 = 3회 × 0.30 + 여유 0.6)를 6.10.4에 추가한다. 넘으면 그 계정의 신규 생성은 429 `QUOTA_DAY`(사유 `cost_cap`)로 막는다. A4는 경고와 함께 이 차단이 발동했음을 알린다.
  > - 06 cancel API: 취소 즉시 진행 중 LLM 호출을 abort하고 `llm_calls.status='aborted'`로 기록한다(AC-06-40과 같은 방식).
- **수용 기준**: 통합 테스트 ① 같은 계정이 노출 0 취소를 3회 하면 3번째는 한도 1 감소 ② Mock 호출당 US$0.30으로 계정 누적 원가가 1.5를 넘은 뒤의 요청은 429이고, 다른 계정의 요청은 정상 202 ③ 취소 후 5초 안에 해당 잡의 `running` LLM 호출이 0개. 00 §9.3 `canceled` 행과 06 206행이 같은 문장입니다.

### PM3-03. 평가·staging LLM 지출이 예산 모델 밖에 있음
- **심각도**: Major
- **관련 절**: 00 §9.4 근거 문장·검산 표·"staging live 일 예산 US$2", §10.5 "모델·프롬프트 변경 시" 루틴. 06 1987행(staging `GEN_DAILY_BUDGET_USD=2`, "골든 live 실행" 용도), 2138행("staging 키, 평가 전용 예산" — 값 정의 없음). 07 G2(골든 32×3 전체), 7.8(P-1 20·P-2 20+20·P-4 ≥30쌍), `release.golden.costMeanMaxUsd 0.25`, `release.promotion.blindPairs 40`. 05 D-05C `REF_TAGGING_BUDGET_USD=10`(별도 집계)
- **허점**:
  1. **G2를 실행할 수 없습니다**. 골든 전체 실행은 96잡이고, 평균 원가 상한 US$0.25를 넣으면 약 **US$24/회**입니다. 그런데 staging 일 예산이 US$2이고 `packages/llm`이 예산 가드를 적용하므로(06 75행), 약 8잡 뒤 KS-1이 막습니다. 그러면 G2 리포트는 결코 32×3을 채우지 못합니다.
  2. **"평가 전용 예산"이라는 말만 있고 값이 없습니다**. 키 이름, 기본값, 어느 집계(일·월, prod·staging)에 포함되는지가 06·07·09장 어디에도 없습니다.
  3. **총비용이 없습니다**. 출시 전 평가 비용(골든 1~3회 + 회귀 + 블라인드 시안 생성 + 베이스라인 시안)과 운영 중 비용(모델·프롬프트 변경마다 골든 + 40쌍, 시즌마다 `ref_tagger`)이 §9 원가 모델에 한 줄도 없습니다. §9.4 검산은 사용자 생성만 다룹니다.
