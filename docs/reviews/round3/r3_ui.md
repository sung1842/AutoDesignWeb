# R3 리뷰: 시니어 UI 디자이너 관점

- 대상: `docs/spec/v2/03_design_system.md` 중심. 3.1.3 색 역할, 3.1.5·3.1.5a 타입 토큰과 텍스트 역할 표, 3.4.2·3.4.6 팔레트·타입 스케일, 3.5 컴포넌트, 3.6 블록, 3.7.5 서브셋, 3.8 조판·줄 예산, 3.11 반응형, 3.13 브랜드 컬러, 3.14 조화 점수를 보았다. 다른 장은 UI 관련 절만 grep으로 확인했다: 01 1.5.5.2·1.8.5·1.13, 04 §4.2.1~4.2.2·§4.6.2·§4.7.1·§4.8·§4.10.1~4.10.3·§4.11.1·§4.13.2(AIL-*)·§4.15.2·§4.16, 06 6.8.2, 07 7.1.2·7.x 뷰포트 표, 09 `registry` 타입·B25.
- 기준: `rubric.md`, 2라운드 `r2_ui.md`(UI2-01~09), `decisions_v3.md`(S-37~S-40)
- 규칙: 2라운드 항목의 해결 여부는 decisions_v3를 믿지 않고 장 본문을 grep해서 판정했다. 수치는 모두 직접 계산했다. 3.4.6 타입 스케일은 3.1.5 식으로 다시 계산해 8행 모두 일치했다. 3.4.2 대비 표 11쌍 × 8프리셋도 WCAG 2.x 상대 휘도로 다시 계산해 모두 일치했다. 아래 새 항목의 수치도 같은 스크립트로 냈다. 다른 3라운드 리뷰(PM·UX·QA·테크)에 이미 있는 항목은 다시 적지 않았다.

## 총평

2라운드 Major 4건은 문서에 들어갔다. 반영 수준은 항목마다 다르다.
- **H7과 단계 이름 분리(UI2-02)**: 깔끔하게 해결됐다. 허용 집합 전 조합에서 display/body 비를 계산해 보니 최소 2.99(T2·T3, ratio 1.2·boost 1.0), 최대 8.0(상한 클램프)이다. 따라서 H7은 모든 조합에서 만점이고, 표준 트리 H = 100의 영점이 다시 선다.
- **브랜드 컬러 종료 순서(UI2-01)**와 **맥락별 폰트 서브셋(UI2-04)**: 01·04·06장까지 같은 값으로 퍼졌다.

이번 라운드에서 새로 드러난 문제는 **"토큰 값은 맞는데, 그 토큰을 어디에 쓰느냐는 규칙이 비어 있어 게이트가 실패하는" 지점**이다.
1. **반전 섹션(CTA 밴드·푸터) 안의 버튼·링크 색 규칙이 없다.** 기본 팔레트 8개 중 6개에서 primary 대 surface-inverse 대비가 3:1에 못 미친다(T8 1.00:1, T1 1.06:1). 표준 트리 끝에 반드시 오는 `cta.band`(bg = inverse 고정)의 주 버튼은 G-03 위반이다. 자동 보정 한도(ΔL 0.15)로는 고칠 수 없다. accent를 텍스트(링크·라벨)로 쓸 때의 대비 조건도 없다.
2. **G-12·AIL-17이 5개 뷰포트에서 "토큰 집합 소속"을 검사하는데, 3.1.5의 유동 타입(clamp)과 컨테이너 중앙 정렬 여백은 768·1024·1536·1920에서 토큰 집합 밖 값을 낸다.** 이대로 구현하면 모든 후보가 "컴파일러 버그"로 폐기된다.
3. **텍스트 역할 표가 AC-03-38("모든 텍스트 노드의 `data-role`이 이 표의 키")을 만족하기에 모자라다.** 버튼 라벨, nav 링크, 폼 라벨, 메뉴 항목·가격 같은 역할이 없다.
4. **헤드라인 줄 예산의 입력이 파이프라인 순서와 맞지 않는다.** 카피 덱은 잡당 1회이고 레이아웃 6개와 병렬로 호출되므로, 덱을 만들 때는 hero variant를 알 수 없다. 덱 제약에 쓸 `maxChars`를 결정할 수 없다는 뜻이다.

네 건 모두 표 1~2개와 문장 몇 줄이면 고칠 수 있다. 방향은 이미 옳다.

### UI3-01 · Major · 반전 섹션의 버튼·링크 색과 accent 텍스트 대비 규칙이 없어, 기본 팔레트 6/8에서 G-03·G-02 실패

- **관련 절**: 03 3.1.3(`primary` "대 bg ≥ 3:1", `focus-inverse`만 반전 섹션 규칙 있음, `accent` "면적 ≤ 10%"만), 3.4.2 팔레트, 3.5.3 state 규칙, 3.6.1 `cta.band` "`bg = inverse` 고정", 3.6.7 표준 트리 "bg → surface → bg → inverse(cta)", 3.13.3 "컴파일러가 accent를 CTA 보조·링크·라벨·괘선에만 사용" / 04 G-02·G-03, §4.11.1 대비 자동 보정(전경 ΔL ≤ 0.15, 배경 ≤ 0.05)
- **허점**: 3.1.3은 반전 섹션 위 **텍스트**(`fg-inverse`)와 **포커스 링**(`focus-inverse`)만 정하고, 반전 섹션 위 **주 버튼·보조 버튼·링크**의 색은 정하지 않는다. 컴파일러가 기본 규칙(primary 버튼, `border-strong` 외곽선, primary 링크)을 그대로 쓰면 결과는 다음과 같다(직접 계산).

| 프리셋 | primary 대 surface-inverse | border-strong 대 surface-inverse | accent 대 bg(텍스트로 쓸 때) |
|---|---|---|---|
| T1 | **1.06** | 4.16 | 5.79 |
| T2 | **2.86** | 3.92 | — |
| T3 | **2.04** | 3.20 | — |
| T4 | **2.17** | 3.18 | **2.75** |
| T5 | 3.13 | **1.00** | **1.22** |
| T6 | 3.02 | 3.40 | **2.16** |
| T7 | **1.42** | 4.44 | — |
| T8 | **1.00** | 4.41 | 6.38 |

  `cta.band`는 PS-1~4·PL·PP 표준 패턴과 표준 트리에 모두 들어가고, `primaryCta`는 필수 슬롯이다. 따라서 T1·T2·T3·T4·T7·T8의 거의 모든 시안에서 G-03("배경과 구분이 필요한 버튼 경계 ≥ 3:1")이 실패한다. 자동 보정은 primary L을 최대 0.15 옮기는데, T8은 primary와 inverse가 같은 L 0.18이라 0.15를 옮겨도 약 1.6:1에 그친다. 게다가 이 보정은 primary 토큰 **전체**를 바꾸므로 라이트 배경 위 버튼까지 바뀐다. T5는 보조(outline) 버튼 테두리가 inverse와 같은 색(1.00:1)이다. accent 쪽도 같다. 3.13.3은 accent를 "링크·라벨"에 쓴다고 하지만 3.1.3에는 accent 대 bg 텍스트 대비 조건이 없다. 그래서 T4·T5·T6에서 accent 라벨은 G-02(4.5:1)에서 실패하고, 보정 한도 안에서는 고칠 수 없다(T5 accent L 0.90 → 0.75여도 약 2:1).
- **왜 문제인가**: 첫 화면 다음으로 눈에 띄는 전환 지점(CTA 밴드)에서 버튼이 보이지 않거나 게이트에서 폐기된다. 폐기가 6후보 모두에서 일어나면 폴백으로 간다. 에이전트는 반전 면의 버튼 스타일(색 반전, 외곽선, primary 유지 중 무엇)과 accent 텍스트 허용 여부를 직접 정해야 한다(C2). 디자인 시스템 리뷰에서 "inverse surface 위 컴포넌트 토큰 부재"는 바로 지적되는 공백이다(C3).
- **보완안 [MVP]**:
  1. 3.1.3에 **반전 면 컴포넌트 매핑**을 추가한다(파생 토큰, 팔레트 추가 없음).
     - `button.primary@inverse`: bg = `fg-inverse`, 글자 = `surface-inverse`. 대비는 fg-inverse 대 inverse와 같으므로 ≥ 4.5가 이미 보장된다. hover는 bg α 0.88.
     - `button.secondary@inverse`: 투명 bg + 1px(bold면 2px) `fg-inverse` 테두리.
     - 링크@inverse = `fg-inverse` + 밑줄.
     - 단, primary 대 inverse ≥ 3:1이고 on-primary 대 primary ≥ 4.5:1이면(T5·T6) primary를 그대로 써도 된다. 이 판정은 `deriveTokens`가 결정론적으로 하고 `tokens.inverseButtonMode: 'primary'|'invert'`로 기록한다.
  2. 3.1.3 `accent` 행에 "텍스트(링크·라벨) 사용은 accent 대 bg ≥ 4.5:1일 때만. 미달이면 accent는 채움(+`on-accent`)·괘선·아이콘(비텍스트, 대 bg ≥ 3:1이 필요한 정보 아이콘 제외)에만 쓴다"를 넣는다. `tokens.accentTextSafe: boolean`을 파생하고, 컴파일러가 이 값에 따라 분기한다. 3.13.3의 "링크·라벨" 문구도 이 조건으로 바꾼다.
  3. 같은 규칙을 이미지 위(`text_over_image`) 버튼에도 적용할지 한 줄로 정한다. 권장안은 오버레이 위에서는 `@inverse` 매핑을 쓰는 것이다.
- **수용 기준**:
  - 32 TokenSet(프리셋 8 × 팔레트 4)에서 반전 면 버튼 경계 ≥ 3:1, 버튼 글자 ≥ 4.5:1, 링크 ≥ 4.5:1을 단위 테스트로 검사하고 100% 통과한다(AC-03-02 쌍 목록에 3쌍 추가).
  - 표준 트리 24개 렌더에서 G-02·G-03 위반 0건이다(AC-03-20에 G-02·G-03 추가).
  - `accentTextSafe = false`인 TokenSet의 렌더에서 accent 색 텍스트 노드가 0건이다(렌더 검사).

### UI3-02 · Major · G-12·AIL-17의 5뷰포트 "토큰 집합" 검사가 유동 타입(clamp)·중앙 정렬 여백·고정 워드마크 크기와 충돌

- **관련 절**: 03 3.1.5 "보간 `clamp(m, A + B·vw, d)`, 375에서 m, 1280에서 d", 3.11.1 xl·2xl 바깥 여백 `(100vw − container)/2`, 3.1.6 "15개 밖의 margin·padding·gap 금지(AIL-17)", 3.5.1 C18·3.1.5a `nav.wordmark` "20~24px 고정(단계 밖)" / 04 G-12 "렌더 computed style의 색·font-size·spacing·radius가 토큰 집합 안(AIL-17)", AIL-17 "허용 오차 0.5px", 4.15.2 렌더 게이트 "5개 뷰포트 … G-12 … + AIL error", 06 6.8.2 "뷰포트 5종 순차 → 게이트 측정"
- **허점**: 토큰 집합에 있는 font-size는 단계별 데스크톱 값 d와 모바일 값 m뿐이다(`typography.<단계>` + `mobileSize`). 그런데 clamp 보간 때문에 768·1024에서는 그 사이 값이 나온다. 직접 계산한 예는 T5 `t-1` 66.6px(768) / 81.3px(1024), `t-display` 85.0 / 106.5px, T1 `t-1` 53.4 / 60.2px로, 모두 집합 밖이다. 여백도 마찬가지다. 컨테이너 중앙 정렬 여백은 1536에서 168px(container 1200), 1920에서 360px로, 4pt 스케일 15개(최대 160) 밖이다. `nav.wordmark`는 단계 밖이라고 명시되어 있어서 모든 뷰포트에서 AIL-17에 걸린다. G-12는 "컴파일러 버그, 후보 폐기"이고 AIL-17은 error(G-09)다. 문서대로 구현하면 **정상 시안 전부가 768·1024·1536·1920에서 폐기된다.** H6·H8은 1280에서만 재므로 이 문제가 없다. 결국 같은 "스케일 준수"를 두 경로가 서로 다르게 재는 셈이다.
- **왜 문제인가**: 에이전트는 테스트가 실패하는 원인이 규칙에 있다는 것을 알게 되고, 결국 허용 오차를 넓히거나 뷰포트를 줄이게 된다. 이것은 CLAUDE.md §3이 금지한 "수용 기준 완화"에 해당한다. 문서가 기대값 함수를 정해 주지 않으면 합법적인 해결책이 없다(C2).
- **보완안 [MVP]**:
  1. 04 G-12·AIL-17 문장을 **"뷰포트별 기대값 소속"**으로 바꾼다. font-size 기대값은 `expectedSize(step, vw) = clamp(m, A + B·vw, d)`(3.1.5 식, 03장이 순수 함수로 제공)이고 허용 오차는 0.5px이다. 색·radius는 그대로다.

### UI3-08 · Minor · FP20 300 웨이트의 "≥ 48px" 판정 기준 뷰포트 미정(AC-03-25 충돌 확장)

- **관련 절**: 03 3.4.4 "300은 크기 ≥ 48px 단계에만, 48px 미만 제목 단계는 400", 3.7.3 FP20, AC-03-25 "heading 요소의 computed font-weight가 1종", 3.4.6 T8 `t-1` 96/44·`t-display` 128/52
- **허점·보완**: UI2-08의 AC-03-25 충돌은 그대로 남아 있고, 문제가 하나 더 있다. T8 `t-1`은 1280에서 96px, 375에서 44px이어서 clamp 중간에 48px을 지난다. 웨이트를 단계별로 고정할지(데스크톱 값 기준이면 300), 뷰포트별로 바꿀지(375에서 400) 정해져 있지 않다. 뷰포트별로 바꾸면 미디어 쿼리 경계와 clamp 교차점이 어긋난다. 권장안은 "판정은 단계의 **데스크톱 크기** 기준, 뷰포트와 무관"이다. 그리고 AC-03-25에 "FP20은 heading 웨이트 2종(300/400) 허용, 페이지 고유 웨이트 ≤ 3 유지"라는 예외를 넣는다.
- **수용 기준**: T8 기본 TokenSet에서 각 단계의 font-weight가 뷰포트 5종에서 같다. AC-03-25가 T8 표준 트리에서 통과한다.
