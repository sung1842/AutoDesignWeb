## 총평

2라운드 Major 5건은 결정(S-32~S-36)이 모두 본문에 들어갔다. `MockupCard.movedAxes`·`diffFromTrue`와 보정 칩 문구 3종(01 1.7.1, 04 4.3, 06 6.4.3), `allowSoftRoundShadow`·`presets:lint-matrix`·카드 그림자 단계(03 3.1.8·3.4), 사진 `tonePref`·업종 키워드 사전·portfolio placeholder(04 4.9.4), `styleguide.html`과 E-14(04 4.16), P-2s·P-4b·변형 층화(07 7.8, 00 §5.1)를 본문에서 확인했다. 특히 PD2-01과 PD2-05는 문구와 기준값까지 들어가 있어 그대로 구현할 수 있다.

남은 문제는 **"고친 곳이 다른 규칙과 다시 부딪히는 곳"**과 **"규칙은 적었지만 시험이 없는 곳"**이다.
1. **S-33의 FP15 수정이 새 위반을 만들었다.** heading 한글을 Wanted Sans로 바꾸면서 body Pretendard가 그대로 남아, 비 mono 패밀리가 3종이 됐다. AC-03-25 정적 검사에서 확정적으로 실패한다(2라운드에 내가 낸 보완안의 계산 착오다).
2. **styleguide가 시안이 아니라 유형 기본값을 보여 준다.** 04장은 서체·팔레트 표기를 `ResultView.guide`와 같은 원천으로 쓰라고 했는데, 그 필드는 앵커 프리셋 값이다(06 6.4.3). 시안의 실제 팔레트·페어링·브랜드 색과 어긋난다.
3. **업종 사진 규칙이 생성 경로에 꽂히지 않았다.** 키워드 사전이 정한 허용 태그를 LLM이 고르는 `slot.tag`나 `image_tags_allowed`(LT-10)와 어떻게 묶는지 적혀 있지 않다. 톤 정렬도 해시 선택식과 결합 의미가 없다.
4. **핵심 출시 게이트 P-2의 베이스라인 렌더 조건이 통제되지 않았다.** 본 시스템은 이미지 팩과 웹폰트를 넣은 채 찍고, 베이스라인 HTML은 이미지·폰트를 무엇으로 렌더할지 정해지지 않았다. 이대로라면 선호율이 "취향 통제"가 아니라 "사진·폰트 유무"를 잰다.
5. **S-32~S-34의 새 규칙에 AC·TC ID가 없다.** 2라운드 수용 기준(칩 문구 일치, 톤 혼용 0, 키워드 픽스처, lint-matrix)이 본문 서술로만 남아 잠금 테스트에 들어가지 않는다.

### PD3-01 · Major · P-2·P-2s 베이스라인의 렌더 조건이 통제되지 않아 선호율이 자산 유무를 잼

- **관련 절**: 07 7.8.1 자극물 행, 7.8.3 베이스라인·P-2s, 7.8.2 P-1a 대조군(텍스트·이미지 치환) / 00 §5.1 A2·A2s, §1 O1 / 04 AC-04-40, AC-04-18(본 시스템 외부 참조 0)
- **허점**:
  - 본 시스템 시안은 이미지 팩 사진(local_business hero는 대부분 `full-bleed-image`), 자체 호스팅 한글 웹폰트(Pretendard·MaruBuri 등), 아이콘 SVG를 포함해 렌더된다. 베이스라인은 "한국어 원페이지 랜딩 HTML을 만들어라 + 브랜드 데이터 블록"뿐이고, 렌더는 "샌드박스 렌더 후 스크린샷만 보관"이라고만 적혀 있다. 베이스라인 HTML이 참조하는 외부 이미지(unsplash URL 등)·Google Fonts·CDN Tailwind를 허용하는지 차단하는지, 차단하면 무엇으로 대체하는지가 없다(06·09장에도 없음).
  - 차단하면 베이스라인은 깨진 이미지 + 시스템 폰트로 찍혀 거의 확정적으로 진다. 허용하면 실행마다 외부 자원 상태에 따라 결과가 달라지고 06장 보안 원칙(외부 요청 없음)과도 맞지 않는다. 어느 쪽이든 선호율은 "사진과 서체가 있는 쪽"을 고르는 비율에 가깝다.
  - P-1a는 사람 대조군의 텍스트·이미지를 골든 브리프 콘텐츠와 이미지 팩으로 치환해 이 교란을 이미 통제했다. P-2·P-2s만 빠져 있다.
- **왜 문제인가**: P-2는 O1·A2·G7b 출시 게이트이고 DF-2의 유일한 사람 증거다. 대기업 디자인 리뷰는 "같은 재료로 비교했는가"를 먼저 묻는다. 자산 비대칭이 남으면 70%를 넘겨도 증거로 인정받지 못한다(C3). 렌더 환경도 에이전트가 정해야 한다(C2).
- **보완안 [MVP]**:
  1. 07 7.8.3에 **베이스라인 자산 동등화** 규칙을 둔다. ① 프롬프트에 해당 브리프 용도·업종의 이미지 팩 후보 목록(상대 경로 `assets/images/<id>.webp` + `altKo` + 태그, 최대 12개)과 허용 서체 목록(`assets/fonts/` 상대 경로 `@font-face` CSS 블록을 프롬프트 부록으로 고정)을 넣는다. ② 렌더는 본 시스템과 같은 워커 렌더러, 같은 로컬 자산 서버, 외부 네트워크 차단으로 한다. ③ 외부 URL `<img>`·`<link>`는 렌더 전에 결정론으로 제거하고, 제거 수를 기록한다.
  2. 적합성 검사: 베이스라인 스크린샷마다 "로드된 이미지 ≥ 1, 한글 텍스트 노드의 실제 폰트가 시스템 폴백이 아님(AC-03-23의 CDP 측정 재사용)"을 확인한다. 미달이면 재요청 규칙(최대 2회)을 적용하고, 그래도 미달이면 제외 수에 넣는다(기존 ≤ 2 상한 유지).
  3. P-2s도 같은 하네스를 쓴다. 잠금 파일 `eval/blind/baseline_assets_appendix.md`를 추가한다.
- **수용 기준**:
  - `pnpm eval:baseline` 산출 리포트에 브리프별 `externalRefsRemoved`, `imagesLoaded`, `systemFontFallback` 값이 있고, 채택된 베이스라인 100%가 `imagesLoaded ≥ 1 ∧ systemFontFallback = 0`이다.
  - 베이스라인 렌더 중 외부 네트워크 요청 0건(렌더러 요청 로그).
  - 07 7.8.3과 00 §5.1 A2 행이 동등화 규칙을 참조한다.

### PD3-02 · Major · styleguide의 서체·팔레트 원천이 앵커 프리셋이라 내보낸 토큰과 어긋남

- **관련 절**: 04 4.16.1 "`styleguide.html`은 `deriveTokens` 결과와 03장 컴포넌트 템플릿만으로 컴파일한다. 서체·팔레트 표기는 결과 화면 ⑤ 디자인 가이드 카드와 같은 함수(`ResultView.guide`)를 쓴다" / 06 6.4.3 `guide: {pairingName, paletteHex, radiusFamily} /* 앵커(또는 override) 프리셋에서 */` / 06 스토리지 표 `exports` 행(공통 파일 목록) / 04 E-14
- **허점**:
  - 시안의 실제 값은 앵커 프리셋 기본값과 다르다. `color.palette_id`는 PAL-T{n}-0~3 중 하나이고, `type.pairing_id`·`shape.radius_family`는 보정과 `enforceVariantL2Diff`로 바뀌며(04 4.4, `v_fit`·`v_bal`은 최소 3키가 다름), 브랜드 색이 들어오면 primary/accent가 바뀐다(03 3.13). `ResultView.guide`는 이 중 어느 것도 반영하지 않는다.
  - 그래서 문장대로 구현하면 한 styleguide 안에서 색 역할 칩(시안 토큰)과 팔레트 표기(유형 기본)가 다른 값을 보인다. 서체 이름도 시안 CSS와 다를 수 있다. E-14는 대비값만 검사하므로 이 불일치를 잡지 못한다.
  - 2라운드 내 보완안 3("같은 원천")이 "같은 표기 함수, 입력은 시안 토큰"이라는 뜻을 분명히 하지 않은 탓이다.
  - 06 스토리지 표의 `dtcg_json` 공통 파일 목록(README·LICENSES·CREDITS·AI_NOTICE + tokens)에 `styleguide.html`이 없다. 04 4.16.1과 다르다.
- **왜 문제인가**: styleguide는 DF-3("취향 → 디자인 시스템")을 사람이 볼 수 있게 만든 유일한 산출물이다. 내보낸 `tokens.json`과 다른 팔레트·서체를 적은 문서는 외주 브리핑에서 오히려 혼선을 만든다. 에이전트는 두 지시 중 하나를 골라야 한다(C2).
- **보완안 [MVP]**:
  1. 04 4.16.1 문장을 "서체·팔레트 **표기 형식**(이름 사전·HEX 표기)은 `ResultView.guide`와 같은 포맷터 `formatGuide(tokens)`를 쓰되, 입력은 해당 버전의 `tokens`·`l2`다. 앵커 프리셋 값은 '유형 기본값' 참고 행으로만 따로 보인다"로 바꾼다. 06 6.4.3의 `guide` 주석에 `formatGuide(presetTokens)`로 만든다고 적어 같은 함수임을 명시한다.
  2. E-14에 "styleguide의 팔레트 HEX·페어링 ID·radius 계열이 같은 버전 `tokens.json`과 100% 일치" 조건을 추가한다.
  3. 06 스토리지 표 `exports` 행의 공통 파일 목록에 `styleguide.html`을 추가한다.
- **수용 기준**:
  - 골든 5케이스 중 브랜드 색 입력 케이스와 `palette_id ≠ PAL-T{n}-0` 케이스가 각 1건 이상 있고, 두 케이스의 styleguide 팔레트 HEX가 `tokens.json` 값과 일치한다(E-14 확장, AC-04-34).
  - `grep -n "styleguide" 06_architecture.md`가 스토리지 표 행에서 1건 이상 나온다.

### PD3-03 · Major · S-33 FP15 수정으로 비 mono 패밀리 3종: AC-03-25·H4와 충돌

- **관련 절**: 03 3.7.3 머리말("비 mono 패밀리 수 ≤ 2(04장 H4 만점 조건)"), FP15 행(heading 한글 Wanted Sans 700/**800**, 라틴 Syne, body **Pretendard 400**), AC-03-25, 3.14.3 H4 / 04 4.10 H4, AIL-03(a) / S-33
- **허점**:
  - FP15의 패밀리는 Wanted Sans, Syne, Pretendard 3종이다. AC-03-25("모든 페어링의 비 mono 패밀리 수 ≤ 2", 정적 검사)는 데이터만으로 확정적으로 실패한다. 같은 장의 다른 라틴 페어링(FP08·FP14·FP16)은 body도 Wanted Sans라서 2종이다.

  - 2라운드 내 보완안 3이 "비 mono 2종 유지"라고 계산을 잘못했고, S-33이 그대로 옮겼다. 에이전트는 잠금 AC를 완화할 수 없으므로 페어링 데이터를 어떻게 바꿀지 스스로 정해야 한다(C2).
- **보완안 [MVP]**: FP15 body를 **Wanted Sans 400**으로 바꾼다. 그러면 패밀리는 Wanted Sans + Syne 2종(H4 만점)이다. 한글 전용 헤드라인이면 사용 패밀리는 Wanted Sans 1종이지만, AIL-03(a) 목록(Inter, Roboto, Arial, system-ui, Geist, Pretendard, Noto Sans KR)에 Wanted Sans가 없으므로 위반이 아니다. FP14(Wanted Sans 단일 한글)와 차별성이 줄어드는 점은 FP15의 라틴 Syne과 heading 700 기본으로 유지한다. S-33 FP15 문장과 03 3.18 행을 함께 고친다. (대안: Syne을 빼고 "Wanted Sans 800 + Pretendard"로 둔다. 다만 FP15의 '실험 디스플레이' 성격이 사라지므로 권하지 않는다.)

  - AC-03-25 정적 검사가 20쌍 전부에서 통과한다(FP15 = 2종).

### PD3-04 · Major · 업종 허용 태그가 `slot.tag`·`image_tags_allowed`(LT-10)와 연결되지 않고, 톤 정렬과 해시 선택의 결합이 미정

- **관련 절**: 04 4.9.4(후보집합 식, 톤·업종 블록), 4.2.1 `layout_constraints.image_tags_allowed: ImageTag[]`, LT-10, 4.6 카피·레이아웃 LLM 출력 / 03 3.10.2(태그당 8~12장, 톤 각 ≥ 30%) / 09 B24
- **허점**:
  - `image_tags_allowed`를 누가 어떻게 계산하는지 어디에도 없다(04장에 선언 1회, LT-10 1회뿐). 키워드 사전의 "허용 태그 부분집합"은 4.9.4에서 **선택 단계**에만 나온다. 매칭이 1건 이상일 때 LLM이 그 부분집합 밖의 태그(예: 미용실 브리프에 `bakery`)를 고르면 어떻게 되는지 규칙이 없다. 그대로 두면 PD2-03에서 지적한 "업종과 무관한 사진"이 매칭 성공 케이스에서도 남는다.
  - 정렬과 선택의 결합이 모호하다. 식은 `asset_id = 후보집합[sha256(…) mod |후보집합|]`인데 "1순위 = 같은 톤, 2순위 = neutral"은 정렬 규칙으로만 적혀 있다. mod가 전체 집합에 걸리면 정렬은 효과가 없다. "1순위 집합이 비어 있지 않으면 그 안에서만 고른다"인지 정해야 한다. 기존 정렬 기준(`asset_id` 오름차순)과 우선순위가 어떻게 겹치는지도 없다.
  - `tonePref = neutral`일 때 "페이지의 첫 사진이 정한 톤"을 따르는데, "첫 사진"의 순서(섹션 순서? 슬롯 순서?)와, 첫 사진이 `common.texture-*`(톤 태그 없음, 3.10.2 "질감 제외")일 때의 처리가 없다.
- **왜 문제인가**: hero 사진은 첫 화면에서 가장 큰 면적이다. 업종 불일치는 P-2 선호율과 F9 채택률을 직접 깎는다. 위 세 지점은 모두 에이전트가 해석해야 하는 제품 결정이다(C2). 같은 입력의 결정론(AC-04-17)은 유지되지만 결과가 의도와 다를 수 있다.
- **보완안 [MVP]**:
  1. 04 4.2.1 명세서 생성 단계에 `image_tags_allowed = purposeTags(p) ∩ industryTags(BrandInput)`을 정의한다. `industryTags`는 키워드 사전 매칭 결과이고, 매칭 0이면 `{storefront} ∪ common.texture-*`이다. 그러면 LLM은 허용 태그만 고르고 LT-10이 강제한다. 4.9.4의 업종 블록은 "매칭 0일 때 hero 외 사진 슬롯 대체"만 남긴다.
  2. 4.9.4 선택식을 단계형으로 고친다. `C1 = 후보 ∩ tone == pageTone`, `C2 = 후보 ∩ tone == neutral`, `C = C1 if |C1| > 0 else C2`, `C = ∅`이면 `fallback_variant`. 각 집합은 `asset_id` 오름차순으로 정렬한 뒤 해시 mod로 고른다.
  3. `pageTone` = `tonePref`가 warm/cool이면 그 값이다. neutral이면 **섹션 순서 → 슬롯 순서로 처음 선택된 톤 태그 있는 사진**의 톤이다. 질감 이미지는 톤 판정에서 건너뛴다.
- **수용 기준**:
  - 키워드 사전 픽스처 30건(매칭 20 + 비매칭 10)에서 `image_tags_allowed`가 기대 집합과 같다(단위 테스트).
  - MockProvider가 허용 밖 태그를 내는 픽스처에서 LT-10 스키마 오류가 난다.
  - 골든 노출 시안의 한 페이지 안 warm↔cool 혼용 0건, `pageTone`과 반대 톤 사진 0건(manifest 대조).

### PD3-06 · Minor · `diffFromTrue` 정렬 기준·L2 쉬운 말 사전의 방향성과 키 범위 미정

- **관련 절**: 01 1.7.1 "상위 2개", 1.15.3 `l2.plain.<key>.<value>`("키 집합은 03장 3.2 L2 enum 전체"), 04 4.4 L2 차이 7키
- **허점·보완**: ① "상위 2개"의 순서가 없다. 4.4 7키 나열 순서(pairing → palette → radius → depth → density → hero → signature)를 고정 우선순위로 명시한다. ② 사전 예시("더 촘촘한 여백")는 비교형인데 키는 값 하나에만 걸려 있어 방향을 표현하지 못한다. 예를 들어 `v_true = compact`, `v_fit = regular`면 "더 여유로운"이 맞지만 값 사전에는 그런 문구가 없다. 순서형 키(density, radius_family, shadow_level, display_boost)는 `l2.plain.<key>.up|down`, 명목형 키(pairing_id, palette_id, signature_id)는 `l2.plain.<key>.changed`("다른 서체 조합", "다른 색 조합")로 둔다. ③ 7키 중 hero variant와 signature_id는 L2 18키 enum이 아니므로 "3.2 L2 enum 전체" 범위에 들어가지 않는다. 키 집합을 "4.4 7키"로 바꾼다. 그러면 사전은 약 20문구로 줄어 temp 시드로 바로 쓸 수 있다.
- **수용 기준**: 1.15.3에 사전 전체 문구가 있고, 단위 테스트에서 순서형 키 4종 × up/down 픽스처의 문구가 방향과 일치한다.

### PD3-07 · Minor · `interface Preset`에 `allowSoftRoundShadow` 필드가 없음

### PD3-08 · Minor · P-4·P-4b의 재인 편향과 동일 쌍 처리

- **관련 절**: 07 7.8.5, 01 1.5.2 ③ 유형 미니 페이지(앵커 프리셋 사전 렌더)
